## Overview

    Validates the pure Simple SSH AES-256-GCM packet wrapper used after NEWKEYS.
    The live SimpleOS SSH blocker fails while decrypting the first encrypted client
    packet, so this spec keeps the coverage at packet scope rather than only at the
    raw AES primitive layer.

    ## Packet Shape

    The encrypted packet is encoded as:

    | Field | Size | Auth Role |
    |-------|------|-----------|
    | packet_length | 4 bytes | AEAD associated data |
    | encrypted body | variable | padding length, payload, padding |
    | tag | 16 bytes | AEAD authentication tag |

    The payload fixture is an SSH `SERVICE_REQUEST` for `ssh-userauth`, matching
    the first normal client-to-server message after NEWKEYS.

    ## Deterministic Fixtures

    This spec does not depend on entropy, sockets, QEMU, or an OpenSSH process.
    Every packet byte is produced by pure Simple code from fixed fixtures:

    | Fixture | Value Shape | Purpose |
    |---------|-------------|---------|
    | traffic key | 32 ascending bytes | AES-256-GCM key input |
    | IV | 12 bytes starting at `0xa0` | SSH GCM invocation base |
    | sequence | `0` | first encrypted packet after NEWKEYS |
    | payload | `SERVICE_REQUEST ssh-userauth` | first expected client request |

    The fixed values make failures reproducible on interpreter, hosted native, and
    baremetal lanes. They also isolate packet construction from transport noise:
    if this spec passes but the live SSH stack still fails, the remaining defect is
    outside the basic packet wrapper round-trip.

    ## Acceptance Checks

    The sequence-zero example proves all of these conditions together:

    1. The first four bytes remain an unencrypted packet length.
    2. The packet length excludes the four length bytes and includes padding.
    3. The authenticated body includes padding length, payload, and zero padding.
    4. The final sixteen bytes are an AES-GCM authentication tag.
    5. Decrypting with the matching SSH sequence returns only the payload.

    The rejection examples guard the live failure's most likely compatibility
    edges: nonce derivation from sequence, tag authentication, key selection,
    packet-length/body mismatch, and maliciously large packet lengths. The
    replay-capture example verifies the exact diagnostic line emitted by the live
    AES-256 failure path includes the sequence, key, IV, packet length, and full
    encrypted packet hex needed to create a later OpenSSH replay fixture.

    ## Failure Modes

    | Case | Expected Result |
    |------|-----------------|
    | sequence 0 | decrypts the packet and returns the service payload |
    | sequence 1 | rejects the packet because the nonce changes |
    | corrupted tag | rejects the packet before exposing payload |
    | wrong key | rejects the packet before exposing payload |
    | body length mismatch | rejects the packet before GCM ambiguity |
    | huge packet length | rejects before the live reader waits for a huge body |
    | live AES-256 decrypt failure | emits replay material for offline SSpec capture |

    ## Debugging Notes

    If sequence-zero decrypt fails, inspect the packet body split first:

    | Check | Likely Defect |
    |-------|---------------|
    | `packet_length` mismatch | SSH packet padding or length arithmetic |
    | tag mismatch at sequence zero | AAD, key, IV, or nonce construction |
    | sequence-one decrypt succeeds | sequence number is not included in nonce |
    | wrong-key decrypt succeeds | AES-GCM authentication is bypassed |

    The live OpenSSH replay fixture is intentionally separate from this deterministic
    guard. A captured OpenSSH packet should be added beside this spec once the
    handshake logger can preserve client key, IV, sequence, ciphertext, and tag
    without leaking unrelated session material.

    The replay fixture below is from an earlier live AES-256 capture gate. It uses
    the runtime KDF oracle key and IV from the same transcript to prove the pure
    Simple packet decryptor accepts the OpenSSH-produced sequence-zero packet.
    OpenSSH sends `SSH_MSG_EXT_INFO` before the later `SERVICE_REQUEST`, so the
    expected plaintext is `ext-info-in-auth@openssh.com`. The old wrong pure-KDF
    fixture is retained as a wrong-key rejection guard. Current native pure KDF
    parity is covered by `ssh_kdf_native_qemu_spec.spl`.

    When the live SimpleOS path negotiates AES-256 and fails packet authentication,
    `SshSession.recv_packet_payload()` emits a single `aes256-gcm replay` serial
    line. Preserve that line from `build/os/x64-ssh-live.serial.log`, then turn it
    into `ssh_aes256_gcm_openssh_replay_spec.spl` with fixed byte arrays.

    ## Step Base

    1. Build deterministic SSH key, IV, and `SERVICE_REQUEST` payload fixtures.
    2. Encrypt the payload with AES-256-GCM at SSH packet sequence zero.
    3. Assert packet length and authentication tag framing.
    4. Decrypt at the matching sequence and compare the payload.
    5. Replay with the wrong sequence, corrupted tag, and wrong key.
    6. Reject packet-length/body mismatch and maliciously large clear lengths.
    7. Format the replay-capture line used by the live failure branch.
    8. Replay a captured OpenSSH AES-256 sequence-zero `EXT_INFO` packet with
       matching runtime-oracle key material and with an old wrong pure-KDF fixture.

    ## Examples

    1. Encrypts and decrypts a post-NEWKEYS service request packet.
    2. Rejects sequence mismatch replay.
    3. Rejects tag corruption.
    4. Rejects wrong-key decrypt.
    5. Rejects packet-length/body mismatch.
    6. Rejects maliciously large encrypted packet lengths.
    7. Formats replay capture material for future OpenSSH packet fixtures.
    8. Decrypts the captured OpenSSH sequence-zero `EXT_INFO` packet with
       runtime-oracle key material.
    9. Rejects the captured OpenSSH packet with the old wrong pure-KDF fixture.

    ## Maintenance Notes

    Keep this spec narrow. It is a packet-wrapper compatibility guard, not a full
    SSH transcript simulator. Add transcript checks to
    `sshd_production_packet_transcript_spec.spl`, add primitive vectors under the
    crypto unit specs, and reserve this file for the boundary where SSH packet
    framing meets AES-256-GCM authentication.
