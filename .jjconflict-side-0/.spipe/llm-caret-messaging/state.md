# Feature: llm-caret-messaging

## Raw Request
Implement an LLM Caret plugin/chat feature for Claude, Codex, Gemini, and LLM Caret; preserve the supplied `llm_caret_messaging` bounded-context recommendation as research, extend the research, plan parallel ownership, and define the SPipe/plugin/skill relationship.

## Task Type
feature

## Refined Goal
Deliver a production LLM Caret messaging subsystem whose primitive Simple room defines canonical chat semantics, whose capability-driven transport adapters bridge external platforms, and whose agent-control adapters safely attach Claude Code, Codex, and Gemini sessions through a composite plugin and dedicated messaging MCP.

## Acceptance Criteria
- AC-1: A separate `llm_caret_messaging` bounded context defines typed identities, rooms, messages, receipts, tasks, artifacts, profiles, bindings, capabilities, and loop-prevention metadata without provider-specific domain types.
- AC-2: The primitive Simple server provides durable account enrollment, rooms, direct rooms, threads/replies, history/cursors, truthful receipts, profiles, tasks, context manifests, ACL/audit, idempotent writes, an outbox, restart recovery, and HTTP plus streaming APIs backed by the pure-Simple `PureDatabase` SQL engine.
- AC-3: `AgentControlPort` adapters support Claude Code, Codex, and Gemini lifecycle/context/task control, including Codex App Server steering with a hook fallback and managed, reversible hook configuration.
- AC-4: `ChatTransportPort` uses versioned `native`, `emulated`, `primitive_sidecar`, and `unsupported` capability levels; no platform branch is added to `provider.spl`, and unsupported native behavior follows an explicit primitive-shadow-room plan.
- AC-5: Stable agent naming, profile/join queries, deterministic main/subagent routing, mention/keyword/reply/previous-message commands, notify-all authorization, progress policies, private-message isolation, and context construction satisfy REQ-LLM-MSG-004 through REQ-LLM-MSG-015.
- AC-6: A composite integration plugin safely merges and removes Claude, Codex, and Gemini hook/settings fragments, verifies owned hashes and executables, exposes a dedicated messaging MCP, and never stores transport secrets in hook files.
- AC-7: The legacy `AgentTeamMailbox`, provider protocol `Message`, provider registry, existing LLM compatibility server, and SPipe documentation MCP retain their bounded roles; compatibility is provided by adapters rather than expanding those types into the network domain.
- AC-8: Unit, adapter-contract, integration, and executable SSpec system tests trace all 17 REQ-LLM-MSG requirements; simulator evidence is labeled as integration evidence and unavailable credential-backed platform rows remain visibly blocked or unsupported.
- AC-9: Security and reliability verification covers webhook authentication, scoped local hook tokens, email-token hashing/expiry, room ACLs, private-room isolation, redaction, replay/idempotency, rate limiting, dead letters, and agent-loop/storm prevention.
- AC-10: Final verification checks matching `doc/06_spec`, `doc/07_guide`, `.codex/skills`, `.agents/skills`, `.claude/skills`, `.claude/agents/spipe`, `.gemini/commands`, feature-expert, SPipe state, and traceability artifacts; generated manuals must be usable without opening their source specs.

## Scope Exclusions
- `AgentTeamMailbox` is not converted into a durable or network mailbox.
- Chat transports are not added to `provider.spl`.
- External consumer accounts are not created from email addresses.
- LINE and KakaoTalk are not advertised beyond capabilities their public APIs actually support.
- Simulator success is not accepted as live-platform evidence.
