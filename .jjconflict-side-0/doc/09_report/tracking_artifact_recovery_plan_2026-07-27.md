## Scope note: the "missing" paths are wrong, not the files

`.claude/rules/structure.md:49-52` claims these auto-generated docs live under
`doc/02_requirements/feature/` and are refreshed "every test run":

```
| Features         | doc/02_requirements/feature/feature.md         | Every test run |
| Pending features  | doc/02_requirements/feature/pending_feature.md  | Every test run |
| Test results      | doc/08_tracking/test/test_result.md             | Every test run |
| Test DB           | doc/08_tracking/test/test_db.sdn                | Every test run |
```

No generator anywhere in `src/` writes to `doc/02_requirements/feature/`. Every
generator (Simple lib, `feature-gen` CLI, and the vendored Rust `doc_gen.rs`)
targets `doc/08_tracking/feature/`, which matches `structure.md`'s own
directory-purpose line ("`08_tracking/` — auto-generated"). At that correct
path, `feature.md` and `pending_feature.md` **do exist** — they are stale, not
missing. `structure.md`'s table itself is the stale artifact here (not fixed
in this pass — read-only audit, one report file only). Only `test_db.sdn` is
genuinely absent, at any path.

## Environmental blocker

`scripts/resource/kill_simple_monitor.shs:14-15` hardcodes `CPU_THRESHOLD=95`
and `MIN_AGE_SECS=60` with no env override (unlike `CHECK_INTERVAL`,
`MEM_THRESHOLD_MB`, etc., which do read `KILL_SIMPLE_*` env vars). Kill logic
at lines 147-153 fires when a `bin/simple test`/`run` process (matched by
`is_simple_run_or_test`, line 61) has been alive ≥60s AND is pegged at ≥95%
CPU. `is_protected()` (lines 41-57) exempts anything whose argv contains
`claude`, `codex`, `tmux`, `node`, `npm`, or the MCP/LSP daemon binaries —
confirming the documented bypass is a `claude` (or similar) token in argv.

Note: `doc/09_report/kill_simple_monitor_rules_and_test_exemption_2026-07-27.md`,
cited in the task, **does not exist in this checkout** — cite the script
directly (as above) instead of that doc.

## Ordered recovery plan

1. **Trigger a scoped test run to create/refresh `test_db.sdn` and
   `test_result.md` in one shot.** Pick a small, fast directory (e.g.
   `src/lib/common/text` or another narrow unit-test slice) so the process
   exits well inside the monitor's 60s/95%-CPU kill window:
   ```
   bin/simple test src/lib/common/text --no-progress --no-cover-check
   ```
   Expected runtime: seconds to low tens-of-seconds for a narrow directory
   (vs. the full suite, which the task states cannot complete on this
   machine). This is the only command that both creates the missing
   `test_db.sdn` (stable) and rewrites the 69-day-stale `test_result.md`,
   since both come from the same `update_test_database()` → `db.save()` →
   `generate_test_result_md()` sequence (`test_runner_main.spl:874,907-912`).

2. **Regenerate `feature.md` from the already-current `feature_db.sdn`.**
   `feature_db.sdn` was committed today (`a9bf5c9`), so no test run is needed:
   ```
   bin/simple feature-gen
   ```
   Expected runtime: sub-second — it only reads/parses one `.sdn` file and
   writes Markdown.

3. **Validate/repair the newly-created `test_db.sdn` for structural issues**
   (cheap, catches a bad first write before it's relied on):
   ```
   bin/simple check-dbs
   bin/simple fix-dbs --dry-run
   ```

4. **`pending_feature.md` has no live regeneration path today** — its only
   generator, `generate_pending_feature_md` inside `generate_all_docs`
   (`doc_generator.spl:326-336`), is orphaned: both former call sites in
   `test_runner_main.spl:37` and `test_runner_modes.spl:26` are commented out,
   and `feature-gen` never calls it. Restoring this file requires a source
   change (re-wire the commented `use` + call, or add a `--pending` flag to
   `feature-gen`) that is out of scope for this read-only audit. File this as
   a follow-up bug: **"pending_feature.md generator is dead code — no CLI
   path produces it."**

5. **Once steps 1-3 land, re-run step 1's scoped command against a couple
   more directories** (or, machine load permitting, the full suite in the
   background with `run_in_background`) to build real pass/fail numbers
   before trusting `test_result.md`'s percentages for planning — one narrow
   directory only proves the pipeline works, not overall project health.

6. **Separately** (per the task): the off-by-one first-character stripping
   bug in `test_result.md`'s entries ("ookup on empty table", etc.) is being
   fixed by another agent — re-run step 1 again after that lands so the
   regenerated file doesn't carry the corruption forward.
