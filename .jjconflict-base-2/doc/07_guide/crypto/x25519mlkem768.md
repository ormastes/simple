# X25519MLKEM768

Simple implements the TLS hybrid group defined by
`draft-ietf-tls-ecdhe-mlkem-05`, using NamedGroup `0x11EC` and FIPS 203
ML-KEM-768. The client share is `ek || X25519_public` (1216 bytes), the server
share is `ciphertext || X25519_public` (1120 bytes), and the key-schedule input
is `ML-KEM_secret || X25519_secret` (64 bytes).

Draft `-05` now marks X25519MLKEM768 `Recommended: Y` after a second IETF Last
Call, but it is not yet a published RFC. NIST also records a future-correction
planning note for FIPS 203, so configs and retained artifacts bind the exact
draft/FIPS profile rather than an unversioned algorithm name. Hybrid-first
ClientHello messages can exceed a common TCP MSS; the parser accepts the
complete reassembled handshake and the implementation must not silently
downgrade merely because the larger message exposes a broken middlebox.

Import `os.crypto.x25519_mlkem768` for the versioned config, deterministic
keygen/encapsulation/decapsulation APIs, backend evidence, and composition
helper.

## Current status: primitives work, TLS wiring does not (yet)

The cryptographic primitives — keygen, encapsulation, decapsulation, and the
hybrid secret combine — are implemented, tested against the scalar oracle and
NIST ACVP/`mlkem-native` vectors, and independently benchmarked (see
[Performance](#performance) below).

**End-to-end TLS 1.3 handshake negotiation of X25519MLKEM768 is currently
BLOCKED in production code, not merely unbenchmarked.** As of the 2026-08-05
AC-9 measurement pass:

- The server path (`src/os/tls13/server_handshake.spl`) always calls its
  hybrid handshake preparation function with an **empty** ML-KEM
  encapsulation seed — by design, per the code's own comment, so
  X25519MLKEM768 is structurally never offered on the production server path.
- The client connect path (`src/os/tls13/_Tls13/`) has **zero** references to
  ML-KEM, hybrid negotiation, or the `0x11EC` group code point.

Net effect: no code path in this tree currently completes a real TLS 1.3
handshake that negotiates X25519MLKEM768. Names like
`enable_x25519_mlkem768`/`require_x25519_mlkem768` exist as config fields
exercised by integration-test fixtures, and `tls13_accept_x25519_mlkem768*`
appears in fail-closed/deadline-handling code paths, but none of these are
reachable from the shipping server-accept or client-connect flow yet. Treat
this guide's protocol/wire-format/API description below as accurate for the
**primitive layer** (`os.crypto.x25519_mlkem768`) and as **not yet true** for
"my TLS server/client will negotiate X25519MLKEM768 if I flip this flag."
The resume path (wiring a real KEM seed into the server call and adding
hybrid group offering to the client) is tracked in
`doc/09_report/x25519mlkem768_acceleration_performance_2026-08-05.md` §4.

At the primitive layer, live TLS code intends to opt in with
`enable_x25519_mlkem768`; setting `require_x25519_mlkem768` additionally
rejects classical negotiation once the wiring above lands. The fd runtime
shortcut fails closed because it cannot encode the hybrid share. Servers are
intended to use `tls13_accept_x25519_mlkem768`, which takes a backend config
and draws independent server random, X25519 scalar, and ML-KEM encapsulation
randomness — but see the BLOCKED note above for why this is not yet reachable
from `server.spl` in practice.

## Backend selection: `suggest` vs `require`

Backend selection has two modes, resolved by
`x25519_mlkem768_resolve_backend(config, operation)`
(`src/os/crypto/x25519_mlkem768/execution_policy.spl`), which every
production entry point (`x25519_mlkem768_keygen`/`_encapsulate`/`_decapsulate`)
calls unconditionally as its first step:

- **`Suggest`** — if the requested backend is unavailable or not yet
  promoted, resolution still succeeds (`Ok`), silently falls back to the
  scalar CPU oracle, and records the fallback honestly: `fallback_used=true`
  plus a human-readable `fallback_reason`.
- **`Require`** — fails closed (`Err`) with reason "requested X25519MLKEM768
  backend has no promoted native implementation" if that backend lacks
  native correctness, provenance, coverage, and performance evidence. No
  silent fallback ever occurs under `Require`; the caller gets a `Result` it
  cannot ignore without explicitly discarding it.

This was independently re-verified live on 2026-08-05
(`doc/09_report/x25519mlkem768_ac6_fail_closed_verification_2026-08-05.md`,
AC-6): resolution is **promotion-gated, not hardware-detection-gated**. As of
that verification, `Automatic` and `ScalarCpu` always resolve successfully;
every specialized backend (`Avx2`, `Neon`, `Rvv`, `Cuda`, `Vulkan`, `Metal`)
is currently *not promoted*, regardless of whether the underlying hardware is
physically present on the host. Concretely, on a host with two real NVIDIA
GPUs and a working Vulkan 1.3 instance:

| requested backend | `suggest` | `require` |
|---|---|---|
| `automatic` / `scalar-cpu` | `Ok`, no fallback | `Ok`, no fallback |
| `avx2` / `neon` / `rvv` | `Ok`, falls back to scalar-cpu, reason recorded | `Err`, fails closed |
| `cuda` / `vulkan` | `Ok`, falls back to scalar-cpu, reason recorded (hardware present is irrelevant to this gate) | `Err`, fails closed |
| `metal` | `Ok`, falls back to scalar-cpu, reason recorded | `Err`, fails closed |

In practice: `require`-ing any accelerated backend today always fails
closed, on any host, until that backend is explicitly promoted. If you want
"use the fastest thing available, and I don't mind if that's scalar," use
`Suggest` and check `fallback_used`/`fallback_reason` on the returned
evidence. If you want a hard guarantee that a specific accelerated
implementation ran (e.g. for a compliance or performance SLA), use `Require`
and expect it to fail until promotion lands — do not interpret the failure as
a hardware or driver problem on your host.

The scalar CPU implementation is the oracle. Native NTT/INTT acceleration uses
a typed-array `std.simd` façade backed by the production C runtime: AVX2 uses
eight i32 lanes, NEON uses four, and RVV strip-mines using the public VLEN.
Every candidate operation requires a positive vector-chunk counter and exact
scalar equality. The canonical probe is
`scripts/check/check-x25519mlkem768-cpu-simd.shs`; QEMU proves ARM/RISC-V
correctness but not native performance. Full-operation coverage and performance
gates still prohibit production promotion. CUDA, Vulkan, and Metal additionally
require device compilation, submission, completion/fence, readback, identity,
and byte equality on the canonical fixture — see the next section for current
GPU evidence status.

## GPU acceleration status

The evidence bar for any GPU backend claim is: real device compilation, real
submission, a real completion fence, a real device-originated readback, and
byte-exact agreement with the scalar oracle on the canonical fixture
(`ntt-v1-p97-i29-c17-q3329`). A CPU-mirror pass, a hash comparison without
execution, or a self-referential "the branch that asserts its own admission
reason" test does not meet this bar and must not be read as device evidence.

As of 2026-08-05, at the NTT-kernel level, both GPU backends meet that bar on
real hardware:

- **CUDA**: kernel source
  (`src/os/crypto/x25519_mlkem768/kernels/ml_kem_ntt_forward.ptx`), the
  independent Driver-API probe (`test/fixtures/crypto/x25519mlkem768/cuda_ntt_probe.c`),
  and the build/verify script (`scripts/check/check-x25519mlkem768-cuda-ntt.shs`)
  produce deterministic cubins (built twice, byte-compared) matching the
  pinned digests, then compile + submit + fence + read back + oracle-match on
  **two physical devices**: `NVIDIA RTX A6000` (sm_86) and `NVIDIA TITAN RTX`
  (sm_75), via `nvcc`/`ptxas` 13.0. Evidence lands at
  `build/evidence/x25519mlkem768/cuda/sm_{75,86}.cubin` (gitignored build
  output, regenerate with the script above).
- **Vulkan**: GLSL compute-shader source
  (`src/os/crypto/x25519_mlkem768/kernels/ml_kem_ntt_{forward,inverse}.comp`)
  compiles to SPIR-V bit-identical to the pinned digests via
  `glslangValidator --target-env vulkan1.1`, validates with `spirv-val`, and
  the build/verify script (`scripts/check/check-x25519mlkem768-vulkan-ntt.shs`)
  runs a full compile/submit/fence/readback/oracle-match sweep across both
  forward and inverse stages on the same two physical NVIDIA devices.
  Evidence lands at
  `build/evidence/x25519mlkem768/vulkan/x25519mlkem768_ntt_{forward,inverse}.spv`.
  A prior barrier/coefficient-mismatch investigation
  (`doc/08_tracking/bug/x25519mlkem768_vulkan_ntt_negative_modulo_driver_defect_2026-08-05.md`)
  root-caused a negative-operand GLSL `%` (`OpSMod`) defect in this host's
  NVIDIA Vulkan compute driver path; the unmodified original shader source
  now reproduces cleanly once that was understood.
- **Metal**: the physical-device receipt format and admission logic (pinned
  metallib, registry-id/Darwin-build identity, `MTLGPUFamily::Metal3`
  capability check from a live device handle) are implemented, but physical
  execution remains blocked — there is no macOS/Metal hardware in this
  environment to run it on.

**Known gaps, current as of 2026-08-05:**

- **Promotion.** Real device-level NTT kernel evidence existing does not mean
  CUDA/Vulkan are promoted production backends — see the `suggest`/`require`
  table above. `require cuda` and `require vulkan` still fail closed today
  even on a host with the hardware and passing kernel evidence, because
  promotion additionally needs full-operation coverage and performance gates
  that have not been completed.
- **Artifacts are not committed.** The underlying build artifacts (`.cubin`,
  `.spv`) are gitignored build output and must be regenerated locally with
  the check scripts above before a GPU-backed spec can pass; they are not
  committed to the repository.
- **CUDA integration spec currently blocked by an unrelated compiler defect.**
  `bin/simple test test/02_integration/os/crypto/x25519mlkem768_cuda_binary_execution_spec.spl`
  fails with `semantic: unknown extern function: rt_array_data_ptr_u8` — the
  interpreter (which `bin/simple test` uses by default) has no adapter for
  that runtime symbol, even though it exists for codegen/JIT. This is a
  compiler/runtime interpreter-extern gap, not a crypto or GPU-artifact
  defect; the independent non-Simple physical evidence above
  (`sh scripts/check/check-x25519mlkem768-cuda-ntt.shs`) is unaffected by it.
  The Vulkan integration spec
  (`test/02_integration/os/crypto/x25519mlkem768_vulkan_candidate_spec.spl`)
  does not hit this gap and passes end-to-end (`3 total, 3 passed`).

The canonical public NTT data is fixture
`ntt-v1-p97-i29-c17-q3329` in
`test/fixtures/crypto/x25519mlkem768/canonical_fixture.spl`; native C probes
include the paired `ntt_fixture.h`, and Metal emits the same id. Do not compare
or promote receipts with a different fixture id. Full-candidate evidence hashes
only public client/server wire shares, never seeds, private keys, randomness,
decapsulation keys, or shared secrets.

Run evidence with the contract documented in
`doc/03_plan/sys_test/x25519mlkem768_acceleration.md`. The pinned NIST ACVP and
`mlkem-native` provenance lives in
`test/fixtures/crypto/x25519mlkem768/manifest.sdn`.

The independent-oracle preflight compares one complete 2,464-byte public and
secret-result bundle: 1,216-byte client share, 1,120-byte server share,
64-byte server secret, and 64-byte recovered client secret. It rejects missing,
truncated, mislabeled, or empty pure-Simple/oracle inputs before the shared
Alpha/Beta/Normal chooser can apply its generic one-sided fallback behavior.
Normal mode proves selection only; it is not a differential-parity claim.

The free/open oracle manifest v4 accepts a current Go or CIRCL PASS only when
its regular no-follow retained log and receipt exist and hash-match. Each log
must contain exactly one comparator-bound record for Set A (ML-KEM), Set B
(X25519), and Set C (hybrid), including exact output lengths and SHA-256 values
computed from the compared bytes. Missing, swapped, truncated, or relabeled
logs fail closed; literal PASS labels are not execution evidence.

GPU dispatch treats fixture and runner hashes as untrusted labels. It reopens
the canonical manifest, fixture, and runner through regular no-follow paths,
requires lowercase SHA-256 identities, and rehashes all three at the mutation
gate. Imported RVV receipts are independently checked by both the matrix and
executed-row consumers: VLEN must be a power of two in 128..65536, and non-RVV
rows must carry zero RVV metadata.

Checked ML-KEM APIs treat generic `list` values as untrusted integers rather
than implicit bytes. Scalar, SIMD, and provider key generation,
encapsulation, and decapsulation reject every negative or greater-than-255
element before cryptographic work; validation covers the complete encoded
decapsulation key and checks returned ciphertext/shared-secret octets as well.

For source-matched compiler bring-up, the manifest also pins
`pure_simple_oracle_probe.spl`. It is ordinary Simple rather than SPipe DSL and
checks the same key, ciphertext, and shared-secret digests. A passing type
check is available. The full stage-3 streaming route bypasses the tracked
entry-closure aggregate-transport crash and reaches HIR, but no source-matched
probe binary has completed; native cryptographic PASS still requires that
binary to exit zero.

Current correctness and coverage status is recorded in
`doc/09_report/x25519mlkem768_acceleration_evidence_2026-08-02.md`; current
performance status is recorded in
`doc/09_report/x25519mlkem768_acceleration_performance_2026-08-05.md` (see
[Performance](#performance) below). Missing measurements and blocked hosts
are release blockers, not skips.

## Performance

The 2026-08-05 AC-9 report
(`doc/09_report/x25519mlkem768_acceleration_performance_2026-08-05.md`)
provides the first complete, externally-timed, paired/rotated-order
measurement (n=17 repeats per operation) of keygen, encapsulation,
decapsulation, hybrid-combine, and a full keygen→encapsulate→decapsulate
exchange (`kex`) — everything AC-9 asks for **except** the end-to-end TLS 1.3
handshake leg, which is reported BLOCKED (see
[Current status](#current-status-primitives-work-tls-wiring-does-not-yet)
above), not approximated with a proxy number.

| operation | n | median | min | max | throughput |
|---|---|---|---|---|---|
| keygen | 17 | 8042.4 ms | 6375.0 ms | 15661.7 ms | 0.124 ops/s |
| encapsulate | 17 | 8407.5 ms | 5450.6 ms | 13032.4 ms | 0.119 ops/s |
| decapsulate | 17 | 7942.7 ms | 4589.1 ms | 15542.8 ms | 0.126 ops/s |
| hybrid-combine | 17 | 1.013 ms | 0.432 ms | 1.875 ms | 986.8 ops/s |
| full hybrid exchange (`kex`, keygen+encapsulate+decapsulate — not a TLS handshake) | 17 | 23153.2 ms | 17009.5 ms | 39216.7 ms | 0.043 ops/s |

Max RSS was flat across every operation, 60.7–61.3 MB, dominated by
interpreter/module-load baseline rather than per-operation allocation.

**Read these numbers as an interpreter-dispatch baseline, not an algorithm
cost.** Every operation above except `hybrid-combine` passes through
`x25519_mlkem768_resolve_backend`, which currently hits two JIT-fallback
blockers (an HIR type-inference gap on an imported-struct `bool` field, and
an unresolved `cuda_module_load_binary` symbol) that silently drop the
calling function to the tree-walk interpreter — this is why keygen/
encapsulate/decapsulate measure ~8 seconds each while `hybrid-combine`, whose
call path avoids `resolve_backend`, measures ~1 millisecond: three orders of
magnitude difference from interpreter dispatch overhead alone, not from the
underlying cryptography. This is tracked separately in
`doc/08_tracking/bug/x25519mlkem768_jit_fallback_interpreted_execution_2026-08-05.md`.
Only a Rust-built bootstrap seed binary was available at measurement time —
no self-hosted `simple` binary exists in this tree yet — so these numbers
also do not reflect self-hosted-compiler performance.

## Security notes

The checked ML-KEM boundary validates lengths, canonical public key encoding,
strict octet range for every generic-list input and checked output, embedded
decapsulation-key hash, implicit rejection, and X25519 all-zero output.
Production TLS no longer uses fixed ephemeral material or logs traffic
secrets. The authored critical-branch inventory currently covers 30 owners
and 173 logical conditions as 346 required true/false outcomes; it is a
denominator, not measured coverage.

**Secret zeroization is a documented, accepted limitation, not an implied
property.** `src/os/crypto/ml_kem.spl` overwrites function-owned secret
material (key-generation slices, encapsulation/decapsulation buffers, FO
messages/coins, candidate and implicit secrets, error-path temporaries)
immediately after use, and this best-effort wipe is spec-verified to zero
every owned list/byte-array element it reaches
(`test/01_unit/os/crypto/x25519mlkem768_hybrid_support_spec.spl`). It
deliberately does not — and, on the current GC-managed `list`/runtime, cannot
— guarantee that GC/compiler-created copies, SHA3/SHAKE sponge internals, or
K-PKE polynomial temporaries never leave a stale copy in memory; caller-owned
seeds, keys, ciphertexts, messages, and returned shared secrets remain the
caller's responsibility to release. This scope was formally decided
2026-08-05 (NFR-005 re-scoped per AC-10; see
`doc/08_tracking/bug/mlkem_gc_secret_zeroization_limit_2026-08-03.md`): a
canonical non-GC secure-zero owner type would close the remaining exposure
but is out of scope for this campaign — it needs a new secret-byte owner
type, a K-PKE/NTT/Keccak hot-path rewrite off GC-managed lists, and
heap-forensics verification that does not exist anywhere in this codebase
today. The unobservable half (whether a secret can be proven gone from all
memory) is documented rather than test-asserted, per AC-10's "tested where
observable" clause.

The runtime C SIMD dispatch has a separate incremental gcov denominator for
x86 AVX2/scalar, AArch64 NEON, and RV64 RVV. Its arc counts measure compiled C
control-flow outcomes only; they are neither Simple source-condition coverage
nor GPU execution. Cross-lane merged SDN output remains diagnostic until the
merge validator directly binds and compares the authoritative denominator.

## Performance-promotion evidence chain

Performance promotion uses the following public-only chain:

1. Re-admit all seven Matrix v2 source rows and mint one exact backend
   measurement qualification v3. It binds scalar and candidate configuration,
   artifact, and executor identities; fixes Set A/B/C to
   ML-KEM/X25519/hybrid order; and binds a runtime-owned platform observation
   containing the exact monotonic-clock provider, per-run CSPRNG nonce digest,
   host target, runner/observer artifact, and physical peak RSS. Post-workload
   RSS refresh preserves that original session nonce, recomputes the
   observation hash, and rejects observer-identity drift.
2. Admit role-fixed scalar and candidate warm setup outside the timed interval.
3. Retain 30..1024 ordered full-exchange nanosecond samples and admit raw
   timing receipt v3. One exchange is exactly keygen + encapsulate +
   decapsulate. The v3 receipt hash binds the actual GPU kernel-event count and
   one bounded SIMD hit count per candidate sample. Each SIMD entry must be at
   least three and the checked sum must equal the aggregate; scalar/GPU vectors
   are empty.
4. Admit paired schedule v1 over the same even count in 30..1024 of zero-based
   ordinals. Each ordinal
   retains scalar and candidate monotonic start/finish intervals whose exact
   durations equal the corresponding raw samples. Even ordinals run scalar
   then candidate; odd ordinals run candidate then scalar, giving ABBA order
   across adjacent pairs. Successive pairs may not overlap.
5. Derive p50/p95/p99 and operations per second (three operations per complete
   exchange) from those samples, then admit performance attestation v7 and any
   backend-specific promotion receipt. Its qualified-timing hash binds the
   paired-schedule receipt hash.

Raw timing rejects setup, kernel-only work, fallback, correctness mismatch, and
incomplete acceleration evidence. GPU receipts require equal positive
transfer, launch, synchronization, device-readback, and kernel-event totals;
the total must cover at least three high-level operations per exchange and may
be larger when an operation dispatches multiple kernels. Scalar and SIMD
receipts require all five GPU totals to be zero. Use
`scripts/check/check-x25519mlkem768-scalar-perf.shs` is a diagnostic scalar
microbenchmark only: its timer and fixture differ from the typed paired
collector, so it is not a valid speedup denominator. Promotion must use the
same-run typed scalar/candidate ABBA samples over the qualified workload. The contract scenarios are
`test/01_unit/lib/common/crypto/x25519mlkem768_qualified_timing_spec.spl` and
`x25519mlkem768_performance_attestation_spec.spl`. Synthetic unit fixtures are
never physical-performance evidence. Hashes provide integrity, not collector
authentication; release evidence must come from the retained prebuilt collector
on the named physical host.

The SIMD timing entrypoint does not accept caller-created batches or RSS
integers. It owns both scalar and candidate exchanges, copies every mutable
input before each timed span, alternates ABBA order, and returns both admitted
timing receipts plus paired schedule v1. Session, clock, host, runner, and peak
RSS come from qualification-v6's runtime-owned observation. Physical
x86/ARM/RISC-V evidence uses the qualification returned by the collector,
because it contains the same-session post-workload live identity/RSS refresh.
Before either timed role runs, paired SIMD collection requires AVX2, NEON, or
RVV with `Require`, `AbsoluteAndScalar`, `minimum_batch = 1`, and
`batch_size = 1`; a suggested backend or claimed larger batch is not exact
paired evidence. Each returned SIMD observation binds requested/resolved
backend, the admitted configuration digest, ABBA order, and timed state. The
collector independently validates the returned spans and re-admits those
bindings before retaining a sample. It rejects the workload before timing
unless qualification v6 and the actual `client_private`, `d`, `z`,
`server_private`, and `m` produce the canonical domain-separated semantic
digest, and unless derived client/server public-share digests equal the
qualification's canonical fixture digests. It rechecks raw inputs after the
samples. Physical
x86/ARM/RISC-V evidence still requires running the collector on the named
hosts. Qualification v6 binds canonical typed candidate/scalar configuration
digests as well as the GPU build-admission digest. CUDA and
Vulkan executor-owned minters now bind the exact binary set, cache key, device
name/capability, and UUID-derived or full driver identity. Their generic paired
entry point remains fail closed, while the concrete CUDA/Vulkan/Metal collectors
retain the same executor across every full exchange. Before executor creation
they double-snapshot regular/no-follow source and binary paths, compare them to
the live admission, and rehash them after the workload. This code is not a
physical timing claim until its focused SSpecs and device runs execute through
an admitted self-hosted binary. CUDA, Vulkan, and Metal reject any raw-input mismatch
before runner/artifact/executor access and recheck at final admission; equal
public outputs therefore cannot hide clamped private-input aliases.
Metal now binds a pinned metallib, stable registry-id/Darwin-build identity,
and `supportsFamily(MTLGPUFamily::Metal3)` capability from the same retained
device handle. Unsupported devices reject before queue/shader creation, and
the admission minter consumes the observed session field rather than assigning
`metal3`. Physical execution remains blocked on macOS.
