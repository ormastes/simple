# Feature: environment_optimized_dynamic_libraries

## Raw Request
Research further and create an Astra-led design and plan in parallel with smaller-model reviewers for environment-optimized dynamic libraries spanning SIMD tiers, compiler/JIT/AOT specialization, shared parsing, and GPU-resident execution.

## Task Type
feature

## Refined Goal
Define a buildable, testable architecture and staged delivery plan for baseline-safe environment-selected provider families that optimize Simple's parser and generated native/JIT/AOT code while preserving exact capability, ABI, semantic, lifetime, and execution-evidence contracts across CPU, native dynlib, SMF, and GPU placements.

## Acceptance Criteria
- AC-1: Local and domain research identify current implemented seams, placeholders, contradictions, and authoritative external mechanisms with exact source references.
- AC-2: Feature and NFR option documents provide 2-4 alternatives with description, pros, cons, and effort; final requirements are written only after explicit user selection and unchosen option files are deleted.
- AC-3: Architecture separates host execution environment, target codegen profile, artifact placement, and workload execution policy, and defines admission separately from execution placement.
- AC-4: Versioned contracts `EnvironmentSnapshotV1`, `VariantDescriptorV1`, `BindingPlanV1`, and `FrontendFacetV1` specify bounded decoding, exact capability predicates, ABI/artifact identity, dependency closure, generation pinning, and truthful admission/execution receipts.
- AC-5: Design covers baseline-safe startup, hot-call dispatch without per-token lookup/locking, native/SMF/JIT adapters, cache keys and invalidation, parser legacy/canonical parity, GPU device-program admission, cancellation, retirement, and safe fallback.
- AC-6: The plan stages observation, explicit opt-in, parser-only SIMD variants, generated dynlib/JIT/AOT specialization, and GPU-resident islands without requiring a whole-executable ISA matrix.
- AC-7: System-test planning traces every requirement to real assertions and defines `setup_environment_catalog`, `step_admit_variant`, `step_bind_provider`, and `check_execution_receipt`; unfinished executable scenarios use `fail(...)`, never placeholder passes.
- AC-8: Verification plans cover baseline/v2/v3/v4 feature-negative cases, OS vector state, cross-architecture rejection, native/SMF callable proof, JIT/AOT emitted-code evidence, parser dialect parity/tails/guard pages, GPU negative controls/fences, concurrency/lifetime, cold/warm latency, p95/p99, RSS, transfers, and artifact size.
- AC-9: Every unavailable hardware/host row remains an active blocked/TODO criterion with owner, prerequisite, exact resume command, retained artifacts, and final reviewer; current-host evidence cannot close the umbrella feature.
- AC-10: Knowledge is refreshed in research/requirements/architecture/design/plan, `doc/07_guide`, feature- and layer-expert skills, and gap-specific `doc/08_tracking/bug` records plus must-check ledger v3 ownership. `doc/06_spec` and workflow skills/commands are N/A until executable scenarios or workflow contracts change; if they do, they become mandatory.
- AC-11: The smallest bootstrap projection is baseline core plus composition/catalog and parser provider seam; no Rust-seed fallback, implicit full bootstrap, release, push, or capability promotion is allowed by this research/design lane.
- AC-12: A highest-capability reviewer resolves contradictions and rejects unsupported done marks after lower-model sidecar work is merged.
