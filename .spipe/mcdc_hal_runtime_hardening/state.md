## Task Type

## Refined Goal
Deliver production MC/DC coverage and runtime/HAL differential-testing infrastructure that can be compiled completely out, enabled statically, or loaded dynamically with bounded overhead; routes tagged operations through Pure Simple, C, and Rust providers for deterministic comparison; and drives environment interactions from extracted instructions while allowing only explicit reasoned exclusions from the 100% normal-mode MC/DC gate.

## Acceptance Criteria
- AC-1: Local and domain research identify the existing coverage, aspect/dynload, runtime/HAL tag, dual-backend, I/O comparison, environment-test, and skip/exclusion owners; final feature and NFR requirements are written only after the user selects options with pros, cons, and effort, and unchosen option files are deleted.
- AC-2: The compiler and runner collect true decision and condition outcomes for every eligible Boolean decision, including short-circuit and nested conditions, and a focused oracle suite detects cases where branch or statement coverage is 100% but MC/DC is not.
- AC-3: Coverage reports define stable decision/condition identities, witnessed independence pairs, source locations, eligible/excluded totals, and deterministic merge behavior across processes and repeated runs; normal mode fails unless eligible MC/DC is exactly 100%.
- AC-4: MC/DC supports three explicit build/runtime policies: static-off emits no probes, branches, tables, allocations, logging calls, dynload checks, or linked coverage payload; static-on uses compiled instrumentation; dynamic mode loads the coverage aspect only when requested and remains unloaded otherwise.
- AC-5: Static-off native artifacts pass a code/IR or symbol-level equivalence gate against an instrumentation-free build and a representative benchmark demonstrates zero measurable instrumentation work; static-on and dynamic-idle/active paths meet the user-selected latency, throughput, binary-size, peak-RSS, allocation, and log-volume NFR budgets on realistic fixtures.
- AC-6: Dynamic coverage uses the canonical aspect/dynload ownership path, performs no repeated full-tree scan or per-event load lookup, bounds buffers and log output, unloads/settles safely, and preserves complete coverage data on normal shutdown and defined failure paths.
- AC-7: A canonical `rt(hal)` tag declares operation identity, provider availability, comparison semantics, normalization rules, side-effect authority, and environment requirements without introducing per-OS app implementations or raw runtime shortcuts outside owner facades.
- AC-8: Tagged operations can run Pure Simple, C, and Rust implementations under the canonical dual-backend modes: `alpha` runs all applicable providers and stops on a difference, `beta` runs all applicable providers and emits a bounded critical difference report, and `normal` runs only the configured preferred provider; provider execution may be parallel only where isolation and deterministic parent-authoritative comparison make side effects safe.
- AC-9: Existing I/O comparison is migrated or adapted to the canonical tag path, demonstrates equal results and error semantics for representative file, stream, process, and environment interactions, and supports optional configuration for provider priority and comparison policy while preserving a documented no-config default.
- AC-10: Runtime/HAL tests are split into a pure extraction stage that emits typed, versioned environment-access instructions and an environment executor that performs each requested interaction, records inputs/results/provenance, and returns them for deterministic provider comparison without hidden direct environment access in the test logic.
- AC-11: The environment instruction protocol covers every runtime/HAL interaction required by the selected scope, rejects unknown or malformed instructions, bounds payloads/time/resources, prevents unsafe replay or duplicate side effects, and has contract tests plus at least one live current-host integration path per producible interaction class.
- AC-12: Scenario exclusion has one canonical structured expression requiring a stable reason code and human-readable reason, identifies the unavailable capability or intrinsically unproducible condition, appears as excluded (never PASS), and is removed from the MC/DC denominator only when a checker validates the reason; blank, generic, stale, or locally producible skips fail verification.
- AC-13: Executable SSpec scenarios and their generated/manual documents trace every requirement, include deliberate-red fixtures for incomplete MC/DC and invalid skips, contain no placeholder passes, and read as an operator manual with clear setup, action, comparison, exclusion, and evidence steps.
- AC-14: Correctness evidence covers interpreter and applicable native/JIT paths, static-off/static-on/dynamic modes, provider disagreement, provider absence, concurrent comparison, instruction extraction/execution, malformed input, bounded logging, shutdown/failure persistence, and every current-host runtime/HAL capability row; unavailable external-host rows remain blocked with linked Todo DB entries and exact resume plans rather than being counted as skipped or complete.
- AC-15: Runtime and compiler changes pass the focused unit/integration/system/performance gates, the direct environment/runtime guards, required compiler/lib/MCP/LSP checks when affected, and the release-bound whole SPipe suite once; verification reports requirement-by-requirement evidence and stops after at most three distinct fix/verify cycles.
- AC-16: Knowledge is refreshed in the same lane: research, requirements, architecture, system-test plan, detail design, agent-task plan, generated/manual specs, coverage/runtime developer guides, and both feature- and layer-expert `skill.md` entries are updated; every discovered but unfixed gap gets a `doc/08_tracking/bug/` record with file:line and unblock condition. Workflow/tooling contracts in `.codex/skills/`, `.agents/skills/`, `.claude/skills/`, `.claude/agents/spipe/`, `.claude/commands/`, and `.gemini/commands/` are updated when affected, or explicitly marked N/A with reasons.
- AC-17: Every `rt(hal)` operation defaults to the mission-critical assurance profile or a stricter profile unless its declaration explicitly names and justifies a lower profile; the compiler/checker reports unclassified legacy runtime operations as warnings during a bounded migration period and, at the selected enforcement milestone, rejects them as errors.
- AC-18: Mission-critical-or-higher runtime/HAL paths perform no dynamic memory allocation after their declared initialization boundary, including instrumentation, provider dispatch/comparison, environment instruction capture/replay, logging, error, timeout, and shutdown paths; fixed-capacity requirements and overflow behavior are explicit and fail closed, and allocation-trace evidence proves the invariant.
- AC-19: Required interface migrations cover operation tags, caller-supplied storage/arenas, capacity/result types, provider capabilities, and fallible overflow/error results across all affected facades and consumers; compatibility shims emit actionable deprecation warnings, have a documented removal milestone, and are removed or promoted to hard errors at that milestone without introducing raw runtime aliases.
