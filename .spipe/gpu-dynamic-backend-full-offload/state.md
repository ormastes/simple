# Feature: GPU Dynamic Backend and Full Offload

## Raw Request
`$sp_dev 1. gpu backend properly made solid interface and dynamic load and no need to change rebuild simple binary. and solid interface. check it works as designed. 2. with vulkan backed simple 2d, web, gui, wm gpu offload check and fix. do profile. in function call and xxxir passing lanes. 3. cuda backend with rendering verify. 4. metal. 5. web,db server optimize gpu offload code working and profile and fix perf and working.`

## Task Type
feature

## Refined Goal
Deliver a stable, versioned, dynamically loadable GPU provider interface below the shared ProcessingIR and DrawIrComposition boundaries, then prove correct and profiled Vulkan, CUDA, and Metal execution for rendering and coarse-grained web/database offload without rebuilding the deployed Simple binary when a compatible provider is installed or replaced.

## Acceptance Criteria
- AC-1: A documented, versioned GPU provider ABI supports discovery, compatibility negotiation, capability enumeration, lifecycle, submission, synchronization, typed errors, device-origin readback, and clean unload; a compatible provider can be installed or replaced and exercised by the unchanged deployed Simple binary, while incompatible or missing providers fail closed to an explicitly reported fallback/unavailable state.
- AC-2: Public callers use one owner facade and shared backend registry; CUDA, Vulkan, and Metal remain implementations below ProcessingIR and DrawIrComposition rather than public API forks, raw backend-field access, per-surface adapters, or new app-local `rt_*` shortcuts.
- AC-3: Executable contract tests prove provider discovery precedence, ABI/version rejection, symbol/capability validation, concurrent session isolation, repeated load/use/unload, provider replacement between processes, bounded failure cleanup, and unchanged-binary loading using hashes of the binary and both provider artifacts.
- AC-4: Vulkan-backed Simple 2D, WebIR-to-DrawIR, GUI widget-tree-to-DrawIR, and canonical WM scene-to-DrawIR routes submit the exact produced composition through Engine2D and prove compile, submit, fence, positive backend handle, device-origin readback, and exact CPU-oracle parity without a private renderer or CPU mirror being labeled GPU work.
- AC-5: Focused profiles measure the same representative frames at function-call, producer-to-DrawIR, DrawIR-to-backend, backend submission, fence, readback, and end-to-end lanes; retained before/after results report workload identity, warmup/sample counts, median/p95, max RSS, bytes/calls crossing each IR boundary, and identify and fix or track every material regression.
- AC-6: CUDA rendering executes representative 2D/GUI/Web/WM Draw IR fixtures with stable device identity, exact readback parity, typed injected-failure isolation, same-process recovery, and retained native profile evidence; source inspection, emission-only evidence, synthetic handles, and CPU mirrors do not pass.
- AC-7: Metal rendering satisfies the same fixtures, failure/recovery contract, readback parity, and profile schema on a prepared native macOS host; until fresh native evidence exists, the criterion remains blocked with an open TODO and resume plan naming prerequisites, exact command, retained artifacts, owner, and final reviewer.
- AC-8: Web-server GPU offload keeps accept, protocol parsing, routing, backpressure, serialization, durability, and invalidation CPU-owned while verified coarse-grained payload work uses the shared ProcessingIR provider; correctness, fallback, bounded queue/resource behavior, and retained throughput/latency/RSS profiles must meet the selected NFRs and canonical native HTTP comparison gates.
- AC-9: DB-server GPU offload proves exact CPU parity and durability semantics for selected coarse-grained RAM-only, SSD-backed, NoSQL/vector, scan/filter/aggregate workloads; profiles separate transfer, kernel, synchronization, commit/invalidation, and end-to-end costs, and GPU execution is selected only where retained measurements beat the CPU path under the selected NFRs.
- AC-10: SSpec scenarios trace every requirement and keep unavailable native host/capability rows visible as blocked/unsupported rather than skipped; generated `doc/06_spec` Markdown reads as an operator manual, contains no placeholder assertions, and no executable `*_spec.spl` exists under `doc/06_spec`.
- AC-11: Knowledge artifacts are current: research, selected requirements/NFRs, architecture, UI/detail design, system-test plan, agent-task plan, feature and layer expert `skill.md` pages, GPU/UI/web/DB developer guides, performance reports, and a bug/TODO with file:line plus unblock condition for every unfixed gap. Evidence-wrapper or workflow changes also update affected SPipe manuals and Codex/Claude/Gemini skill, agent, and command instructions; unreachable capabilities are documented as blockers, not advertised as available.
- AC-12: Final verification passes focused lint, duplicate checks, runtime/env guards, relevant compiler/lib/app checks, native provider/render/offload gates, regression tests, and independent highest-capability review, with no acceptance command repeated after an unchanged PASS and no more than three fix/verify cycles per failing feature row.

## Scope Exclusions
- GPU backends do not own TCP accept, HTTP parsing, DB durability, transaction commit, cache invalidation, WebIR, Draw IR, or platform presentation policy.
- A runtime/compiler rebuild needed to introduce the provider ABI is allowed during implementation; after deployment, compatible provider installation or replacement must not require rebuilding or changing the Simple binary.
- Host-unavailable Metal or CUDA execution, fallback rendering, static source wiring, screenshots alone, and synthetic or CPU-mirror receipts are not feature-completion evidence.
- Engine3D HUD/world rendering remains a separate consumer lane and is not a shortcut for Web, GUI, WM, Draw IR, or Engine2D acceptance.

## Cooperative Review
Broad lane: lower-model sidecars may inspect disjoint dynamic-loader, Vulkan UI, CUDA rendering, Metal native-host, web offload, DB offload, and profiling evidence rows after architecture defines the shared contracts. Merge owner: primary Codex session. Final reviewer and generated-manual quality owner: highest-capability Codex. Shared interfaces: `GpuProviderAbiV1`, `GpuProviderRegistry`, `GpuProviderSession`, `ProcessingIrExecutor`, `DrawIrBackendExecutor`, and `GpuExecutionReceipt`. Manual flow helpers: `step("Load and negotiate a compatible GPU provider")`, `step("Submit the exact shared IR workload")`, `step("Wait for device completion and read back")`, `step("Compare device output with the CPU oracle")`, and `step("Profile the producer IR backend and end-to-end lanes")`. Setup/checker helpers: `scripts/check/check-gpu-provider-dynload-registry.shs`, platform-native provider checkers, the production GUI/web renderer parity checker, and canonical web/DB performance wrappers. Any temporary helper must fail explicitly with `assert(false)` or `fail(...)`.

## Runtime Boundary Decision
- runtime_need: Host dynamic-library open/symbol/close and native GPU device access are below the pure-Simple provider boundary.
- facade_checked: Existing dynlib/SMF facilities, GPU backend registry, ProcessingIR executor, Engine2D backend lane, environment/process facades, and current Vulkan/CUDA/Metal provider checkers.
- chosen_path: Reuse existing facades and add only the smallest owner-level provider facade; change runtime code only where evidence proves host dynamic loading or device access is below the pure-Simple boundary.
- rejected_shortcuts: App-local raw `rt_*` aliases, direct backend pokes, provider-specific public APIs, surface-local renderers, fixture-only success branches, fabricated handles, CPU mirrors presented as device readback, and rebuilding Simple for every compatible provider change.
