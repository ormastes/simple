## What changed

Pure Simple only. No Rust was edited (policy: pure Simple first, C for
hardware, never Rust). No C was edited either — see the blocker below.

`src/lib/nogc_sync_mut/gpu/engine2d/simd_kernels.spl`:

1. **`_scalar_blend_row` was producing wrong pixels.** `val d = dst[idx]` off an
   `any` receiver, then `(d >> 24) & 0xFF`, silently yielded garbage — `da=17`
   read as `138`, `out_a` 145 instead of 32. 210 of 256 sampled (sa,da) pairs
   disagreed with the C kernel. Fixed with `val d = dst[idx] as u32`, the only
   read form that untags correctly. Generic compiler defect filed separately.
2. **`native_pixel_rows_enabled()` now defaults to scalar.** New
   `SIMPLE_2D_SIMD` knob, values `auto|off|sse2|avx2|neon` (+ `rvv`, `on`).
   Allow-list, not deny-list: `rt_env_get` does not reliably return `""` for an
   unset variable, so anything that is not an explicit ISA request means `auto`,
   which means scalar. **WS-A owns the `screen_simd` rc.conf key that surfaces
   this; the two value sets must stay identical — noted in the source comment.**
   The explicit ISA values keep the native bodies reachable and testable.

## D1 — closed as already done

The brief said `nogc_async_mut/gpu/engine2d/` carried a full duplicate
implementation. It does not: `simd_kernels.spl` is 21 lines and
`simd_provider.spl` is 9 lines, both `export use` facades over `nogc_sync_mut`,
and `grep -rn 'fn simd_blend_row' src/lib` returns **exactly one** definition,
in `nogc_sync_mut`. Nothing to delete. The one cosmetic wrinkle —
`gc_async_mut/simd_kernels.spl` reaching `nogc_sync_mut` via the
`nogc_async_mut` facade rather than directly — is a two-hop re-export of the
same single owner, not a divergence, and was left alone rather than churn a file
whose exported symbol subset other modules depend on.

## D2 — partially done; the C half is filed, not merged

Done in Simple: the marshalling pessimisation is off by default and the scalar
path it now routes to is correct.

**Not done: the in-place C span kernels** (`rt_engine2d_simd_blend_span_u32`,
`_blend_const_span_u32`, `_blit_row_u32`, D2.1/D2.2). Exercising a new
`runtime_simd_dispatch.c` symbol requires rebuilding and redeploying
`bin/release/x86_64-unknown-linux-gnu/simple` — the binary other live sessions
resolve. Shipping an unmeasurable kernel by swapping the shared toolchain binary
mid-session was judged the worse trade.

Also discovered while attempting it: the existing in-place
`rt_engine2d_simd_fill_span_u32` is **both slower (13 ms vs <1 ms scalar) and
numerically wrong** — it corrupts the fill colour, `0xFF112233` → `0xFF132233`.
`rt_engine2d_simd_copy_span_u32` is correct under the same probe. Wired up,
measured, reverted, filed. That boxing bug must be fixed before any new span
extern is written, because the same discipline applies to all of them.

Details: `doc/08_tracking/bug/engine2d_simd_span_kernels_slower_and_fill_colour_corrupt_2026-08-06.md`.

## Does SIMD work end-to-end?

Two separable answers:

- **On this x86_64 host, under JIT: the C kernel is reachable and correct.**
  `blend_kernel_probe.spl` shows `rt_engine2d_simd_blend_row_u32` matching the
  reference formula on every probed case. What is broken around it is the
  Simple-side marshalling (§ above) and `fill_span`'s colour boxing.
- **On SimpleOS/QEMU: unknown — nothing was measured.** No SimpleOS run was
  performed in this pass. The host result must not be read as SimpleOS evidence.
