# Native OrderedMap loses key lookup after successful insert (2026-09-27)

Status: PARTIALLY ISOLATED; REQ-PSC-002/-007/-008 still fail.

A focused Windows x86-64 native probe copied `src/lib/nogc_sync_mut/src/collections/ordered_map.spl` byte-for-byte into an isolated two-file source root (matching SHA-256 `742DA7AD8BC76F734E0A0369EAD8768BF9DCC89D65EC4ABF045E880607151E96`). The isolated pure-Simple Stage2 compiler built it with LLVM, `core-c-bootstrap`, and `SIMPLE_NO_STUB_FALLBACK=1`: two modules compiled and linked with zero failures. Running the probe produced:

```
after insert len=1 has=false keys=[<value:0x7>]
panic: nil-valued ordered key missing
```

The failing operation is `OrderedMap<i64,text?>.put(7,nil)` followed by `contains_key(7)`. `put` returned true; the count incremented and the key snapshot contains one item, but lookup returned false. The current `compare_key` guard, generic key comparison lowering, and value materialization need a targeted differential trace. The earlier unguarded comparison path was not run in this probe, so the evidence does not yet isolate the regression to that guard. Do not claim ordered generic map semantics or interpreter/native equivalence until this is fixed and the complete transition/removal spec passes.

Next-turn differential: the native probe showed `7 == 7` and `keys()[0] == 7` true, with neither `<` nor `>` true for the stored key. Replacing only `contains_key` in the isolated copy with its earlier direct comparison made both literal and stored-key lookup true, while `put(7, "seven")` still treated that key as new. This isolates the initial lookup failure to the generic `self.compare_key(K,K)` call path, rather than integer equality itself.

The shared map now compares concrete keys at each call site and passes only boolean comparison results to a non-generic checked-relation helper. An exact-source copy of this revision (SHA-256 `520A875DF7FFEC01F7B5D43015D46D43206CCC030E8819ED0DCD8FD76742F3F7`) compiled and linked with zero failures. There is no marker separating the replacement from the following loop inserts, so the failing call is not yet localized. The helper can detect a real incoherent key, but `i64` should be coherent; inspect the `put` mutable-node path and exact comparison flags before changing policy. This turn used all three probe build cycles.

Next-turn root-cause probe (three build/run cycles, cap reached): an isolated flag print located the false coherence panic at `put(4, ...)` after key `7`: equality, less, and greater were all false. Making the loaded node immutable in the isolated map did not change it; direct concrete `4 < 7` and stored-key `7 > 4` in the caller were true. Disassembly of the generated `OrderedMap.put` object showed generic `K` ordering calls `rt_any_lt` and `rt_any_gt`, while equality calls `rt_native_eq`. An isolated diagnostic edit to `runtime_any_ops.c` printed `ITEM7_ANY_LT raw=4,7 decoded=0,0 float=0,0` immediately before the panic. `rt_any_lt` assumes tagged `any` inputs and calls `rt_value_as_int`; the generic map passes raw `i64` keys, so both small values decode to zero. This is a compiler lowering / runtime representation boundary defect, not an incoherent integer comparator. The instrumented runtime and map reside only in `D:\wk-profile-switchable-item7-20260926`; shared runtime was not changed. Build log: `build/item7-ordered-probe-any-args-build-20260927.log` in that isolated worktree (2 compiled, 0 failed, linked; `RUN_EXIT=1`). Repair the generic comparison lowering to preserve the actual `K` representation; changing `rt_any_lt` to reinterpret all inputs as raw integers would break legitimate tagged `any` callers. Then rerun an exact-source map probe and the required admitted specs. The Stage2 compiler used here is diagnostic only, not a release/test authority.
