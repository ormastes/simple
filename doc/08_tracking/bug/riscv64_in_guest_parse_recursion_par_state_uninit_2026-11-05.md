# riscv64 in-guest parse dies in rt_array_set: parser module init never runs (par_state uninitialized)

- **Status:** OPEN — root cause bounded, fix belongs to a compiler/linker lane
- **Filed:** 2026-11-05 (lane `work/riscv-inguest-recursion-20261105`)
- **Follows:** PR #6983 (35-symbol link port), #6987 (cfg env preseed),
  #6990 (parser-provider enum-equality workaround)

## Symptom

The riscv64 in-guest interpreter kernel boots under OpenSBI v1.4 and,
after the #6990 provider-admit workaround, proceeds into the real parse
of the hello-world source. It then parks:

```
[TRAP] S-mode exception, the guest is parking here
[TRAP]   scause=0x0000000000000005 sepc=0x0000000080200976
[TRAP]   stval=0x0000001100000000 sp=0x0000000082e6a8f0
[TRAP]   _stack_bottom=0x000000008266ac80 stack_guard=intact
```

scause=5 (load access fault) in `rt_array_set` loading the array header
`type` word; the receiver is the garbage tagged handle 0x0000001100000001
and `sp` sits within ~1 KiB of the 8 MiB stack top — hours-scale recursion
or a runaway deep call chain preceded the fault.

## Differential (host vs guest)

The EXACT in-guest chain — `_pp_preprocess_conditionals` →
`parse_and_build_module` → `desugar_module` → `desugar_collections_static`
→ `HirLowering.lower_module` — over the same hello-world source text
terminates on the host in ~4 s, both with ambient env and with the
guest-seeded cfg env (`UNAME=simpleos`, `HOSTTYPE=riscv64`; spec at
`/tmp/rv-boot/host_diff_spec.spl`, verdict 1/1, 8/8 on the provider
specs). The non-termination is therefore a freestanding-guest
divergence, not a frontend algorithm bug. (Note: `simple run` cannot be
used for this differential — its cranelift JIT finalize cannot resolve
`InterpreterBackendImpl_dot_new`; the spec runner's interpreter mode
works.)

## Evidence chain (temporary IA-TRACE instrumentation, reverted)

Instrumented the executed copies of `rt_array_set` / `rt_index_set`
(the ghdl_boot_info_runtime.c copies win the duplicate-symbol lottery;
instrumenting baremetal_runtime_core.inc.c printed nothing — same lesson
as the #6983 allocator lottery). Guest serial, first bad calls:

```
[IA2-TRACE] rt_index_set value=0x0000000000000000 index=0 ra=0x803367fc
[IA2-TRACE] rt_index_set value=0x0000001100000001 index=0 ra=0x80336bb4
[IA-TRACE]  rt_array_set  arr=0x0000001100000001 idx=0 ra=0x80200f14
```

All three return addresses are inside
`compiler__frontend__core__parser__parser_init_with_path`
(+0x2fc, +0x6b4): the `par_state.par_kind_slot[0] = 0` /
`par_text_slot[0] = ""` re-init writes. The `par_state` MODULE GLOBAL
(`compiler__frontend__core__parser__par_state`, WEAK OBJECT at
0x8266a218, inside .bss) is ZERO (first trace) then GARBAGE (second
trace) — its `var par_state: ParserState = parser_state_fresh()`
initializer never ran. Consequences in order: the `== nil` re-init
guards misfire on 0/garbage (NIL is the TAG_SPECIAL word 3, so 0 tests
NOT-nil), the slot writes no-op or store through garbage, and the parse
continues on corrupt module state until the recursion/garbage fault.

Why the initializer never ran, measured on the linked interp kernel
(`build/os/riscv64_interp/interp/kernel.elf`, nonce-agnostic):

- `parser_state_fresh` (0x803340b0) has **zero call sites** in the
  entire image.
- `__simple_call_module_inits` (0x806528cc, generated by
  native_project/linker.rs `generate_init_caller`) contains 156 guarded
  init calls; **none** targets any `__module_init_*` of
  `compiler.frontend.core.parser` (the module's init symbols exist as
  defined text — `__module_init_compiler__frontend__core__parser`
  0x8033fcbc and its `_dynamic` inner 0x8033fc78 — but nothing calls
  them).
- crt0.S zeroes ALL of .bss (`_sbss`..`_ebss`, 8-byte store loop), so
  the zero start is expected; the 0x1100000001 garbage is written later
  by code operating on the zero/never-initialized global.
- .bss is now ~32.5 MB because the ghdl TU's heap is a 32 MiB static
  array (PR #6983); crt0 still covers it fully (bound symbols, not a
  size constant), so zeroing is not the defect.

## Root-cause boundary

`generate_init_caller` scans every linked object's global symbols for
the `__module_init_` prefix with no type filter, so the parser module's
init SHOULD be found. It is not, which means either the parser module's
object was absent from the scan set for this closure, or its global
symbol list missed the init at scan time (`cached_global_symbols`).
That is a compiler/linker emission question (seed-side,
`src/compiler_rust/compiler/src/pipeline/native_project/linker.rs`),
not a runtime-port question — this lane stops here per its scope.

Plausible impact beyond this row: ANY module-global whose initializer
matters and whose module init is similarly missing from the generated
caller will read zero/garbage in every freestanding in-guest image while
working hosted (hosted runs module inits through the runtime's own
path, which is why the host differential terminates). The
host-works/guest-corrupts asymmetry signature is exactly this record.

## Repro

1. `PATH=/usr/lib/llvm-18/bin:$PATH SIMPLE_BIN=<checked-in seed> sh
   scripts/os/build-simpleos-riscv64-interpreter-kernel.shs` (PASS).
2. Wrap `build/os/riscv64_interp/interp/kernel.Image` in OpenSBI v1.4
   `fw_payload` (pinned a2b255b8), boot `-machine virt -cpu rv64 -smp 1
   -m 512M -bios fw_payload.bin -serial file:log` (`-bios` only).
3. Transcript: `[interp] lowering hello-world source through the real
   frontend` then the scause=5 trap above.

## Next lane

Instrument `generate_init_caller`'s scan (or dump `_init_all.c` for the
interp closure) to answer: was
`__module_init_compiler__frontend__core__parser` present in
`cached_global_symbols` for the parser module's object? Fix whichever
side dropped it, then re-run this repro — the acceptance is the guest
advancing past `parser_init_with_path` into real tokenization (or the
next honestly-named blocker).

## 2026-11-05 — CORRECTION (lane `work/riscv-inguest-module-init-20261105`): "init never runs" is DISPROVEN

The root-cause boundary above ("the parser module's init is missing from
the generated caller") is WRONG. Measured on the current tip
(`d5bfa447382`):

- `generate_init_caller` DOES run for the freestanding link
  (`linker.rs:2847`, `link_objects_freestanding`) and finds **150**
  inits (temporary INIT-TRACE instrumentation, reverted) — including
  `__module_init_compiler__frontend__core__parser`.
- The generated `_init_all.o` carries both a GOT_HI20 and a CALL_PLT
  relocation against the parser init; the final kernel's GOT slot for
  it is populated (`0x80663638 = 0x8033f9d4`), and `boot_entry.c:95`
  calls `__simple_call_module_inits()` before `spl_start`.
- The init body is correct: `__module_init_..._parser_dynamic`
  (`0x8033f998`) calls `parser_state_fresh` and stores the result
  through a pool entry whose value is exactly `&par_state`
  (`0x82669218`) — verified from the linked bytes.
- DECISIVE EXPERIMENT (temporary, reverted): boot_entry was patched to
  call `__module_init_compiler__frontend__core__parser()` DIRECTLY
  before `spl_start`. The parse faulted IDENTICALLY afterwards
  (scause=5 in rt_array_set, garbage tagged receiver
  `0x0000001900000000`, `/tmp/rv-boot/interp-serial-diag.log`). So the
  initializer RUNS and STORES CORRECTLY, and `par_state` is STILL
  zero/garbage when `parser_init_with_path` reads it. The defect is
  DOWNSTREAM of the init: the global is clobbered between boot and the
  parse, or the accessor and initializer disagree on the global's
  representation/layout in a way static analysis of this lane could not
  pin down (the accessor's field offsets 0x58..0x70 for the token slots
  are consistent with the 15-field `ParserState`; both functions live in
  the SAME object `mod_116.o`, so the duplicate-object lottery does not
  apply to them; `.bss`/`.stack` do NOT overlap in this build — a
  4-byte gap, correcting the transient suspicion raised mid-lane).

Next-lane recommendation: attach QEMU's gdb stub and set a hardware
watchpoint on `&par_state` (`0x82669218`) across boot→parse to catch
the clobbering write red-handed; alternatively instrument the seed to
trace the store/load addresses of `par_state` at runtime. The lane's
hard rule (6 cycles) stopped the investigation here; all temporary
instrumentation (INIT-TRACE in `linker.rs`, direct-call diagnostic in
`boot_entry.c`) was reverted, and the kernel build re-verified PASS on
the clean tree.

## 2026-11-05 — WATCHPOINT LANE (PR #7001+1): the clobber caught, fix landed, residual defect filed

No riscv64-capable gdb exists on this host (host gdb 15.1 is aarch64-only;
/tmp/riscv-tools has no gdb), so the hardware-watchpoint route was out.
Used the software-sentinel fallback instead.

### Method

Temporary probe (all reverted) in the runtime TU: `rv64_par_state_note()`
snapshots the `par_state` global + its first 20 words at the top of
spl_start; `rv64_par_state_check(tag)` at entry-phase boundaries;
`rv64_par_state_dump(tag)` from the trap handler.

### Findings

1. **The global is never clobbered.** At the fault: `cur == exp ==
   0x80676fc1` — `par_state` holds the same valid tagged pointer the
   init stored. The #7001 "clobbered between boot and parse" hypothesis
   is HALF right: the global survives; its POINTEE gets overlaid.
2. **The struct's pointee IS written over by allocations.** Trap-time
   field dump vs the boot snapshot: fields 0-3 legitimately re-created
   by `parser_init_with_path`'s reset; **fields 6, 10, 14 all hold
   0x0000001100000001** (and field 8 = 0xffffffffffffff00, field 18 =
   0x000000a000000002) — array-header-shaped data written over the
   struct by a bump allocator.
3. **The writer: the ghdl TU's 32 MiB static `g_heap` array from PR
   #6983.** Measured in the same ELF: `g_heap` at 0x80665000 (the very
   start of .bss, spanning 32 MiB) and `par_state`'s struct at
   0x80676fc0 = g_heap + 0x11fc0 — INSIDE the array's span. `.bss` is
   for zeroed globals; making it also the allocator arena meant every
   code-side allocation bump-overlaid live module globals. The 64 KiB
   original array never reached the globals; the 32 MiB enlargement
   did. Root cause of the "clobber" = the #6983 fix itself.

### Fix (landed)

- `ghdl_boot_info_runtime.c`: the 32 MiB static .bss array is DELETED.
  That TU now owns the THIRD disjoint slice of the linker-reserved
  `.heap` (RV_HEAP_BASE/RV_HEAP_SIZE), exactly like the other two
  runtime TUs — never .bss.
- `baremetal_stubs.c` / `baremetal_runtime_core.inc.c`: halves ->
  thirds (first / second slice) so all three duplicate allocators own
  disjoint regions regardless of the --allow-multiple-definition
  lottery.
- `linker_riscv_common.ld`: `.heap` 64M -> 192M so each third keeps
  the 64M per-owner capacity the halves used to carry; fits in the
  510M RAM region (NOLOAD, no flat-Image bytes).

### Result

The boot recovered everything the overlay had been corrupting serial-
early (banners, prints — the mid-fix 21MiB-thirds boot panicked with an
empty message pre-banner because init allocations exceeded a third;
the 192M heap fixed that). The parse now reaches the same rt_array_set
load fault — but the garbage word is byte-identical
(0x0000001100000001) across completely different memory layouts, i.e.
it is DETERMINISTIC DATA, not an overlay artifact: an (i32,i32)-shaped
pair (1, 17) sitting in every `[...]`-literal-initialized ParserState
slot field. That is a seed codegen value-representation defect in the
array-literal construction (fields 6/10/14 = the three `[]`/`[0]`
slot owners), a different class from this record's clobber — filed here
as the new tail: next lane owns the constructor lowering; the runtime
side of THIS record is closed (no clobber remains: the sentinel proves
the global and, post-fix, no overlay writer exists inside .bss).

## 2026-11-05 — REPRO LANE (PR #7011+1): the deterministic word is a struct-literal codegen defect, minimally reproduced and bisected

The byte-identical 0x0000001100000001 is NOT an overlay and NOT an
array-literal defect. Reproduced in isolation, in-guest, and bisected:

- Plain locals `var a: [i64] = [0]` (also `[text] = [""]`, four of
  them): **correct in-guest** (`PROBE OK array literals`).
- Struct literal with ONE field `[i64]`: **OK**. TWO fields
  (`[i64]`,`[text]`): **OK**. FOUR array fields (`ProbeFourA(a:[0],
  b:[0], c:[0], d:[0])`): **FAULTS** on the first field read —
  scause=5, stval = `0x0000003300000008` (earlier program revision:
  `0x0000001100000008`; the high half tracks an ALLOCATION SIZE, 0x11
  = 17 then, 0x33 = 51 now; low half is type 8 = HEAP_STRING_BUILDER).
  So a struct-literal FIELD receives a pointer to / the header of an
  unrelated string-builder allocation once the literal has ~4 fields.
- Host `simple run` (JIT/interpreter) passes the identical struct-literal
  repro (`STRUCT LITERAL OK`) — the defect is **AOT cranelift only**.
  Both the checked-in seed and a seed rebuilt from this branch
  (release tip `13a060d644e`) reproduce it: genuine release-tip bug,
  not seed staleness.
- `simple compile` SMF output is target-independent (only addresses
  differ between riscv64 and x64 SMF), so the corruption is born in
  the AOT backend's struct-init value plumbing
  (`codegen/instr/closures_structs.rs::compile_struct_init` stores
  field_values at MIR-provided offsets; with ~4 array-typed field
  values — likely spilled — the value/field pairing breaks). The
  likely trigger boundary (2 fields OK, 4 broken) points at a
  register-pressure / spill path in the emitter, not at the offset
  table itself.

Repro for the next (seed) lane — in-guest probe used by this lane
(temporary kernel-entry probe, reverted):

```spl
struct ProbeFourA:
    a: [i64]
    b: [i64]
    c: [i64]
    d: [i64]

fn probe() -> bool:
    var q: ProbeFourA = ProbeFourA(a: [0], b: [0], c: [0], d: [0])
    # first read of q.a faults: q.a == garbage {size,type} word
```

In-guest iteration loop: add the probe to
`examples/09_embedded/simple_os/arch/riscv64/interpreter_hello_entry.spl`,
`sh scripts/os/build-simpleos-riscv64-interpreter-kernel.shs` (~80 s),
wrap the interp kernel.Image in the pinned OpenSBI v1.4 fw_payload and
boot `-machine virt -cpu rv64 -smp 1 -m 512M -bios fw_payload.bin
-serial file:log` (~3.5 min). Host AOT x86_64 builds of even a trivial
entry exceeded 5 min on this host (SCV admission closure), so in-guest
is the practical loop. Cycles: 6 of 6 used; stopping per the rule with
the repro, bisect, and candidate area recorded.

## 2026-11-05 — SEED-CODEGEN LANE (PR #7019+1): the 4-field struct-literal defect was the STALE CHECKED-IN SEED; the ParserState fault is a different, open defect

Fast host harness built first (this host has no riscv gdb and host AOT
x64 builds of any entry exceed 5 min, so): `LocalExecutionManager::cranelift()`
JIT tests (temporarily un-gated from x86_64 for this run, reverted) plus
`SIMPLE_DUMP_CLIF=probe` AOT object compiles.

Findings:

1. **The 4-field struct-literal corruption is NOT in release.** The
   identical 4-field repro PASSES on the host cranelift JIT and its AOT
   CLIF is exactly right (four independent box/new/push chains; stores
   pair v3/v8/v13/v18 with offsets 0/8/16/24 of the rt_alloc'd block).
   Re-tested IN-GUEST with a seed rebuilt from THIS branch (release tip
   `9bf94d89a91`): `PROBE OK four-field struct literal`. All prior
   in-guest repros that showed the fault (including #7019's) were built
   with the CHECKED-IN bootstrap seed — which was built from the
   diverged main tree and lacks release's struct-init fixes. Root
   cause of THAT defect: stale seed, fixed in release already.
   OPERATIONAL LESSON, load-bearing for every future in-guest lane:
   `SIMPLE_BIN` for `build-simpleos-riscv64-interpreter-kernel.shs`
   MUST be a seed built from the same release commit; the checked-in
   `src/compiler_rust/target/bootstrap/simple` is main-built and
   silently miscompiles struct literals.

2. **The ParserState parse fault PERSISTS with the release seed**
   (same scause=5 rt_array_set trap, stval=0x0000001100000000, after
   the now-passing 4-field probe). So par_state's construction differs
   from the plain 4-field case in a way that still breaks: it is a
   15-FIELD struct returned BY VALUE from `parser_state_fresh` into a
   MODULE-INIT (`__module_init_..._dynamic`) and stored into a module
   GLOBAL. The prime remaining suspects, in order: (a) large-struct
   RETURN ABI (sret) in the AOT cranelift path for rv64 — a 120-byte
   struct vs the 32-byte probe; (b) the module-init/global store path.
   Next lane's first probe: a >=16-field struct returned from a plain
   function, read back field-by-field, in-guest (entry probe), with a
   release-built seed; then the same inside a module-init.

No production code changed in this lane (temp host tests, the x86_64
test gate, and the in-guest entry probe all reverted). Cycles: 5 of 6.

## 2026-11-05 — SRET-PROBE LANE (PR #7020+1): NOT sret — the ghdl bump cursor is REWOUND mid-init; field-level evidence

All in-guest evidence built with a RELEASE-BUILT seed
(`/tmp/riscvH-target/release/simple` from `4d041e6cbf6`), fresh native
cache (`compiled=614 reused=0`) — no stale artifacts.

Boundary probes (in-guest, entry probes, reverted):
- 16-field struct of `[i64]` returned BY VALUE from a plain fn, zeros:
  **OK** (f0/f7/f15 read back). Distinct per-field values [i]..[i]:
  **OK** — no value/field swap. So large-struct return lowering is
  CORRECT; the #7020 sret hypothesis is dead.
- The SAME shape as a MODULE-LEVEL `var g: Probe16 = make()` (the
  par_state pattern): **faults** reading f11 — BUT the global itself
  holds a valid, stable tagged heap pointer (0x88e8a2d1 at spl_start,
  unchanged after 32 more allocations).

Field-level dump of the struct at spl_start (16 words): f0, f1, f6, f7,
f15 are make's valid array pointers; **f2-f5 are a complete
RuntimeString** `{size=33, type=HEAP_STRING}, len=16,
data="0123456789abcdef"` (the hex-literal const of
mcdc_exclusion_evidence.spl / duplicate_check/incremental.spl), and
**f8-f14 are another RuntimeString** `{size=54, type=HEAP_STRING},
len=37, data="simple.instrumentation.cutover/atomic"` (the
ASPECT_CUTOVER_ATOMIC_EXT_V1 const of
src/lib/common/plugin/aspect_params.spl). Two independent modules'
string-const allocations landed INSIDE the struct block at offsets
+16 and +64, with 16-byte alignment spacing exactly matching two
sequential `rv_alloc`s from a cursor positioned at struct+16.

The core TU's own `g_heap_off` at spl_start is 0xdf00 and STABLE
across further allocation — the core cursor never served the struct
and was not poisoned. The struct was served from the ghdl third (heap
offset 0x80142d0). Since a single bump cursor cannot allocate inside
its own earlier block, the ghdl cursor must have been REWOUND from
just past the struct (0x88e8a350) to struct+16 (0x88e8a2e0) AFTER the
entry module's init ran and BEFORE the aspect/hex string-const inits
ran, then bumped forward again (subsequent allocations — including
PROBE-A/B's 32 arrays — continue past the struct, which is why the
global value and f0/f1/f6/f7/f15 stay stable).

The rewind writer is UNBOUND within this lane's budget: it stores an
offset ≈ struct_base+16 into the ghdl copy of `g_heap_off` between
two module inits inside `__simple_call_module_inits`. Both this lane
and the pre-#7011 laneE kernels show the identical mechanism (there:
0x1100000001 = {size=17, type=1} string headers), so it is
seed-independent and cache-independent.

Next lane's first experiment (one in-guest boot): bisect the init
table — disable the aspect_params init (or the hex-const module's
init) in `__simple_call_module_inits` and check whether the overlay
strings disappear from the struct; then walk backwards to find which
init's store rewinds the ghdl `g_heap_off` (a hardware-watchpoint
equivalent: POISON g_heap_off with a sentinel after the entry module's
init and dump it at spl_start; the init that flips it is the writer).
Candidate mechanism to check first: a string-const global init
(`emit_module_init`'s init_strings path) whose `global_ids` lookup
resolved to the ghdl `g_heap_off` address (weak-symbol resolution
across the runtime TUs), storing a heap pointer into the cursor.

No production code changed (all probes reverted). Cycles: 5 of 6.
