# `base64url_decode` silently accepts out-of-alphabet input (RFC 4648 §3.3) and diverges from the differential oracle

- **Status:** OPEN
- **Date:** 2026-08-18
- **Area:** `src/lib/common/base_encoding/base64.spl` (`base64url_decode`)
- **Related migration:** C-MIG-0023 (base64url). This is a **correctness** gap;
  the separate perf gap is tracked in
  `doc/08_tracking/bug/codegen_lane_still_slow_base64url_utf8_time_utils_2026-08-18.md`.
- **Severity:** Medium-High — `base64url_decode` is on the JWT path, where the
  input is an **untrusted** caller-supplied token.
- **Found by:** extending the existing differential spec
  `test/01_unit/lib/common/base_encoding/base64/base64url_crosslang_spec.spl`
  with out-of-alphabet cases. Every pre-existing example in that spec fed the
  decoders well-formed base64url, so this input class had no coverage at all.

## Which oracle actually executes — read this before quoting the numbers

Under `bin/simple test` (tree-walk interpreter), `rt_base64url_decode` does
**not** reach `src/runtime/runtime.c`. It is dispatched to the interpreter's
extern table (`interpreter_extern/crypto.rs`, registered at
`interpreter_extern/mod.rs:665-666`), which uses the Rust `base64` crate's
`URL_SAFE_NO_PAD` engine. That distinction is documented in the spec's own
header and is repeated here because it changes what the divergence means: the
measurement below is **pure-Simple vs. the interpreter's Rust shim**, not
pure-Simple vs. the C source.

The C source's own invalid-symbol behaviour (`b64url_decode_char` returns `-1`,
caller clamps `if (a < 0) a = 0;`, i.e. an invalid character decodes as if it
were `A`) is visible by reading `src/runtime/runtime.c:2578-2600`, but it was
**not** the code path exercised by this measurement, and is not asserted here.

## Measured (2026-08-18, interpreter lane, Rust seed `bin/simple`)

Probe calling both providers on identical input:

| input | pure-Simple | oracle (Rust shim) |
|---|---|---|
| `!!!!` | `""` | empty |
| `%%` | `""` | empty |
| `....` | `""` | empty |
| `ab*d` | 2 chars — invalid symbol dropped, remainder decoded | differs |
| `a b c` | 2 chars — same | differs |
| `a+b/c` | 3 chars | differs |

Neither side signals an error for any of these. RFC 4648 §3.3 requires
rejection.

## Why this matters

`src/lib/nogc_sync_mut/web_framework/auth_middleware.spl` decodes JWT header
and payload segments from an attacker-supplied token. A decoder that never
reports "this was not valid base64url" means a malformed segment is
indistinguishable from a well-formed one at the call site: the caller gets a
shorter-but-successful string and parses it as JSON. Any downstream logic
assuming "it decoded, therefore it was well-formed" is unsound.

Note this is also a **cross-provider** gap, not just a strictness preference:
the two implementations disagree on exactly these inputs, so changing which
provider is linked changes observable behaviour for malformed tokens.

Caveat on blast radius: `auth_middleware.spl:385` currently defines its **own
local** `fn base64url_decode` rather than importing the std one, so the std
function is not necessarily the code running on that path today. Consolidating
those duplicate decoders onto one audited implementation is part of the fix,
not a reason to downgrade it.

## Scope — what is NOT broken

The well-formed path is solid and already covered by the same spec: the RFC
4648 §5 vectors (unpadded forms of the §10 test vectors), a 100-case
shared-logic differential, exact boundary lengths, and a >4KB input all pass
with the two sides byte-identical. The defect is confined to the
invalid-symbol path.

Corpus limits, stated so they are not over-read: the shared 100-case generator
emits only the byte values `0x30`, `0x61`, `0x7e`, `0x7f`, and the `0xC3 0xA9`
UTF-8 pair. `0x00`, `0x80`, and `0xFF` are **not** generated by it; a
bytes-typed corpus would be needed for those and has not been written.

## Suggested fix

`base64url_decode` must distinguish "decoded" from "not valid base64url":

1. Return `Result<text, DecodeError>` and handle the error on the JWT path —
   correct, but an API change with existing callers; or
2. add a strict sibling (`base64url_decode_strict`) that rejects, and move the
   security-sensitive callers (`auth_middleware.spl`, `password_reset.spl`,
   including their local duplicates) onto it.

Either way, do **not** adopt the C source's clamp-to-zero behaviour as the
target — silently substituting `A` for arbitrary attacker bytes is the more
dangerous of the two leniencies.
