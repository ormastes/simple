# Native test daemon startup faults at indirect callback

**Status:** Source mitigation drafted; pure-Simple rebuild and runtime check open.

The installed release-path `simple test test/01_unit/app/build/scheduler/distributed_attempt_spec.spl --mode=interpreter` exits 139 immediately after `[setup] cover-check` and before executing any scenario. Existing macOS crash reports `simple-2026-09-24-181842.ips` and `simple-2026-09-25-040722.ips` both show `EXC_BAD_ACCESS` at null address, with `src__lib__nogc_sync_mut__daemon_sdk__client__daemon_ensure_running` directly below the faulting frame. The test runner calls `test_daemon_ensure_responsive` after cover-check. This strongly suggests the captured `fn() -> bool` startup callback in `app.test_daemon.client` is lowered as a null indirect target in that installed native binary; the crash reports alone do not prove the precise codegen fault.

`src/app/test_daemon/client.spl` no longer passes a captured startup callback through the generic SDK. Static review found the old launcher cannot start the protocol this client expects: the native compiler CLI rejects `test-daemon start`, while the alternate lightweight daemon uses a different lock and request format. Retrying it would delay direct test execution without making the generic daemon responsive. The client now pings only an already-running compatible daemon; otherwise the test runner takes its existing direct-execution fallback. It also no longer kills a PID read from a potentially stale lock after a failed ping. The generic daemon SDK remains unchanged for other clients.

**Qualification:** Build and deploy a current pure-Simple binary, run one focused passing SSpec and one failing SSpec, and record whether each used the direct fallback or an existing generic daemon. A direct-route pass can establish the crash mitigation and failure propagation, not daemon startup. Qualifying daemon execution separately requires a compatible generic launcher and a routing receipt. Compare startup/P95 and RSS on the same fixture. Do not label the existing exit-139 run a pass. The repository's three-cycle bootstrap/test verification cap was already reached in this session, so no unchanged retry was made here.
