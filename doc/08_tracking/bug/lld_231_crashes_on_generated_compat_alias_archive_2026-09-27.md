# ld.lld 23.1.0 crashes (0xC0000005) parsing our generated one-member compatibility-alias archive

Filed: 2026-09-27
Host: DESKTOP-5A4V03J (Windows 11, `x86_64-pc-windows-gnu`, LLVM/clang 23.1.0
from `C:\llvm\install`)
Severity: Blocking the Stage 2 link on the clang+LLD lane.

## Symptom

The Stage 2 link now runs through LLD (clang-only / no-GNU-ld policy) and LLD
dies with an access violation instead of producing a diagnostic:

```
Generating 1 compatibility aliases for resolved symbols...
Compatibility alias preview: select
Link command: "C:\llvm\install\bin\clang" "--target=x86_64-w64-windows-gnu" "-fuse-ld=lld" ...
Build failed: link failed: PLEASE submit a bug report to https://github.com/llvm/llvm-project/issues/
Exception Code: 0xC0000005
 #0 checkAndSetWeakAlias(lld::coff::SymbolTable&, lld::coff::InputFile*, lld::coff::Symbol*, lld::coff::Symbol*, bool)
 #1 lld::coff::ObjFile::initializeSymbols()
 #2 lld::coff::ObjFile::parse()
 #3 lld::coff::LinkerDriver::addFile(lld::coff::InputFile*)
 #4 lld::coff::LinkerDriver::addObjectFile(...)
 #5 lld::coff::LinkerDriver::addArchiveBuffer(...)
 #6 lld::coff::LinkerDriver::addBuffer(...)
clang: error: linker command failed due to signal
```

## What is being linked at that moment

Exactly one compatibility alias, for `select`, generated by
`stubs.rs` (~line 1312) as a STRONG global with a jump:

```asm
.section .text$compat_alias_0,"xr"
.globl select
select:
  jmp <resolved target>
```

packaged as a one-member archive — deliberately, as the comment there records:
"The one-member-per-alias archive is the COFF liveness boundary."

The crash is therefore in LLD's *weak*-alias handling while parsing an archive
member that we emit as a strong definition, for a symbol (`select`) that
ws2_32 also provides. The interaction between our definition and the import
library's is the thing to characterise.

## Why it surfaced only now

This lane previously linked with mingw-winlibs GNU `ld`, which never got far
enough to parse this archive: it failed earlier because it cannot consume the
`\?\` verbatim cache-root paths at all. With `-fuse-ld=lld` (clang-only
policy) the link proceeds to symbol resolution and reaches this crash.

## Root cause FOUND (2026-09-27, supersedes the "not yet established" list below)

The trigger is ours, not LLVM's. `resolve_defined_suffix_alias`
(`stubs.rs`) ends in a fallback that only runs for a symbol containing NO
`__` -- i.e. a plain C identifier -- and matches it against any defined Simple
symbol ending in `__<name>`. An undefined reference to winsock `select`
therefore resolved to `lib__nogc_async_mut__async__combinators__select`, and
the generator emitted a global `select` for it.

That fallback captures EVERY libc/winsock name a Simple module happens to
share: `read`, `write`, `open`, `connect`, `send`, and so on. The LLD crash is
the lucky outcome; a successful link would have routed every socket `select()`
call into an async combinator, silently.

Fixed by `PLATFORM_C_SYMBOLS` in `stubs.rs`: those names return `None` from the
resolver, leaving the reference for the platform's import library, which is the
correct provider. Pinned by
`platform_c_symbols_are_never_aliased_to_simple_functions` in `tests.rs`, which
asserts both halves -- `select` must not resolve, and a genuine bare Simple
symbol (`trim`) still must.

**The LLD-side defect remains real and unreported:** a linker must diagnose a
duplicate/conflicting symbol, never segfault. A reduced case is still worth
building for upstream, but it is no longer on this repo's critical path.

## Originally not established (kept for history)

- Whether a minimal reproducer is just `select` + ws2_32, or needs the full
  archive set. No reduced case has been built yet.
- Whether LLVM 20 (the documented fallback pin) crashes identically. Testing
  that is cheap and is the first thing to try, because it separates "LLD
  regression in 23.1.0" from "our object is malformed".
- Whether passing the alias object DIRECTLY instead of wrapped in a
  one-member archive avoids it. The crash arrives via `addArchiveBuffer`, so
  this is a plausible workaround, but it trades away the liveness boundary the
  archive exists to provide and must not be taken without understanding that
  cost.

A crash is never an acceptable end state for a linker regardless of the input,
so an upstream report is warranted once a reduced case exists.
