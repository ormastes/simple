# No-await async lowering called a missing constructor

The source9737/producer776ce2 Phase4 HIR run reported unresolved `Future` in `compiler/90.tools/fix/main.spl`. This module declares async main without the explicit `std.async.future.Future` import required by the existing HIR contract. The selected library's real immediate-value constructor is `Future.from_value`; frontend desugaring instead emitted nonexistent `Future.ready`.

The bounded repair adds that logical library import to the CLI and uses `from_value` for functions without suspension points. It does not hardwire a GC/synchronization family or replace async syntax with synchronous signatures. The existing no-await path eagerly evaluates one body value and returns a ready future.

For nongeneric functions, the body executes in a generated private synchronous function with the original parameters, return type and contract. The public wrapper calls that function exactly once with all parameters explicitly supplied, then constructs `Future.from_value`. Thus defaults are not reevaluated, contracts over the original result T execute in their original scope, and polling does not reevaluate the body. Names are allocated deterministically against authored module declarations, explicit imported bindings, earlier helpers and wrapper parameter names. Generated declarations are included in the function headers and ordered function inventory. Fully hygienic resolution against wildcard-imported names is not established by this syntax-only allocator.

A bare block argument lets an explicit `return` escape the transformed outer function with a raw value instead of `Future<T>`. An immediately invoked lambda is also unsafe in the current compiler: type inference retains the enclosing `current_return_type`, while MIR `lower_iife_call` / `lower_inline_lambda_with_locals` lowers the body into the caller and saves only local bindings. That independent IIFE return-scope limitation remains recorded here; this repair uses an actual function boundary rather than assuming a lambda fixes it.

Seven executable behavior cases cover parameters/local values, early returns, tail values, inferred unit, evaluate-once polling, synchronous controls and the generic tail-only path. Five parser/lowering cases additionally inspect real positional CallArg metadata, lower the explicit-return helper through HIR, retain default parameters and generic tail scope, test deterministic collision handling and preserve unit/synchronous declarations. Runtime execution of all twelve cases remains PENDING; the behavior fixture uses module state and must execute serially within its owning process. The next producer must contain the frontend change; old compiler receipts cannot qualify it.

Generic functions retain their original block scope with the real `from_value` constructor. A bare AST Call loses explicit type arguments, and monomorphization infers only from value arguments; a generated helper would lose parameters used only in the body. No invented type-argument transport is introduced here. Generic explicit returns therefore remain unsupported and unqualified: `test/fixtures/compiler/async/generic_early_return_pending.spl` retains the failing reproducer, with a real typed Future and expected value. It is not counted as a passing case. Generic tail-only behavior is an authored regression awaiting execution, not an observed PASS.

The broader await state-machine path still emits `Future.from_generator`, which this selected legacy library does not implement. This repair does not manufacture that method, turn pending work into a ready value, or claim general async/await completion. Implicit Future-import discovery and lazy no-await execution are also outside this existing explicit-import/eager-ready contract.
