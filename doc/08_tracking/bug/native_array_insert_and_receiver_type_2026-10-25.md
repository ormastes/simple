# Native Array.insert and array receiver typing

Status: OPEN — insert compiler-pass fix verified; native qualification and whole-closure receiver transport remain pending.

The original macro registry, macro source collector and reference projector used `out.insert(index, item)`. PR4668 temporarily replaced those calls with push and explicit reverse shifts. That workaround does not implement the missing native builtin. The original native MIR method dispatch has push/append/merge/write_span handlers but no Array.insert handler; no retained rt_array_insert primitive exists.

The proposed compiler fix emits insert using the existing retained rt_array_len/push/get/set ABI. It admits only a producer-proven runtime array after custom method/UFCS recovery. It evaluates arguments once, saturates negative signed indices to zero, leaves indices greater than length unchanged, guards all writes on successful push, snapshots the appended tagged value once and shifts raw tagged slots backwards. The method returns its receiver and uses existing mutating receiver writeback. This follows the reference interpreter contract in interpreter_method/collections.rs474 and interpreter_helpers/args.rs56. Resource-bearing source operands move into push only once.

Unsigned 64-bit indices remain explicitly rejected until unsigned bounds semantics are qualified. No claim that every integer index is supported. Raw fixed/GPU storage without runtime handle provenance remains rejected.

The separate native `.len()` failure at core_codegen.spl1084:46 reports receiver_has_type=false and receiver_type_kind=-1 on a typed local initialized by `_sffi_tuple_get<[MirOperand]>`. PR4726's typed helper is temporary. Existing declared-type and unresolved length recovery already exist; the warning alone does not establish which owner/metadata branch failed. A compiler-pass regression now retains this SFFI projection shape, but no speculative length fallback was added.
