# SVM-G signed i32 right shift selects the logical opcode

Severity: P2. Status: fixing; executable verification pending.

The isolated `work/pure-svmg-signed-shift-d88f` repair passes checked left/target
signedness into both opcode selectors and selects the existing SAR opcode for
signed i32. The unit spec and separate ordinary driver execute generated
bytecode through the real reference VM, covering signed counts 0/1/31/33,
positive and unsigned controls, compound assignment and float rejection.
Those tests are written and source-reviewed; execution remains UNRUN.

At source `81d2ba024e818edb13a47322c28e0c0b0f22af94`, both `binop_opcode` and `assign_opcode` in `src/compiler/70.backend/svmg_lowering.spl` map right shift to `OP_SHR`. Their callers distinguish float operands but do not use the checked integer signedness.

The actual reference VM implements `OP_SHR` by shifting the unsigned word bits and implements `OP_SAR` by shifting the signed value. Consequently a checked signed i32 `-8 >> 1` or equivalent `>>=` selects bytecode that computes `2147483644`, while arithmetic shifting requires `-4`. This is a source prediction, not a new executed result.

The primary Pure-Simple LLVM emitter's right-shift branch in `_MirToLlvm/core_codegen.spl` selects `emit_lshr` only for an unsigned left operand and `emit_ashr` otherwise. This supplies the existing signed-shift contract; no mixed-type promotion choice is needed for two checked i32 values.

Repair both binary and compound shift selection using the checked left integer kind. Preserve u32 logical shifting, including `0x80000000u32 >> 1 == 1073741824u32`, the existing count-mask contract, and unsupported float shifts. Execute generated bytecode through the real reference VM for signed negative, positive and unsigned controls before closing the bug.

The separate D4 integer-print/float-compound candidate remains immutable during its diagnostic. No shift repair or claim was applied as part of that candidate.
