# macOS bootstrap fails Cocoa runtime ownership before Stage 2

**Status:** OPEN, 2026-09-25. Reproduced in isolated detached checkout `/var/folders/94/j3lc49d93bx148gqls5kx5d40000gn/T/simple-stage2-verify.XXXXXX.bnq5e4anZs` at `HEAD` `664c80efda5` with the distributed-build feature's source/test drafts copied in. The command used `SIMPLE_BOOTSTRAP_RUST_LLVM=0 sh scripts/bootstrap/bootstrap-from-scratch.sh --full-bootstrap --stop-after-stage2 --produce-stage3-receipt=self-host-convergence-check --output=build/bootstrap-dist-check --no-mcp --jobs=2 --progress` on macOS `aarch64-apple-darwin`.

The Rust seed and native libraries built, then `scripts/check/check-macos-cocoa-runtime-owner.shs` failed before Stage 2. Its contract requires exactly one `rt_cocoa_*` export in `libsimple_runtime.dylib` and none in `libsimple_native_all.a`. The retained `runtime.symbols` has no `_rt_cocoa_window_new`; `archive.symbols` has **two** such definitions, and the same mismatch repeats for all twelve checked Cocoa symbols. The retained log is `build/bootstrap-dist-check/logs/aarch64-apple-darwin/macos-cocoa-owner.log` in the isolated checkout; verdict is `ABORTED: stage=rust-rust-compiler-backfill-build`.

Source review shows both `src/runtime/hosted/cocoa.rs` (`#[no_mangle]` exports, starting near line 549) and `src/runtime/hosted_cocoa.c` (real Apple exports, near line 244) define the same C names. `src/compiler_rust/runtime/build.rs` near line 500 explicitly links the Objective-C file into the Rust runtime build, including the native archive. That contradicts the owner check. A fix must establish one provider in the dynamic runtime and none in native-all, with the check passing on a clean admitted bootstrap. Do not weaken the owner check or substitute the Rust seed as the production runtime.

Astra's independent review also found that `src/compiler_rust/native_all/Cargo.toml` directly links `spl_hosted_runtime`; its default Cocoa stubs still export these names even without `cocoa-real`. The Cocoa C source is absent from the runtime export scanner's C source list and lacks the retention used for `runtime_sffi_c`, consistent with the missing dylib exports. Simply toggling `cocoa-real` or dropping one C compilation branch would leave the ownership contract incomplete.

After the user allowed a small C layer, a narrow owner fix was drafted in `src/compiler_rust/runtime/build.rs`, `src/runtime/hosted/cocoa.rs`, and an explanatory native-all manifest comment, with `src/runtime/test/cocoa_dynload_owner_selfcheck.c` restoring the focused check. A standalone Mach-O probe found twelve dylib exports, zero Cocoa static exports, and passed offscreen layer create/fill/read/free. A third isolated bootstrap cycle then progressed to the Rust dylib link and failed on `_objc_msgSendClass$...` Objective-C symbols from `hosted_cocoa.o`; the retained diagnostic is `build/bootstrap-dist-check/logs/aarch64-apple-darwin/rust-seed-build.log` in the isolated checkout. The bootstrap uses Homebrew Clang 23, while the first focused probe used Apple Clang 17. Clang 23 emits class-selector stubs unsupported by the installed Apple linker. A follow-up focused probe using the exact Homebrew compiler and Rust cdylib linker passed after adding `-fno-objc-msgsend-class-selector-stubs` only to the Objective-C compilation: twelve unique exports, no class-stub references, and real offscreen pixel operations. The aggregate bootstrap has not been rerun because the session's three-cycle limit is reached. No full bootstrap PASS or Stage 2 binary exists.
