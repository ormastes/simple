# `use app.*` is unresolvable when a `src/lib/**` file is the entry file (E1034)

- **Filed:** 2026-08-17 (lane IMPORTFIX). **Partially retracted 2026-08-18 (lane SMFMASK2).**
- **Status:** OPEN — filed, not fixed. The import path is CORRECT; the defect is in module-root selection.
- **Toolchain:** all probes ran on `bin/simple`, which is the **Rust seed**. Findings are
  attributed to the seed; no pure-Simple binary was exercised.
- **Severity:** P2 — no production lane is currently broken by it, but it makes every
  `src/lib/**` file that imports `app.*` unusable as a run/probe target.
- **Retracted:** the original "stale `.smf` artifacts mask it" claim. It was correlation
  only and fails a direct causation test — see the RETRACTED section below.

## Verbatim error

```
$ bin/simple run src/lib/nogc_sync_mut/test_runner/main.spl
error: SIMPLE_JIT_STRICT: HIR lowering error: cannot resolve import `app.test_daemon.session_types`:
Module resolution error: SemanticWithContext(ContextualError {
  message: "cannot resolve import: module path segment `app` not found",
  context: ErrorContext { span: None, secondary_spans: [], file: None, source: None,
    code: Some("E1034"),
    notes: ["ensure the module file or __init__.spl exists"],
    help: ["check that the module exists at \"src/lib/nogc_sync_mut/test_runner/app\""] } })
[in src/lib/nogc_sync_mut/test_runner/main.spl]: unresolved import; refusing to fall back to the interpreter
```

rc=1 (captured on the line after the command, not through a pipe).

## The import target is NOT missing

`src/app/test_daemon/session_types.spl` exists (11550 bytes) alongside
`src/app/test_daemon/__init__.spl`. Both run clean as entry files themselves
(`bin/simple run` on each: rc=0, zero `cannot resolve import`). Nothing was moved,
renamed, or deleted. Do not "fix" this by rewriting the import path.

## Root cause: the module root is the ENTRY FILE'S DIRECTORY

The `help` line gives it away — the resolver looked for the `app` root at
`src/lib/nogc_sync_mut/test_runner/app`, i.e. relative to the entry file, not at the
repo `src/`. When the same lib module is loaded as a *library* from an app entry under
`src/app/**`, the root is `src/` and `app.test_daemon.session_types` resolves fine. That
is why this has sat unnoticed: the import only breaks on the run-as-entry path.

## RETRACTED 2026-08-18 (lane SMFMASK2): the stale-`.smf` explanation was WRONG

The original filing claimed `use app.*` from a `src/lib/**` entry succeeds **iff** a
prebuilt `.smf` exists for the target package. That was correlation-only and it does not
survive a causation test. **The claim is retracted.** What follows is what was measured.

### Four probes re-verified (rc captured on its own line, never through a pipe)

| entry file | rc | `cannot resolve import` |
|---|---|---|
| `src/lib/nogc_sync_mut/lsp/main.spl` | 0 | none |
| `src/lib/nogc_sync_mut/lsp/transport.spl` | 1 | `` `app.protocol.transport` `` / segment `app` not found |
| `src/lib/nogc_sync_mut/test_runner/main.spl` | 1 | `` `app.test_daemon.session_types` `` |
| `src/lib/nogc_sync_mut/test_runner/test_classification.spl` | 1 | `` `app.test_daemon.session_types` `` |

The rc pattern reproduces exactly. Only the *explanation* was wrong.

### Causation test: removing the artifacts changes nothing

`src/app/lsp` is a **symlink** to `../lib/nogc_sync_mut/lsp`. So the "present
`src/app/lsp/__init__.smf`" in the original table is not an app-side build product at
all — it is `src/lib/nogc_sync_mut/lsp/__init__.smf`, a file inside the entry file's own
directory, seen through the symlink. (This is also why a plain `find src/app -name
'*.smf'` misses it: `find` does not follow symlinks.)

All five `.smf` files in that directory were renamed in place to `*.smf.bak`, and the
succeeding probe re-run:

```
$ ls src/lib/nogc_sync_mut/lsp/*.smf   -> No such file or directory
$ bin/simple run src/lib/nogc_sync_mut/lsp/main.spl
rc=0            # still succeeds
cannot resolve import: 0 occurrences
```

**Removing the artifact did not break the succeeding case.** The `.smf` files are not
causal. All five were restored and verified byte-identical by `md5sum -c` (5/5 `OK`,
no `.bak` left over, none regenerated by the run).

The original correlation table was also factually off on its own terms:
`src/app/protocol/framing.smf` **does** exist inside the package whose column read
"absent".

### The decisive probe: the SAME FILE passes or fails by how its path is SPELLED

`src/app/lsp/transport.spl` and `src/lib/nogc_sync_mut/lsp/transport.spl` are the same
bytes on disk (same inode, via the symlink above):

```
$ bin/simple run src/lib/nogc_sync_mut/lsp/transport.spl
rc=1   error: cannot resolve import `app.protocol.transport` ... segment `app` not found
$ bin/simple run src/app/lsp/transport.spl
rc=1   error: semantic: Cannot resolve module: sys       # UNRELATED later-stage failure
```

Spelled under `src/app/**` the `app.protocol.transport` import resolves and the run gets
all the way to a different, unrelated error; spelled under `src/lib/**` it dies at
E1034. Same file, same imports, same artifacts on disk — only the entry path differs.
**This confirms the root cause above (module root derived from the entry file's
location) and refutes the artifact explanation.**

Why `lsp/main.spl` is the odd one out: it imports only `app.lsp.*`, and `app.lsp` is the
symlink back to its own directory, so those imports are satisfiable from the entry's own
directory. `transport.spl`, in that same directory, imports `app.protocol.*` and fails.
Same entry directory, opposite outcomes — no module-root story that keys on the entry
directory alone distinguishes them, and no artifact story does either. (**UNPROVEN:** the
exact lookup rule that lets `app.lsp.*` through has not been read out of the resolver
source; it is inferred from the probes.)

### `.smf` files are gitignored

`.gitignore:6` is `*.smf`; `git ls-files 'src/**/*.smf'` returns 0. A fresh clone has
none. Since the artifacts are **not** causal, this is *not* a works-on-my-machine trap
for this bug — a fresh clone reproduces the same four rc values. It does mean any future
claim that keys on `.smf` presence must be tested on a clean tree first.

## Is `main.spl` live or dead? — DEAD

`src/lib/nogc_sync_mut/test_runner/main.spl` has no real consumer.

- The live runner is `src/app/test_runner_new/test_runner_main.spl`. It imports ~12
  `std.test_runner.*` modules by explicit brace list and **never** imports
  `std.test_runner.main`.
- Every importer of `test_runner.main` in the tree is a self-referential compatibility
  facade that only re-exports it onward and is itself imported by nobody:
  - `src/lib/nogc_async_mut/test_runner/main.spl:1` → `export use std.nogc_sync_mut.test_runner.main.*`
  - `src/lib/gc_async_mut/test_runner/main.spl:1` → `export use std.nogc_async_mut.test_runner.main.*`
  - `src/lib/gc_sync_mut/test_runner/main.spl:3` → `export use std.gc_async_mut.test_runner.main.*`
- `src/lib/nogc_sync_mut/test_runner/__init__.spl:89` has `export main`, so a barrel
  wildcard would pull it — but no consumer uses a wildcard barrel import; all observed
  call sites are explicit `.{...}` lists.

So `bin/simple test` does not reach it. Deleting it (per the implement-or-delete rule)
would require also removing the three facade files above, which are outside this lane's
ownership — hence filed rather than deleted.

## Fix directions (not attempted here)

1. **Real fix:** make the module root for a `src/lib/**` entry file be the workspace
   `src/` (walk up to the source root / `simple.sdn`) rather than the entry's own
   directory, so `app.` and `std.` resolve identically whether a lib module is the entry
   or an import.
2. **Separately:** decide the fate of `main.spl` + its three facades — they are dead
   weight and one of them is unrunnable.

## Reproduce

```bash
bin/simple run src/lib/nogc_sync_mut/test_runner/main.spl   # rc=1, E1034
bin/simple run src/app/test_daemon/session_types.spl        # rc=0 — target is fine
bin/simple run src/lib/nogc_sync_mut/lsp/transport.spl      # rc=1, same shape, different pkg
bin/simple run src/app/test_runner_new/test_runner_main.spl # rc=0, 0 unresolved — CONTROL
```

The last line is the control that pins the root cause: the live runner under `src/app/**`
pulls in the same `std.test_runner.*` modules and resolves everything (rc=0, zero
`cannot resolve import`). Only the entry file's location differs.

Do not use `bin/simple check` (>600s). Do not bisect with `head -N` — cutting mid-block
manufactures its own error so every prefix appears broken.
