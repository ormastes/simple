# Darwin tree RSS misses charged footprint — OPEN

Full05 exposed a memory-safety gap: its 17 GiB sampled tree-RSS guard did not bound a worker whose sampled charged footprint reached about 40.1 GiB (lifetime peak 41.4 GiB), while a nearby same-PID RSS observation was 5306320 KiB. This is one process observation, not a calibrated simultaneous whole-tree peak. Compressed/swapped accounting can grow VM disk consumption while RSS stays below its threshold. Neither RSS nor charged footprint is a universal substitute or strict numeric bound for the other.

The opt-in source repair adds `--max-phys-footprint-kib` and the canonical parent-policy environment `SIMPLE_BOOTSTRAP_PROCESS_TREE_PHYS_FOOTPRINT_CAP_KIB`. It reads current `ri_phys_footprint` inside the existing PID-start identity bracket, sums the same selected live members as RSS, and enforces the supplement during running and TERM-drain observations. The reported tree peak is the maximum sampled current sum; the single-process peak is the maximum observed current member value. No per-process lifetime peaks are summed. Samples are sequential within a bounded window, not atomic or kernel hard limits.

Default/zero keeps the legacy observer request and RSS policy unchanged. Positive footprint requests require Darwin; live query/protocol failure refuses workload execution rather than falling back to RSS or zero. Footprint breach has a separate receipt status, while RSS fields retain their meaning and limit. The canonical facade explicitly forwards the requested option, so mismatched older watchdogs reject it. An environment variable alone cannot upgrade an old frozen guard.
