# Windows writer-held sealed cache capability (2026-10-18)

Status: additive native C subset implemented and qualified; entry-object publication remains BLOCKED until driver owners pass the new capabilities. No producer rebuild or active cache changes.

The existing receipt/copy barrier asks ordinary READ capabilities to flush. Windows FlushFileBuffers requires a writable OS handle. Reopening an immutable path writable would violate its authority. The new publish-retained-v2 operation reuses the existing secure TEMP writer through actual flush, read-only sealing, handle-based no-replace rename and actual post-rename flush. It then returns a distinct sealed token retaining the exact original handle. The old TEMP token is invalid. Sealed capabilities permit bounded stable read/size, real flush and close, but cannot write or republish. Existing publish-v1 behavior and READ fsync unsupported result stay unchanged. Unix C and Rust also implement v2 using the original descriptor, explicit sealed TEMP state and checked post-publication file/root flushes. Before granting a sealed token they compare the original descriptor identity with the no-follow destination dev/ino/regular-file observation; mismatch consumes TEMP and leaves an unadmitted destination. This is not an atomic conditional rename, a directory lock or a race-immunity claim. The existing Rust Windows cohort remains explicitly unsupported.
