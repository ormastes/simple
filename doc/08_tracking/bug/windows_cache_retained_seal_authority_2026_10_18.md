# Windows writer-held sealed cache capability (2026-10-18)

Status: additive native C subset implemented and qualified; entry-object publication remains BLOCKED until driver owners pass the new capabilities. No producer rebuild or active cache changes.

The existing receipt/copy barrier asks ordinary READ capabilities to flush. Windows FlushFileBuffers requires a writable OS handle. Reopening an immutable path writable would violate its authority. The new publish-retained-v2 operation reuses the existing secure TEMP writer through actual flush, read-only sealing, handle-based no-replace rename and actual post-rename flush. It then returns a distinct sealed token retaining the exact original handle. The old TEMP token is invalid. Sealed capabilities permit bounded stable read/size, real flush and close, but cannot write or republish. Existing publish-v1 behavior and READ fsync unsupported result stay unchanged. Non-Windows v2 is explicitly unsupported.

Zero means destination exists; no replacement occurs. On failure, close any remaining TEMP token. An error after rename may have consumed that token and left an unadmitted immutable file; it never grants a successful sealed capability. Copies alias a runtime token, and the first close invalidates all copies.
