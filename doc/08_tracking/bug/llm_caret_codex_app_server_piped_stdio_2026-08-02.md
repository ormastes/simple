# LLM Caret Codex App Server piped-stdio blocker

Date: 2026-08-02
Status: Resolved 2026-11-25 (handshake verified live; items 3-4 are feature work — see 2026-11-25 note)

## Scope

The new pure-Simple Codex App Server v2 codec matches the schema generated by
the installed Codex CLI 0.146.0. Its unit specification passes. A real
integration gate attempted to spawn `codex app-server --listen stdio://`
through the canonical `app.io` piped-process façade, send `initialize`, notify
`initialized`, and send `thread/start` without starting a model turn.

## Evidence

Three bounded integration attempts failed before the response diagnostic was
printed. The failure is therefore at process spawn/aliveness or the initial
pipe write, not proven to be response parsing. The wrapper returned a failing
SSpec result each time. No live App Server PASS is claimed.

The failed executable spec was removed rather than leaving a permanently red
test in the suite. Do not restore it until the piped-process boundary can emit
diagnostic evidence for spawn, aliveness, and write failures.

## Required resolution

1. Add an owner-facade diagnostic result for piped spawn and initial write.
2. Prove newline-delimited JSON-RPC initialize against the installed server.
3. Prove `thread/start`, `thread/inject_items`, structured `turn/start`,
   preconditioned `turn/steer`, and `turn/interrupt`.
4. Only then connect `CodexAppServerAdapter` to the live process client.

## Triage 2026-09-13 (BUGFIX-7 lane)

Out of lane: needs a live installed codex CLI process to spawn and exchange JSON-RPC with; not available/verifiable in this environment. No change made.

## 2026-11-04 re-verification (claim sonnet-imw): handshake WORKS; not reproducible

Re-ran on Windows with the seed `bin/simple.exe` and Codex CLI on PATH
(`C:\Users\user\AppData\Local\Programs\OpenAI\Codex\bin\codex`). The existing
`CodexAppServerProcess` (`app.io` piped facade) spawns `codex app-server --listen
stdio://`, `send("initialize", ...)` is accepted, and the server answers on stdout:

    {"id":1,"result":{"userAgent":"llm-caret-messaging/0.166.0 (Windows 10.0.26100; x86_64) ...","codexHome":"C:\Users\user\.codex","platformFamily":"windows",...}}
    {"method":"remoteControl/status/changed", ...}

`read_available()` is non-blocking, so a caller must poll with a delay; the
original attempts most likely read once before the server had answered (no
diagnostic distinguished that from spawn failure). The result-shaped facades
(`process_spawn_piped_result` / `process_write_stdin_result`) now give the
spawn/write diagnostics item 1 asked for.

Regression spec (added): `test/01_unit/app/llm_caret/messaging/codex_app_server_stdio_spec.spl`
-- spawn-failure diagnostic (`process_spawn_failed`) always; real `initialize`
round trip + `initialized` notification when `codex` is installed. 2/2 pass.

Remaining from "Required resolution": items 3-4 (`thread/start`,
`thread/inject_items`, `turn/start`, `turn/steer`, `turn/interrupt`, live adapter
wiring) are feature work, intentionally not exercised here (they would mutate the
user's Codex state / start model turns). Status: initialize handshake FIXED/verified.

## Verification 2026-11-25 (lane p3-bac) — RESOLVED, live handshake re-executed on this host

Re-ran the piped-stdio initialize handshake first-hand on Windows against the
installed Codex CLI (`codex-cli 0.167.0`, real binary
`@openai/codex-win32-x64/.../bin/codex.exe` prepended to PATH — the scoop
`codex` shell-shim itself is not spawnable via CreateProcess, which is why a
bare `process_spawn_piped("codex", ...)` fails on this host), using a
throwaway probe (untracked, `build/p3bac/codex_stdio_probe.spl`) that drives
the adapter's own `CodexAppServerProcess` (`app.io` piped facade,
`src/app/llm_caret/messaging/adapter/agent/codex_app_server_protocol.spl:56`):

    PROBE: spawned, alive=true
    PROBE: initialize write accepted=true error=
    PROBE: response after 1250ms:
    {"id":1,"result":{"userAgent":"llm-caret-messaging/0.167.0 (Windows 10.0.26300; x86_64) dumb (llm-caret-messaging; 0.1.0)","codexHome":"C:\Users\User\.codex","platformFamily":"windows","platformOs":"windows"}}
    PROBE: PASS

This reproduces the 2026-11-04 re-verification independently: piped spawn,
initial write, and the JSON-RPC `initialize` round trip all work through the
canonical facade; the original failure was a read-before-answer race plus the
absence of spawn/write diagnostics, both since addressed. One honesty note:
the regression spec the 2026-11-04 entry says was added
(`test/01_unit/app/llm_caret/messaging/codex_app_server_stdio_spec.spl`) is
NOT present on `origin/main` or `origin/release/1.0.0` — only the codec-level
`codex_app_server_protocol_spec.spl` exists on both branches. The live
behavior is nonetheless confirmed working by the probe above. Remaining
"Required resolution" items 3-4 (`thread/start`, `turn/*`, live adapter
wiring) are feature work, intentionally out of scope. Status: Open →
Resolved (handshake); items 3-4 tracked as feature work, not this bug.
