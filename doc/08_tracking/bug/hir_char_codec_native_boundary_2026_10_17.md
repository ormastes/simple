`enum construction 'compiler.hir.hir_definitions.HirExprKind.CharLit': payload type mismatch at 0`

Compiling that generated module can encounter this CharLit branch even when a symbol-patch fixture never constructs a character expression. The reader factory/cursor probe has passed separately; it does not qualify this consumer or eliminate its generated-codec dependency. ## Generator and exact version differences

Canonical owner src/compiler/20.hir/hir_definitions.spl:571 declares `CharLit(value: char)` at both reviewed revisions. src/app/compiler_schema/codec_gen.spl:242 nevertheless classifies both text and char as prim_text. The generator's encoder/decoder paths therefore handle a char as a text field instead of giving it a distinct scalar contract.

At C1, generated/hir_codec.spl:2060-2062 calls hc_enc_enum_text for CharLit. Decoder 2817-2827 reads raw text, represents the wire-nil marker separately, constructs a prototype using an empty/unescaped text value, and uses hc_restore_enum_nil to restore the absent slot. That text prototype violates the declared char payload before nil restoration can help.

At 99b871a, generated/hir_codec.spl:2032-2034 calls w.put_text(b_value) directly. Decoder2775-2778 reads a line and passes either nil or flat_pool_unescape(raw) to CharLit. It still provides text instead of char, but these generated bytes and nil handling are NOT identical to C1. A future fix must name its exact base and preserve that version's intentional wire policy or explicitly migrate it; neither historical behavior may be silently assumed equivalent.

## Native source oracle and missing qualified boundary

The following actual source contracts rule out pointer reinterpretation or weakening payload admission:

- src/compiler/70.backend/backend/_MirToLlvm/core_codegen.spl:2637 and class_def.spl:254 map MirTypeKind.Char to LLVM i32, a scalar rather than a text pointer.
- src/compiler/50.mir/_MirLoweringExpr/enum_constructor_payload.spl:262 admits Char payloads only when the actual MIR type is Char. This check must remain strict.
- src/runtime/runtime_native.c:4790 rt_char_from_code converts a Unicode scalar number into a managed UTF-8 STRING. Its return ABI is not a native char constructor. Invalid scalar numbers produce empty text.
- src/lib/common/encoding/utf8.spl char_from_codepoint returns text. Integer chr/to_char lowering in method_calls_literals.spl:2816 explicitly records HirTypeKind.Str. Neither is a drop-in CharLit payload.
- expr_dispatch.spl:1493 correctly renders an already-existing native Char via rt_char_from_code. This is a real scalar-to-text encoder boundary, not evidence for the reverse conversion.
- expr_dispatch.spl:3421 onward supports generic cast lowering, but no existing qualified typed numeric-to-char source-call oracle was established by this investigation. This report does not assert that the language lacks every possible cast, nor propose an unverified cast as a fix.
- expr_dispatch.spl:6297 explicitly rejects CharLit expressions with E-MIR-EXPR-CharLit. That separate source limitation prevents assuming a character-literal prototype can trivially bootstrap the codec repair.

Value.as_char only extracts an existing char payload. A genuine codepoint-to-native-char boundary remains to be identified or implemented and independently qualified; falsely declaring a string-returning runtime function as returning char would not establish it.

## Required repair and acceptance evidence

The generator needs a distinct prim_char classification and correctly typed encoder/decoder emission. Generated output must be regenerated from the authoritative schema owner, not patched only at one occurrence. Encoding must preserve the selected version's canonical scalar text/escape wire grammar while never passing raw char bits as a text pointer. Decoding must validate exactly one Unicode scalar and construct an actual typed char through a proven boundary. Strict Char payload admission, owned decoder scopes, resource ledgers and artifact seals remain unchanged.

Existing utf8_decode_one validates ranges but substitutes U+FFFD for malformed sequences. Merely accepting its returned value would conflate invalid bytes with a genuine replacement character. Exact byte consumption and canonical UTF-8 re-encoding equality, or an equivalent strict validated primitive, are necessary. This report does not invent a byte helper or an admitted conversion API.

Required controls before declaring repair complete:

1. Real generated CharLit encode/decode/encode preserves actual native Char owner, payload value and canonical wire bytes for ASCII, non-ASCII BMP, supplementary-plane/non-BMP scalar, genuine U+FFFD, NUL, newline and backslash.
2. Empty and multiple-scalar text, malformed/truncated/overlong UTF-8, surrogate encodings and values above U+10FFFF fail with the actual decoder denial policy. Invalid input must not become a successful replacement character.
3. Nil-wire handling is tested against the EXACT chosen version: C1 marker/prototype/slot restoration and99's marker/nullable path are recorded separately. Valid U+0000 and U+0003 must not be confused with absent/tagged-nil carriers. Any intentional wire migration requires an explicit format/version decision and compatibility evidence.
4. Actual character construction and rendering are natively qualified, with no text-pointer cast, fake enum slot, dummy return or relaxed Char admission.
5. The genuine symbol-projection/patch consumer compiles the changed generated module and executes real table roundtrip plus malformed/predecessor/cohort denials under actual transient ownership. A passing factory-only probe is insufficient.
6. Broader compiler/lib/MCP/LSP and BDD gates remain UNRUN until executed against an admitted implementation. No claim is made that this single repair resolves every broader reader diagnostic.

No production code, compiler runtime, generated output or executable tests are changed by this report. No Rust seed execution, new reader attempt or exhausted-feature budget reset was used to establish these findings.

## 2026-10-18: paired generator and generated-code repair prepared

Work starts from `6e8d05eee4817157e34b64ce6a091f3a4bf665c4`, retaining
the C1-style typed prototype and schema-owned enum nil restoration protocol.
The generator now classifies `char` separately from `text`. Encoding uses the
existing `char_from_codepoint` UTF-8 owner and text escaping; decoding validates
one scalar by exact decode/encode byte equality before constructing a `char`.
The nil marker remains `\\N`; a literal backslash followed by N is two scalars
and fails character decoding. Invalid text poisons the actual FlatPoolReader.
Nil, U+0000 and U+0003 remain separate cases in the native regression fixture.

The pure scalar validation workaround has its own canonical report:
`native_text_scalar_validation_failure_2026_10_18.md`. Its second native probe
passed; the complete generated codec fixture is prepared and UNRUN. The
fixture imports actual generated functions rather than reproducing the codec.
Generator parity and BDD regressions are prepared and UNRUN. No complete
compiler link, deployment, reader consumer qualification, or broader
compiler/lib/MCP/LSP verification is claimed. Database reconciliation remains
pending a qualified database tool.

Review tightened the direct scalar helper: `char` lowers to LLVM i32, so it
does not return an unproven nil carrier. A nil marker passed directly to that
helper poisons the reader with `char_nil_requires_enum_slot`. The generated
enum decoder handles the marker before calling the helper and preserves nil
using the existing schema-owned restoration boundary. Tests cover both paths.
