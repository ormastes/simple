# Frozen Phase 2 compiler: a copied `SymbolId` loop key misses its own dict, and Stage 3 faults

- **Date:** 2026-11-18
- **Status:** OPEN as a frozen-compiler bridge. Root cause is fixed in source
  at tip (`5c28b2506cd`, 2026-11-17). The source-level workaround here stays
  until the Phase 2 compiler is rebuilt from a tree that contains that commit.
- **Severity:** P1 (access violation in the Stage 3 compiler; blocks the lane)
- **Lane:** Windows, Stage 3 built by the frozen Phase 2 compiler, Cranelift.
- **Workaround tag:** `# @workaround bug=phase2_struct_dict_key_copy_identity_hash_2026-11-18`
- **Related:** `dict_struct_key_identity_keyed_copied_key_misses_2026-09-13.md`
  (the language-level defect, still open),
  `native_dict_tuple_key_struct_element_address_compared_2026-11-16.md`
  (tuple keys, not covered by the tip fix).

## Symptom

Access violation (0xC0000005) in
`compiler.semantics.join_point_model.forward_join_points_for_module_v1`
(`src/compiler/35.semantics/join_point_model.spl`), in this loop:

```
for dk_22 in module.functions.keys():
    val func: HirFunction = module.functions[dk_22]
    val target = join_point_forward_target(func.body)   # null read
```

`module.functions` is `Dict<SymbolId, HirFunction>`; `SymbolId` is a one-field
value struct.

## Evidence

Host-local observations, one Windows machine, gdb attached to the Stage 3
compiler (probe files under `C:\dev\p3diag\avprobe\`, not in the repo):

- element 0 of the `keys()` array was the block at `0x45d3e281`;
- the key passed to the lookup was a different block, `0x45d3e871`;
- both 8-byte blocks held the value 0 (the same `SymbolId`);
- `rt_dict_get` returned nil and the next field read faulted.

So the generated code copied the loop variable into a fresh 8-byte block
before the lookup, and the runtime did not treat the copy as the same key.

Not measured: which commit the frozen Phase 2 compiler was built from. The
evidence (a headerless struct block passed verbatim as the key) matches a
compiler without `5c28b2506cd`; that it predates the commit is inferred, not
checked.

## Root cause

Two facts combine.

1. **For-in binds a private copy of a struct element.**
   `src/compiler/50.mir/mir_lowering_stmts.spl:5663-5669` calls
   `maybe_copy_struct_value(loop_var, fesn, true)` (defined at `:899`) for
   every struct-typed loop element, because structs are value types (Bug
   #177). This is still true in current source.
2. **The C runtime keys a struct block by address.**
   `src/runtime/runtime_native.c:13835` `rt_core_dict_hash` ends in
   `rt_core_dict_mix((uint64_t)k)` for anything that is not a string, boxed
   integer, float or registered array. `rt_core_dict_key_eq` (`:13867`)
   defers to `rt_native_eq` (`:5820`), which returns 0 at `:5842` unless both
   sides are a registered array or enum.

### What current source does about it

`5c28b2506cd` fixed this at the dict KEY site, not in the runtime and not in
the copy. `box_dict_key_v1`
(`src/compiler/50.mir/_MirLoweringExpr/expr_dispatch.spl:2873`) calls
`canonical_struct_dict_key_v1` (`:2494`), which replaces a single-field
i64/u64 struct key by its field's boxed integer. Any other struct key is
refused at compile time with `E-MIR-STRUCT-DICT-KEY`. A compiler built from
current source therefore still copies the loop variable, but the copy and the
original produce the same key word. Spec:
`test/01_unit/compiler/mir/struct_keyed_dict_key_lowering_spec.spl`; native
oracle: `test/fixtures/native_struct_keyed_dict/main.spl`.

The Stage 3 compiler in this lane is generated by the frozen Phase 2 compiler,
so it gets the old key lowering whatever the source tree says.

### Do the runtime implementations agree?

| implementation | struct key hash | struct key equality |
|---|---|---|
| C, `src/runtime/runtime_native.c:13835`, `:13867`, `:5842` | address | address |
| Simple twin, `src/runtime/simple_core/core_array.spl:430` `dict_find` | none (linear scan) | `rt_native_eq`, `core_string.spl:1431-1531`: string, boxed integer, enum and array arms, then `return 0` |
| Rust seed runtime, `src/compiler_rust/runtime/src/value/dict.rs:230`, `:243` | `value_hash` (content) | `rt_value_eq` (content) |

The C runtime and its Simple twin agree: both are identity-keyed for a struct
block. The Rust seed runtime is content-keyed. That is why the seed
interpreter never shows this failure and a natively built compiler does. It is
a real divergence between the seed lane and the native lanes, already
recorded in `dict_struct_key_identity_keyed_copied_key_misses_2026-09-13.md`.

**Proposal (not done in this change):** make the divergence impossible rather
than route around it per call site. Either (a) keep `5c28b2506cd`'s approach
and extend the compile-time value encoding to the key shapes it still refuses
or misses (multi-field structs, structs inside tuple keys), so no struct block
ever reaches the runtime as a key; or (b) give registered value-struct blocks
a content hash and a field-wise `rt_native_eq` arm in `runtime_native.c` and
`simple_core` together, which needs a struct registry the headerless
`rt_alloc` block does not have today. (a) is cheaper and already half built.
Runtime hashing is deliberately untouched here.

Only `join_point_model.spl` was observed faulting. The other 25 are the same
shape by reading. `abi_interface.spl` guards each lookup with `== nil` and
`continue`, so there the same miss would not fault: it would silently drop
every public declaration from the ABI interface.

Open, and worth a look before trusting the "same shape" claim: the three
`30.types` loops dereference the looked-up function with no guard and run
before semantics, yet the measured fault was in `join_point_model.spl`. Either
type inference did not run on that path (the fault was in a MIR shard
worker), or the copy is not emitted at every site. Not investigated.

Not audited: struct-keyed lookups whose loop variable is not named `dk_<N>`,
and the field-read and struct-return copy shapes the 2026-09-13 record lists.

## Fix

The 23 loops in `20.hir` and `35.semantics` now bind the key array once and
index with its element directly, the idiom already used in
`50.mir/_MirLowering/module_lowering.spl` (`composite_struct_keys`):

```
# @workaround bug=phase2_struct_dict_key_copy_identity_hash_2026-11-18
val dk_22_keys: [SymbolId] = module.functions.keys()
for dk_22_i in 0..dk_22_keys.len():
    val func: HirFunction = module.functions[dk_22_keys[dk_22_i]]
```

No typed struct local sits between `keys()` and the lookup (four files gain an
explicit `SymbolId` import for the array annotation). Iteration order
and the visited set are unchanged.

Spec: `test/01_unit/compiler/semantics/join_point_module_visits_all_functions_spec.spl`.
It pins that every function of a four-function module is visited. It runs in
the interpreter and cannot reproduce the native failure.

## Verification status

- Removal condition: Phase 2 compiler rebuilt from a tree containing
