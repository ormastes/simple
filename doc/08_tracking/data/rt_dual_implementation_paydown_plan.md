# `rt_*` dual-implementation: census, coverage and paydown plan

**Measured 2026-09-01** against `origin/main` at `c0cae452481`, with a seed built
from that tree. Data: `doc/08_tracking/data/rt_dual_implementation_census.tsv`,
generated by `scripts/check/rt-dual-implementation-census.shs`.

## The directive

Every `rt_*` runtime primitive should have a C implementation, a Simple
implementation, an alias binding the two so call sites reach one name, and
intensive tests dual-running them against each other. The related standing rule
is that no NEW `rt_*` may be added in C or Rust: a Rust-only primitive silently
diverges the C lane, because nothing compares them.

## Where the tree actually is

| class | count | share |
|---|---|---|
| defined in **both** C and Rust | 609 | 23.5% |
| **C-only** | 932 | 35.9% |
| **Rust-only** | 1053 | 40.6% |
| **total distinct `rt_*`** | **2594** | |

Dual-run coverage: **24 of 2594 symbols (0.93%)**, across **23 harness pairs**
— up from 16 pairs before this change.

**The 1053 Rust-only symbols are the most severe violation.** They have no C
lane at all, so there is nothing for the C runtime to be checked against, and a
Rust-side behavioural change cannot be detected by any existing gate.

### Two measurement traps, both real

1. **`pub fn rt_*` without `#[no_mangle]` is mangled.** A plain `nm | grep rt_`
   returns 1989 symbols; `nm -C` returns 2010. A census that skipped demangling
   would silently collapse the Rust lane to its `extern "C"` subset.
2. **The link artifact is not single-lane.** `simple-runtime`'s `build.rs`
   compiles the C runtime and bundles those objects *into*
   `libsimple_runtime.rlib` and `.a` — 23 C objects alongside 256 Rust codegen
   units. `nm` over the whole archive reports the **union** of the lanes, which
   classifies every C symbol as also-Rust and collapses the C-only class to
   nearly zero. This is the same failure CLAUDE.md records for
   `check-runtime-api-regression-push.shs`. The census therefore unpacks the
   archive and reads only `*.rcgu.o` members for the Rust lane.

### The census supersedes the hand-written inventory

`doc/08_tracking/c_migration/c_migration_inventory.sdn` states that
`rt_text_to_upper_ascii` has no C counterpart ("returns zero hits"). It now has
two — `src/runtime/runtime_native.c:4084` and
`src/runtime/runtime_simd_case.c:377`. The note is stale. Prefer the
machine-generated census over prose fields in that file.

## What the ratchet freezes

`scripts/check/check-rt-dual-implementation-ratchet.shs` freezes **2489**
single-lane symbols (1020 C-only, 1469 Rust-only) in
`scripts/check/rt_dual_implementation_baseline.txt` and fails any push that adds
a new one or leaves a stale entry.

```
PASS — 2489 symbol(s) checked against 2489 baselined, 0 new, 0 stale
```

Injecting one `pub fn rt_probe()` into the Rust runtime gives exit 1 naming it.

**The ratchet's counts (1020/1469) are larger than the census's (932/1053), and
that gap is stated rather than hidden.** They are different instruments. The
census is authoritative — it reads DEFINED symbols out of real link artifacts,
so a `#[cfg]`-gated or dead definition that never reaches the archive is
correctly absent. The ratchet cannot use `nm`: a per-push gate that needs a
built artifact would ERROR on every clean checkout or, far worse, quietly fail
open, so it reads committed content with the text patterns
`check-runtime-api-regression-push.shs` already relies on. Text extraction
over-counts by roughly 9% on the C lane and 40% on the Rust lane, mostly
`#[cfg]`-gated definitions. For a ratchet — which only ever compares a tree
against itself — over-counting is harmless; under-counting would not be.

## Harness: before and after

`src/lib/common/spec/dual_run.spl` had exactly three functions and two
comparators (`dual_check_f64`, `dual_check_text`). Added:

- `dual_check_i64` — integer pairs previously had to be routed through
  `dual_check_text` by formatting both sides, which made the check depend on
  `i64_to_text`, itself a pair under test. That circularity is now gone.
- `dual_check_bool`, `dual_check_bytes` (length-first, then element-wise, so a
  shared-prefix agreement is correctly a divergence).
- `dual_summarize` / `DualSummary` — table-driven aggregation, so a pair is a
  `use`, an `extern fn` and one list rather than a bespoke while/assert block.

Pairs went **16 → 23**. Gate verdict:
`PASS — 23 pair(s) checked, 23 case(s), 0 divergent` (exit 0); spec 20/20.

## A real defect the new coverage found immediately

The very first math pair added flagged `std.math.special.sqrt_f64` as **not
correctly rounded**, which IEEE-754 requires. It disagrees with `rt_math_sqrt`
by one ULP on `2.0` and `2.5`, and on `1.0e-10` misses the exactly-representable
answer `1.0e-5`. Filed:
`doc/08_tracking/bug/sqrt_f64_not_correctly_rounded_2026-09-01.md`. The pair
asserts the divergence as a self-expiring sentinel rather than relaxing to a
tolerance — when the bug is fixed the assertion fails and forces a spec update.

That a single new math pair found a genuine correctness bug is the strongest
available argument for funding the paydown below.

## Paydown plan

The binding constraint is **not** picking high-traffic symbols. It is:

```
coverable = (registered in the interpreter's extern dispatch table)
          ∩ (a Simple twin that ACTUALLY EXISTS in src/lib)
          − (already covered)
```

Measured: 2064 `rt_*` are dispatch-registered; 390 of those are both-lane and
uncovered; but only **31** have any recorded Simple twin, and of those only
**7** had a twin that actually exists. All 7 were covered by this change.

### Tranche A — implement 5 twins already specified but never written (DONE 2026-09-01)

**Status: landed.** All five twins are written in pure Simple and dual-run:
`src/lib/common/str_search_pure.spl` (`str_ends_with`, `str_last_index_of`),
`src/lib/common/char_from_code_pure.spl` (`char_from_code`),
`src/lib/common/float_class_pure.spl` (`is_nan_f64`, `is_inf_f64`); pairs in
`test/01_unit/lib/common/spec/dual_run_tranche_a_spec.spl`. Each was proved
mutation-red (an injected bug in the twin makes its case FAIL), not merely
green. Two attempted mutants on `char_from_code` are equivalent mutants: with
the surrogate guard or the >U+10FFFF guard removed, the downstream UTF-8
validator rejects the same inputs and still yields "", so the twin's answer is
unchanged. No new `rt_*` symbol was added in C or Rust.


The migration inventory's `replacement:` field mixes **landed** migrations with
**planned** ones. Grepping `src/lib` for each named function found five that do
not exist: `str_ends_with`, `str_last_index_of`, `char_from_code`, `is_nan_f64`,
`is_inf_f64` (oracles `rt_string_ends_with`, `rt_string_rfind`,
`rt_char_from_code`, `rt_math_is_nan`, `rt_math_is_inf`).

These were **deliberately left uncovered**. A placeholder twin would make the
harness certify agreement between the runtime and a function invented to agree
with it — worse than no coverage. Each is small, pure and already
dispatch-registered, so writing the five real twins is the cheapest next +5
pairs. **Do not fix the inventory by editing its prose; regenerate the census.**

### Tranche B — the remaining ~19 recorded twins (~2 weeks, STARTED 2026-09-01)

**Started:** `rt_dict_contains` (C-MIG-0041) and `rt_array_repeat` (C-MIG-0042)
are wired in `test/01_unit/lib/common/spec/dual_run_tranche_b_spec.spl`; their
twins already existed and were only file-private, so the change was to export
them. Both are mutation-red. **`rt_base64url_encode` was attempted and left
UNCOVERED on purpose:** its interpreter oracle takes TWO arguments (a
pointer/length pair), not one `text`, so no honest one-argument value-compare
exists — an adapter written to make the two agree is exactly the twin that
would make the harness certify a lie. It needs the shadow-buffer mode.


`rt_crc32_text`, `rt_base64url_encode`, `rt_dict_contains`, `rt_array_repeat`,
`rt_text_find_invalid_utf8`, `rt_simd_str_last_index_of`, the `rt_string_*`
family, `rt_path_relative`. Each needs its twin's existence verified first —
that check is what shrank tranche 2 from 31 candidates to 7.

### Tranche C — the 1053 Rust-only symbols (the actual debt)

Ordered by directive severity, not traffic. Each needs a C implementation, a
Simple implementation and an alias. At ~7 pairs per focused session this is
years of work, which is exactly why the ratchet matters more than the tranches:
**it stops the number from growing** while the tranches shrink it.

Do not attempt to hand-write ~1500 twins. The realistic target is to hold the
line at 2489 and pay down the dispatch-registered, pure, high-traffic subset.
