# Item 5 app vector receipt runner

This runner is an execution harness for externally built PureDatabase and live HTTP probe binaries. It uses the landed test-only provider event observer. It does not build a compiler or app, and it cannot establish production image size or speedup.

`scripts/check/run-item5-app-vector-receipts.shs` requires four executable app binaries, their exact SHA-256 values, the provider DSO and observer DSO with hashes, the vector provider and implementation identities, a passing Phase2 Hello receipt, and an app-build provenance manifest. The manifest binds each supplied binary hash to the Hello compiler hash and source commit. It is caller-supplied evidence; the runner records its hash and does not independently attest the build process.

Before execution, the runner stages private read-only copies and rechecks their hashes. Each app runs under `process-tree-rss-watchdog.pl` with an enforced RSS cap and timeout. The watchdog's `root_pid` is authoritative. The observer writes one bounded event receipt to inherited FD 3; the runner validates its full schema, PID, event totals, provider load count, status, and required operation loop counts. The runner captures stdout, stderr, watchdog receipt, event receipt, binary/provider/observer hashes, peak RSS, and elapsed wall time.

The scalar app receipts must show zero provider loads and events. The bitmap app must report the fixture success marker, ten successful AND events, and eleven bitmap loops. HTTP must report its live-socket success marker and successful positive-loop evidence for opcodes 3 and 4. DB emits ten complete row records; the runner compares them to an independent arithmetic oracle for each boundary size and empty result. HTTP emits two complete wire records; the runner checks record shape and length and requires exact scalar/vector wire equality. The app fixtures separately assert request policy and rejection behavior.

Timing and RSS are diagnostic only: the event observer adds callback overhead and scalar/vector app runs do not have equivalent workloads. The scalar path is an instrumented no-provider-load check, not proof of a minimal production image. This output is execution evidence only; AVX512 application admission still requires independently reviewed producer provenance and binaries, and does not qualify CUDA, ARM, or RISC-V paths.

The focused shell harness `scripts/check/test-item5-app-vector-receipt-runner.shs` tests receipt acceptance/rejection, PID binding, staging hash enforcement, missing-binary refusal, and help parsing. The four app launch paths use the staged executable files, not their containing role directories. Shell syntax and Perl syntax checks passed. The shared parser accepted all 11 retained native provider receipts against their watchdog root PIDs and accepted the retained valid parser fixture while rejecting 10 prior malformed fixtures.

The optional staging/supervisor negative check passed using a tiny native C program that returns status 1. It verifies that this nonzero child exit is rejected while a completed, quiescent watchdog receipt and bounded observer receipt are retained before assertions. Evidence is at `build/review/item5-app-vector-runner-staging-negative-oct7-20261007`; this is harness-only evidence and does not execute a Simple app. The earlier `/bin/false` attempt at `build/review/item5-app-vector-runner-staging-negative-cycle2-20261006` remains a failed harness attempt documenting argv0 sensitivity in coreutils. Native app evidence remains unavailable until the four separately qualified binaries and their manifest are supplied.
