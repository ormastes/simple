## Open research and requirement decisions

The user additionally requested distributed development through the existing Simple Container and Kubernetes-style language on varied operating systems. [Simple Orchestrator research](../os/container/simple_orchestrator_and_container_2026-09-06.md) already defines SDN/Pod/Job vocabulary and a cross-host architecture. Current source has strict `PodSpecV1` and `JobV1` decoders, a portable `RuntimeProviderV1` result/identity contract, and one hosted Linux OCI provider. `NodeCapabilities` in the draft build contract carries target triples and provider ABI but no independent physical/execution OS or isolation claim. These must be composed in an app adapter, not collapsed into the compiler output target. Astra's 2026-09-25 read-only review found that `pipeline_runner.spl` does not check Pod OS against host OS, routes `native-sandbox` through a raw process, hardcodes the Linux provider and `/tmp`, and does not verify Docker daemon OS. Those gaps must be closed before a distributed container result is trusted. The [clean-container discovery bug](../../08_tracking/bug/container_discovery_missing_admitted_linux_runtime_2026-09-23.md) further shows that workflow discovery currently lacks an admitted runtime artifact. Portable resource syntax does not prove cross-OS execution or equivalent isolation.

- The `dist_build_scheduler` feature route and SPipe knowledge receipt have since been drafted in this worktree; update their source path list as implementation grows and verify the route before acceptance.
- The user's full-implementation and parallel-agent requests selected the complete functional end state and parallel sequencing. [Numbered feature requirements](../../02_requirements/feature/dist_build_scheduler.md) now record that scope; the earlier rollout comparison was removed after selection.
- Select measurable hook, preflight, build, memory, transfer and correctness targets before final requirements. The archive's warm eligible preflight P95 below 60 seconds is a proposal, not an observed result. See [NFR options](../../02_requirements/nfr/dist_build_scheduler_options.md).
- Establish real fixture baselines for native-build, header-heavy Clang builds, worker failures and two-node transfers. Existing probes cannot establish scheduler throughput or cache soundness.

## 2026-09-26 Ninja target invalidation observation

An isolated CMake/Ninja fixture under `build/research/clang_ninja_object_graph`
has a two-object `core` static library and an `app` consumer. `ninja -t query
libcore.a` listed both direct object inputs. After building `app`, `ninja -t
clean libcore.a` removed exactly three files in this fixture: the two `core`
objects and `libcore.a`. The unrelated `app` object and prior executable
remained. A dry-run `ninja app` then scheduled both core compiles, archive
creation and the app relink. This provides a possible graph-owned force
mechanism for a policy-only change even when object timestamps are future or
equal. It is one static-library fixture, not proof for generated sources,
object libraries, shared libraries, side outputs, concurrent builders or
hostile build directories. The Simple top-level policy gate remains unwired;
the current object-map barrier is still source-only and unqualified.

A separate configure-only CMake/Ninja static-library fixture on this macOS
host emitted one `libcore.a` archive edge with two direct object inputs,
`CMakeFiles/core.dir/a.c.o` and `CMakeFiles/core.dir/b.c.o`. Each object had
its own `C_COMPILER__...` producer edge with an order-only CMake target
dependency. This observed shape supports a restricted exact object-map check
against the archive edge; it does not establish the grammar of all CMake
generators, versions, platforms or target kinds.
