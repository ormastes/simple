# Analysis — 2D showcase 40-minute stall: GC-tier Engine2D on a software render path

Date: 2026-07-25
Status: root-caused, not fixed
Related bugs:
- `doc/08_tracking/bug/interpreter_gc_root_scan_blowup_large_array_2026-07-25.md`
- `doc/08_tracking/bug/sha256_bytes_push_quadratic_font_hash_2026-07-25.md`

## Symptom

`2D x headless` cell of the showcase matrix: 320x240 software offscreen render
produced no evidence line after 40+ minutes and had to be killed. Logged as a
regression against a 2026-07-14 note recording "2D 320x240 standalone PASS".
Run log was ~75,000 lines.

## What the evidence actually shows

**The stall is resolution-independent.** Identical failure at 32x24 and at
320x240. This rules out any per-pixel or per-canvas-area algorithm, and with it
the initial O(n^2)-in-pixels hypothesis. Bisecting the showcase primitive by
primitive localized the stall to a single call: `Engine2D.load_font()`.

**Isolated, the same call is fast.** `try_load_runtime_ttf()` on the real font
completes in ~8s standalone. Adding one **unused, untouched** `Engine2D`
instance elsewhere in the same call stack makes the identical call take 2+
minutes and still climb. It reproduces with the font-load code moved to a
separate function, so it tracks *reachability from the live root set*, not
lexical scope.

## Two independent root causes

### 1. Tier misplacement (architectural)

`examples/06_io/ui/graphics_2d_showcase_gui.spl:10`:

    use std.gpu.engine2d.engine.{Engine2D}

`std.gpu.engine2d.engine` resolves to `src/lib/gc_async_mut/gpu/engine2d/engine.spl`
— the **GC tier**. A *software* offscreen 2D render therefore instantiates a
GC-tier, GPU-oriented engine. Meanwhile the font loader it calls lives at
`src/lib/nogc_sync_mut/io/font_sffi.spl:133` — the nogc tier.

Net effect: nogc code mutating a 17.7 MB array (Noto Sans SC) while a GC-tier
object is live on the root set. Per `.claude/rules/` and
`feedback_nogc_async_default_tier`, `gc_async_mut/` is reserved for gpu/cuda/
torch/ML; nogc_async is the default tier. A software 2D path has no reason to
reach into `std.gpu`.

**This is not a one-line import swap.** The nogc `Engine2D`
(`src/lib/nogc_sync_mut/engine/core/engine.spl:54`) is a different abstraction —
a scene graph (`get_node(NodeId) -> Node2D?`, `get_renderer_mode()`) — not a
drop-in for the immediate-mode GPU engine.

### 2. Interpreter/GC root-scan blowup (runtime defect)

Cost per array mutation appears to scale with live-heap complexity. Fixing the
tier stops *this* path from triggering it, but any code legitimately holding a
GC-tier object (gpu, cuda, torch, ML all live there by design) while mutating a
large array remains exposed. Filed separately; that is the deeper fix.

## Ruled out / corrected

- **Not** a per-pixel algorithm — resolution-independent.
- **`sha256_bytes` is not the dominant cause.** It did carry the documented
  `.push()`-clones pattern while hashing the 17.7 MB font on every
  `load_font()`, and has been hardened to pre-size + index-write. But
  benchmarking showed the original was already **linear** on the seed binary
  (clean 2x-time-per-2x-input, 3.08s at full size). Treat that change as
  hardening against a known risk pattern, not as a proven perf fix.

## Wider pattern

This is the third instance today of one structural habit — **the same entity
defined in several places, then diverging**:

| Duplication | Visible failure |
|---|---|
| `ant-trace` / `ant_trace` (29 dir pairs; 48 files differing, 39 dashed-only) | native-build module-name collision, repo-root builds fail |
| `CompiledSymbolKind` x3 (one had `External` where others had `Const`) | `unknown variant 'Const'`, entry-closure discovery dies |
| `Engine2D` + `ui`/`web`/`engine`/`websocket` across all four tiers | GC-tier object pulled into a nogc software path |

Same-named types in different modules collapse in the global registry, so first
registration wins regardless of which module an importer named. That is already
recorded for structs in `feedback_interp_struct_name_collision_global_registry`;
these show it applies to enums and to tier-duplicated classes too.

## Reading-the-output trap (cost two wrong conclusions here)

A spec run emits ~5,200 lines, and the authoritative `Results:` line lands at
~5,149 with **thousands of warning lines trailing after it**. Any `tail -N` with
a small N shows only trailing warnings and looks like a failure with no verdict.

Two false conclusions came from this in one session:
1. "The spec failed / never produced a Results line" — it passed.
2. "`export use ...*` is rejected and blocks the run" — it is a **warning**
   (`ErrorHintLevel::Warning` in
   `src/compiler_rust/parser/src/stmt_parsing/module_system.rs:557-567`); the
   parser still returns `Ok(ExportUseStmt)`. 28 such re-exports exist under
   `src/lib` and none of them block anything.

Always `grep 'Results:'` on captured output. Never conclude from a tail.
This is `.claude/rules/testing.md` F3, restated because it was violated anyway.
