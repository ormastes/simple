# Repo layout survey: major language/compiler repos, and findings for Simple

Date: 2026-09-19
Scope: root and top-3-level directory layout conventions of major compiler/language
monorepos, compared against `/Users/ormastes/simple`'s current root. Written from
model knowledge (WebFetch/curl are blocked in this environment); anything not
independently re-verified against a live checkout is marked **unverified**.

## Method

For each project: approximate root entry count (visible, non-dotfile-heavy),
where vendored/third-party code lives, where generated/build state lives, where
platform variants live, naming convention, doc structure, and
manifest/ownership files. All figures are **unverified** approximations from
training knowledge of each project's public repo structure as of various past
snapshots — repo layouts drift over time and this doc does not re-fetch them.

### Rust (rust-lang/rust)

- Root (~20-25 visible entries): `compiler/`, `library/`, `src/` (mixed: `src/bootstrap`,
  `src/tools`, `src/etc`, some docs), `tests/` (moved out of `src/test` some
  years ago), `Cargo.toml`, `Cargo.lock`, `config.example.toml`, `x.py`
  (bootstrap driver script), `RELEASES.md`, `CONTRIBUTING.md`, `LICENSE-*`.
- Vendored/third-party: **`vendor/`** at repo root (populated by
  `cargo vendor`, mostly for offline/vendored-tarball release builds), plus
  git submodules for a handful of tightly-coupled tools (`src/tools/*` some as
  submodules). No `third_party/` directory — Rust standardizes on Cargo's own
  `vendor/` convention.
- Generated/mutable state: `build/` at root (gitignored) holds all
  stage0/1/2 build artifacts, downloaded stage0 compiler, and test output.
  Nothing generated is committed at root.
- Platform variants: not directory-based; platform/target selection is
  `target-tuple`-parameterized inside `build/<host-tuple>/...` and in
  `library/std/src/sys/<platform>/` (one subdir per platform family, e.g.
  `unix`, `windows`, `wasm`).
- Naming: **snake_case** throughout; no numbered directories.
- Docs: `src/doc/` (rustc-dev-guide, reference, nomicon, book are separate
  linked repos, not in-tree prose beyond READMEs).
- Ownership: `triagebot.toml` (bot-driven review/label routing) instead of
  `CODEOWNERS`; `COMPILER_TESTS.md`, `RUSTC_GUIDE` pointers.

### Go (golang/go)

- Root (~15 entries): `src/` (all stdlib + `cmd/` compiler/linker/tools +
  `go/` build tag machinery), `api/`, `doc/`, `misc/`, `test/` (compiler
  conformance tests, historically flat, largely `.go` files directly under
  `test/`), `AUTHORS`, `CONTRIBUTORS`, `go.env`.
- Vendored: Go's own toolchain vendors a small set of deps under
  **`src/vendor/`** and `src/cmd/vendor/` (per-Go-module vendor dirs, not a
  single top-level `vendor/`) because `src/` itself is a self-contained module.
- Generated/mutable state: `pkg/` (compiled package archives before the
  build-cache era; largely legacy) and `bin/` for build output — both
  gitignored when generated by `make.bash`. No root `build/`.
- Platform variants: **file-suffix based, not directory-based** —
  `foo_linux.go`, `foo_windows_amd64.go`, `//go:build` tags. This is the one
  major counter-example to "variants live in a directory."
- Naming: all lowercase, single-word package dirs, no snake_case multi-word
  dirs by convention (Go style discourages underscores in package names).
- Docs: `doc/` at root, largely superseded by go.dev's separately-hosted docs;
  `doc/go1.N.html` release notes.
- Ownership: no root `CODEOWNERS`; uses Gerrit + `OWNERS`-like conventions
  informally, mostly reviewer assignment by tooling rather than a static file.

### Zig (ziglang/zig)

- Root (~15 entries): `lib/` (stdlib **and** the C headers/libc shims Zig
  ships for cross-compilation, `lib/std`, `lib/libc`), `src/` (compiler
  proper, C++ historically, now self-hosted Zig), `test/` (behavior tests),
  `tools/`, `doc/` (langref source), `build.zig`, `build.zig.zon` (package
  manifest), `CMakeLists.txt` (legacy bootstrap).
- Vendored: **no top-level `vendor/`** — Zig's package manager
  (`build.zig.zon`) fetches deps into a global cache
  (`~/.cache/zig` / `zig-global-cache`), not an in-repo vendor dir; the
  compiler's own C++ bootstrap historically vendored a couple of things under
  `src/` directly (rare, being phased out as self-hosting completes).
- Generated/mutable state: **`zig-cache/`** (build cache, per-project,
  gitignored) and `zig-out/` (build output). This is Zig's namesake example
  of a tool-specific cache dir living beside the source, always gitignored,
  never a place third-party *source* lives.
- Platform variants: `lib/std/os/<platform>`, `lib/std/target.zig` metadata;
  directory-per-platform inside stdlib, similar to Rust's `sys/`.
- Naming: **snake_case**, no numbered dirs.
- Docs: `doc/langref.html.in` single-file reference source; no deep doc tree.
- Ownership: no `CODEOWNERS` historically; small core team, informal review.

### Swift (apple/swift)

- Root (~25-30 entries, notably flatter-feeling despite size): `lib/`
  (compiler library sources: Sema, SILGen, IRGen, Parse, AST — a huge tree),
  `include/` (public + internal C++ headers mirroring `lib/`), `stdlib/`
  (Swift standard library sources), `test/`, `unittests/`, `tools/` (driver,
  lldb support, swift-frontend entry points), `utils/` (build scripts,
  `build-script`), `docs/` (design docs, internals), `CMakeLists.txt`.
- Vendored: `utils/update-checkout` fetches sibling repos (`llvm-project`,
  `swift-corelibs-*`, `swift-package-manager`) as **sibling checkouts**, not
  as an in-tree `vendor/`; a small number of bundled deps live under
  `stdlib/public/Platform` or similar, no unified vendor dir.
- Generated/mutable state: out-of-tree build dir chosen by `build-script`
  (typically `../build/Ninja-.../swift-<platform>-<arch>`, i.e. **sibling to
  the repo, not inside it** — a notable divergence from Rust/Zig's in-repo
  `build/`).
- Platform variants: `stdlib/public/Platform/*.modulemap` per-OS, `lib/*/
  <Platform>` sparingly; mostly `#if os(...)` conditional compilation rather
  than directory splitting.
- Naming: mixed — `lib/` internals use `PascalCase` for C++ files (matching
  LLVM style), Swift-side stdlib uses lowercase dirs.
- Docs: `docs/` (root) is design-doc prose; separate `swift-evolution` repo
  hosts language proposals (kept OUT of the compiler repo entirely — a
  precedent for "proposal-shaped" docs not living beside implementation).
- Ownership: `CODEOWNERS`-style routing done via a bot (`swift-ci`) rather
  than the literal GitHub `CODEOWNERS` file historically.

### Kotlin (JetBrains/kotlin)

- Root (~30+ entries — this is a *large*, less pruned root): `compiler/`,
  `libraries/` (stdlib, kotlin-reflect, kotlin-test, each own Gradle module),
  `js/`, `native/` (Kotlin/Native backend + its own runtime + interop), `wasm/`,
  `plugins/` (compiler plugins: serialization, allopen, noarg, etc.),
  `idea/` historically (IDE plugin, later split out), `docs/`,
  `build-common/`, `gradle/`.
- Vendored: `third_party/` (used for prebuilt native deps, LLVM for
  Kotlin/Native); also relies heavily on Gradle dependency resolution rather
  than vendoring most JVM deps.
- Generated/mutable state: every module's own `build/` (Gradle convention),
  gitignored; a root `build/` also appears from the root Gradle project.
- Platform variants: **top-level directories per backend/target** — `jvm`,
  `js`, `native`, `wasm` each as siblings, not nested under one `platform/`
  — reflecting Kotlin's multi-backend architecture more than a single
  "platform" axis.
- Naming: lowercase, hyphenated Gradle module names in `settings.gradle.kts`,
  directories themselves usually lowercase single words.
- Docs: `docs/` mixes KEEP-adjacent design notes; language spec lives in a
  **separate** `Kotlin/kotlin-spec` repo.
- Ownership: `.github/CODEOWNERS` present; large `OWNERS`-style routing per
  subsystem is informal (JetBrains internal team boundaries).

### TypeScript (microsoft/TypeScript)

- Root (~20 entries): `src/` (compiler, services, server, harness — all
  under `src/`, itself several levels: `src/compiler`, `src/services`,
  `src/server`), `lib/` (**not source** — this is the *shipped* `.d.ts`
  lib files, `lib.es5.d.ts` etc., generated/curated, a naming trap since
  most other projects use `lib/` for source), `tests/` (baselines + cases),
  `scripts/`, `Herebyfile.mjs` (build driver, replaced Gulp), `package.json`.
- Vendored: no `vendor/`; npm `node_modules` (gitignored) covers all deps;
  a handful of doc/spec references (ECMA-262 links) not vendored, only linked.
- Generated/mutable state: `built/` or `lib/` build outputs historically
  under `built/local/`; today mostly under each package's own `dist/`-like
  output plus `.ts-build-info` caches — all gitignored.
- Platform variants: not directory-based (TS itself is host-agnostic; host
  bindings for Node vs browser live in small dedicated files, not dirs).
- Naming: camelCase filenames matching TS/JS convention, no numbering.
- Docs: `doc/spec-ARCHIVED.md` (the language spec was frozen and archived
  in-repo rather than kept live); most current docs live on the wiki, not
  in-tree.
- Ownership: `.github/CODEOWNERS` present, standard GitHub PR review routing.

### Deno (denoland/deno)

- Root (~20 entries): `cli/`, `core/` (the JS/Rust bridge runtime core),
  `runtime/`, `ext/` (extensions, one dir per Web API: `ext/fetch`,
  `ext/fs`, `ext/webgpu` — a strong "one capability = one directory" pattern),
  `tests/`, `bench_util/`, `tools/`, `Cargo.toml` (workspace root).
- Vendored: no top-level `vendor/`; Rust deps via `Cargo.lock` +
  crates.io, JS-facing bits vendored per-extension as needed inside `ext/*`
  rather than centrally.
- Generated/mutable state: `target/` (standard Rust Cargo build dir),
  gitignored.
- Platform variants: `runtime/js/` cross-platform, OS-specific bits behind
  `cfg(target_os = ...)` inline, not directory-split at the top level.
- Naming: snake_case (Rust convention) for the Rust tree, kebab-case
  occasionally for tool/script names.
- Docs: docs mostly live in a separate `denoland/docs` /
  `deno.land/manual` site, not deeply in-tree.
- Ownership: `.github/CODEOWNERS` present, mapping `ext/*` subtrees to
  named maintainers — a good example of manifest-driven subsystem ownership.

### Nim (nim-lang/Nim)

- Root (~20 entries): `compiler/`, `lib/` (stdlib, `lib/pure`, `lib/system`,
  `lib/core`, `lib/posix` etc. — again platform-suffixed/dir-split inside
  `lib`), `tests/`, `tools/`, `doc/` (the manual and rendered docs source
  live IN-tree as `.rst`, unusual among this list — most others keep prose
  external), `koch.nims` (bootstrap/build driver script, Nim's analogue of
  `x.py`/`make.bash`).
- Vendored: `dist/` at root historically held bundled C libraries
  (checksums, nimble packages) needed for bootstrapping without network
  access — effectively Nim's vendor dir under a different name.
- Generated/mutable state: `bin/` (compiled `nim` binary itself, sometimes
  committed for bootstrap convenience in release tarballs, but gitignored in
  the dev repo), `nimcache/` (per-project compile cache, always gitignored,
  never committed source).
- Platform variants: `lib/system/*` per-OS files (`osalloc.nim`,
  `widestrs.nim` etc.), `lib/posix/`, `lib/windows/`.
- Naming: **snake_case**, no numbering.
- Docs: **in-tree `doc/`** with the language manual as versioned `.rst`,
  a notable exception to "docs live externally."
- Ownership: informal; no CODEOWNERS historically (small core team).

### Crystal (crystal-lang/crystal)

- Root (~20 entries): `src/` (**both** compiler and stdlib live together
  under `src/`, split by top-level module name — `src/compiler/`,
  `src/json/`, `src/http/` etc. — a flatter merge than most peers, which
  usually separate compiler-proper from stdlib at the root), `spec/` (specs,
  Crystal's own name for its test suite — note the name collision risk with
  "spec" as used elsewhere for language/requirement specs), `samples/`,
  `etc/`, `Makefile`.
- Vendored: `.build/` and `lib/` (the latter is Crystal *shards* dependency
  cache, analogous to `node_modules`, gitignored) — no static `vendor/`.
- Generated/mutable state: `.build/`, `.shards/`, both gitignored.
- Platform variants: `src/**/  {unix,win32}` suffix files akin to Go's
  `_windows.cr` pattern in places, mixed with directory splits.
- Naming: snake_case.
- Docs: `docs/` separate site source (`crystal-book`) mostly lives in its
  own repo, not deeply in-tree.
- Ownership: `.github/CODEOWNERS` present.

### LLVM monorepo (llvm/llvm-project)

- Root (~25 entries, one per sub-project): `llvm/`, `clang/`, `clang-tools-extra/`,
  `lld/`, `lldb/`, `mlir/`, `flang/`, `libcxx/`, `libcxxabi/`, `libunwind/`,
  `compiler-rt/`, `polly/`, `bolt/`, `openmp/`, `runtimes/` (meta-build
  glue for the `libc*`/`compiler-rt` "runtimes" build mode), **`third-party/`**
  (note the hyphen, not underscore — inconsistent with most others' `third_party`),
  `cmake/`, `.ci/`.
- Vendored/third-party: **`third-party/`** at root, holding things like
  `benchmark` (Google Benchmark) as a controlled subset, plus each
  sub-project's own smaller vendored bits (e.g. `llvm/utils/unittest/googletest`).
  This is the one project in this survey using the literal spelling
  `third-party` (hyphen) rather than `third_party` (underscore) or `vendor`.
- Generated/mutable state: out-of-tree build dir by CMake convention
  (`build/`, user-chosen, always gitignored, frequently placed as a sibling).
- Platform variants: each sub-project has its own `lib/Target/<Arch>/` for
  codegen backends (LLVM's `lib/Target/X86`, `lib/Target/AArch64`, etc.) —
  directory-per-architecture is the dominant pattern here, not per-OS.
- Naming: `PascalCase` for C++ source files matching class names (LLVM's own
  strict style guide), directories mostly `PascalCase` or short lowercase.
- Docs: each sub-project keeps its own `docs/` in ReStructuredText, rendered
  via Sphinx; no single unified doc root.
- Ownership: `llvm/CODE_OWNERS.TXT` (a flat text list, predates GitHub's
  native `CODEOWNERS` file and still coexists with a newer `.github/CODEOWNERS`
  in parts of the tree) — an example of migrating ownership metadata format
  without deleting the old one immediately.

### CPython (python/cpython)

- Root (~25 entries): `Lib/` (**capitalized** — pure-Python stdlib),
  `Modules/` (capitalized — C extension modules), `Objects/` (core object
  implementations), `Python/` (interpreter core, ceval loop), `Parser/`,
  `Include/` (public C headers), `Doc/` (capitalized — reST source for the
  official docs, built via Sphinx), `Tools/` (capitalized — dev/build
  tooling scripts), `Grammar/`, `PC/` + `PCbuild/` (Windows-specific build),
  `Mac/` (macOS-specific), `configure`/`configure.ac`, `setup.py`.
- Vendored: no single `vendor/`; a handful of bundled third-party C libs
  live under `Modules/_decimal/libmpdec/`, `Modules/expat/`,
  `Modules/zlib` references — vendored **per-module**, not centrally, which
  is CPython's main divergence from the rest of this survey.
- Generated/mutable state: in-tree `build/` when using the default
  `./configure && make` flow (gitignored), platform-specific build dirs
  under `PCbuild/` for Windows.
- Platform variants: **directory-per-platform at the root** — `PC/`, `PCbuild/`,
  `Mac/` are Windows/macOS-specific trees sitting as top-level siblings, a
  more root-level-visible version of the pattern than Rust/Zig's nested
  `sys/<platform>`.
- Naming: **CapitalizedWords** for top-level dirs (`Lib`, `Doc`, `Tools`),
  the one outlier from the snake_case-dominant crowd; files inside vary.
- Docs: `Doc/` in-tree, canonical source of the published Python docs —
  another exception (with Nim) to "docs live externally."
- Ownership: no root `CODEOWNERS`; PEP-based governance, per-file
  "Experts Index" in `Doc/` maintained as prose, not a machine-checked file.

Observations that recur across nearly all of them:
1. **No project uses a directory literally named `var/` for anything.**
   `var/` as FHS-style "variable/mutable runtime state" (logs, spool, cache at
   *runtime*, not build time) does not appear as a source-tree convention in
   any of these repos — it's a Unix filesystem-hierarchy term, not a
   repo-layout term, and repurposing it for repo content invites confusion
   with that meaning.
2. **Vendored code always gets its own name distinct from anything else**:
   `vendor/` (Rust, Go-per-module), `third_party/` (Kotlin), `third-party/`
   (LLVM, hyphenated), `dist/` (Nim, an outlier), or no directory at all
   because the package manager fetches out-of-tree (Zig, TypeScript, Deno,
   Crystal, Swift). It is **never** merged with build-output or runtime-state
   directories.
3. **Generated/build state is either gitignored in-tree (`build/`,
   `target/`, `zig-cache/`, `nimcache/`) or fully out-of-tree** (Swift,
   LLVM's typical CMake flow). It is never a place vendored *source* lives,
   and it is never committed.
4. **Platform variants are source** and live inside the source tree
   (`src/`, `lib/`), either as nested directories (`sys/<os>`,
   `Target/<Arch>`) or as filename suffixes (Go, Crystal) — never pulled out
   to a directory that also holds vendor code or runtime state.
5. Root entry counts cluster in the **15-30** range for essentially every
   project surveyed, none of them expose 60+ top-level entries — large
   subsystems get ONE root directory each (`compiler/`, `runtime/`, `lib/`,
   `mlir/`), not a flat scatter of many single-purpose root dirs.

## Findings for Simple

### 1. Should `var/`, `variants/`, and `vendor/` be merged under `var/`?

**No.** Every project surveyed keeps these three concerns in three separate
places, and for principled reasons, not just habit:

- **`vendor/` (limine bootloader) should stay `vendor/`** (or be renamed
  `third_party/`, per CLAUDE.md's own "Owned-Code Scope" language, which
  already uses "vendored or third-party" interchangeably). Every surveyed
  project that vendors anything gives it a name that says "this is not ours"
  — `vendor/`, `third_party/`, `third-party/`, or a package-manager cache
  outside the tree entirely. None of them fold vendored code into a directory
  that also means "mutable state" or "generated output." Merging Simple's
  `vendor/` into `var/` would be a **regression against universal
  convention** with no compensating benefit — the two concerns (frozen
  external source vs. mutable local state) have opposite lifecycles: vendored
  code is committed and rarely touched; `var/`-style state is regenerated and
  usually gitignored.
- **`variants/` (a Simple module: `__init__.spl`, `platform/`, `ui/`) is
  SOURCE and belongs under `src/`**, matching the "platform variants live
  inside the source tree" pattern seen in every surveyed project — Rust's
  `library/std/src/sys/<platform>`, Zig's `lib/std/os/<platform>`, Nim's
  `lib/posix`/`lib/windows`, CPython's `PC/`/`Mac/` (their outlier of
  root-level platform dirs is still source, never merged with build state).
  Root-level `variants/` as a sibling of `src/` is itself already a mild
  anomaly relative to this survey — no peer project keeps platform-dispatch
  *source* as a root sibling of its main source tree. Moving it under
  `src/` (e.g. `src/variants/` or absorbed into `src/lib/` alongside the
  existing `nogc_sync_mut`/`platform`-style dirs) would match the pattern
  exactly. Filing it under `var/` would be actively wrong: `var/` in every
  precedent (and in FHS, which is presumably the origin of the name in this
  repo) means "mutable runtime state," and `variants/` is compiled input, not
  runtime output.
- **`var/` should hold only generated/mutable state (or be removed/gitignored)**,
  matching `build/`, `target/`, `zig-cache/`, `nimcache/`, `.build/` in every
  surveyed project: always either gitignored-and-regenerated or absent from
  the committed tree. If the current `var/lib` content is genuinely mutable
  runtime state (caches, local DB files, logs), it should be gitignored, not
  expanded to also host `vendor/` or `variants/`. If `var/lib` is actually
  committed source or config masquerading as "state," that's a separate
  naming problem worth its own investigation — this survey did not inspect
  `var/lib`'s actual contents (**unverified**: this doc did not read
  `var/lib/**`).

**Trade-offs, stated honestly:**
- *For* merging (the case against this recommendation): a single `var/`
  umbrella directory reduces root entry count by 2, which directly serves
  finding #3's ≤15-entries goal, and if an LLM agent already treats "anything
  not `src/`, `test/`, `doc/`" as fair game for cleanup, fewer root names
  are fewer things to get wrong.
- *Against* merging (why the recommendation still holds): the survey shows
  zero precedent for this merge across 11 major repos; it conflates three
  different lifecycles (frozen-external / compiled-source / ephemeral-state)
  under one name, which is exactly the kind of ambiguity that makes a
  directory's *contents* — not just its *existence* — hard for an agent (or a
  human) to reason about; and the actual root-count win is available more
  safely by moving `variants/` into `src/` and gitignoring/removing `var/`
  outright, achieving the same entry-count reduction without the semantic
  merge.

### 2. Conventions that make a layout robust against LLM agents breaking it

Drawing on both the survey and what already exists in this repo
(`FILE.md` manifests, `scripts/check-workspace-root-guard.shs` per
`.claude/rules/structure.md`):

- **Per-directory manifests with fixed depth** — Simple already has this
  idea (`FILE.md` + root-guard lint) more explicitly than any project
  surveyed above (none of Rust/Go/Zig/Swift/Kotlin/TS/Deno/Nim/Crystal/LLVM/
  CPython enforce a machine-checked "allowed entries" manifest per directory
  — the closest analogue is LLVM's `CODE_OWNERS.TXT` and Deno's
  `CODEOWNERS`, which route *review*, not *structure*). This is a genuine
  strength to keep and extend, not weaken.
- **One naming convention, applied uniformly** — the survey shows every
  project picks ONE case convention (snake_case dominates: Rust, Zig, Nim,
  Deno, Crystal) and sticks to it almost everywhere; the two outliers
  (CPython's CapitalizedWords, LLVM's PascalCase) are each internally
  consistent, not mixed. A repo with mixed conventions gives an LLM agent no
  signal for "does this new file's name match the pattern," which is
  precisely the ambiguity that produces near-duplicate names.
- **No near-duplicate directory names** — none of the 11 surveyed projects
  has two directories that mean almost the same thing (no repo has both
  `doc/` and `docs/`, or both `test/` and `tests/`, at the same time — each
  picks exactly one spelling repo-wide). Simple's current root has **both
  `doc/` and `docs/`**, which is exactly the class of ambiguity every peer
  avoids, plus the numbered-vs-unnumbered test split noted in the prompt
  (`test/01_unit` vs a hypothetical `test/unit`) and `doc/06_spec` vs a
  top-level `spec/` (both present at Simple's root per the `ls` above). An
  agent asked to "add a test" or "add a doc" has no way to know which of two
  plausible targets is canonical without reading prose first — exactly the
  failure mode a machine-checked allowlist should prevent, but only if the
  allowlist names ONE of the two, not both.
- **Machine-checked root allowlist** — already exists
  (`scripts/check-workspace-root-guard.shs`); the finding from this survey is
  that it should be the enforcement mechanism for *decisions* like #1 above
  (e.g., failing a PR that reintroduces a root-level `vendor2/` or a second
  `doc`-like directory), not just a static list that has to be manually kept
  in sync with reality.
- **Stable paths referenced by config, not prose** — every surveyed project
  that has a real "where does X live" answer encodes it in a build/package
  manifest (`Cargo.toml` workspace members, `settings.gradle.kts` module
