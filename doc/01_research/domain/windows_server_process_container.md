# Windows Server process containers: domain research

Sources checked 2026-09-27. Microsoft's [isolation modes](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/hyperv-container) distinguish process isolation, which shares the host kernel and isolates filesystem, registry, process, and network namespaces, from Hyper-V isolation, which uses a utility VM. Windows Server defaults to process isolation, but Simple Container must request and verify it explicitly. Windows *HostProcess* containers are a different facility: they lack filesystem and process isolation, so they do not satisfy this requirement. [Kubernetes HostProcess documentation](https://kubernetes.io/docs/tasks/configure-pod-container/create-hostprocess-pod/).

The [current Microsoft compatibility matrix](https://learn.microsoft.com/en-us/virtualization/windowscontainers/deploy-containers/version-compatibility) lists these process-isolated Server pairs: 2025 host with 2025 **or 2022** image; 2022 with 2022; 2019 with 2019; 2016 with 2016. The page's generic same-build prose does not mention its 2025→2022 exception; use the explicit matrix and confirm the pair on a live host. Server 2016 also requires matching revision; later releases do not require exact patch revision matching. An incompatible pair must fail, with no Hyper-V retry.

The same matrix also lists Windows 11 with Windows Server 2022 and, starting at Windows 11 24H2, Windows Server 2025 images under **process** isolation. Microsoft describes the Windows 11 cross-build route as a development preview; the [isolation guide](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/hyperv-container) recommends Windows Server for production and says Windows client defaults to Hyper-V unless process mode is requested explicitly. The Windows 11 route therefore merits a separate developer fixture and capability, not an implicit extension of Windows Server qualification. The page's 24H2 footnote prints `Build 2600`; probe the live build and current matrix rather than hardcoding that apparent shorthand.

An available native path is containerd with `containerd-shim-runhcs-v1`, which calls HCS through hcsshim; this shim can run process or Hyper-V containers and therefore its mere presence proves neither mode. Its `v1` suffix is a shim name, not a claim that it implements containerd Runtime V1: the [hcsshim README](https://github.com/microsoft/hcsshim) says it implements the Runtime V2 API. That README marks the process-specific `containerd-shim-process-v2` implementation **coming soon**, so the initial design uses the available runhcs shim and probes exact installed versions. [Microsoft's on-premises support policy](https://learn.microsoft.com/en-us/troubleshoot/windows-server/containers/support-for-windows-containers-docker-on-premises-scenarios) says containerd on Windows Server can run containers but receives community rather than Microsoft runtime support; the plan must distinguish that tradeoff from Windows OS support. HCS exposes compute-system and process handles plus create, start, wait, stop, and property operations; the runtime must retain identity across these operations. [HCS API reference](https://learn.microsoft.com/en-us/virtualization/api/hcs/reference/apioverview).

Native Windows containers still need image layers and writable scratch storage; a `sandbox.vhdx` scratch file is a storage artifact and does not make the process-isolated workload a VM. HNS/HCS coordinate endpoint creation, so network policy cannot be inferred from a container ID alone. [Windows storage](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/container-storage); [network architecture](https://learn.microsoft.com/en-us/virtualization/windowscontainers/container-networking/architecture).
Containerd task creation alone is not a network provisioning plan: the adapter must select a concrete CNI/HCN route that owns HNS endpoint creation and cleanup. A virtual switch used for networking is not evidence of a utility VM. [Windows networking architecture](https://learn.microsoft.com/en-us/virtualization/windowscontainers/container-networking/architecture).

For acceptance, record the requested mode **and** an independent runtime/HCS observation of the created compute system. A CLI flag or successful task exit alone cannot distinguish process isolation from an automatic Hyper-V fallback. Microsoft documents `docker inspect ... HostConfig.Isolation` for Docker; a containerd adapter needs equivalent actual-mode evidence from its own runtime/HCS path. The live fixture should also record image OS metadata, resolved digest, host build, and absence of a utility VM. This is an evidence requirement for Simple, inferred from the two isolation modes and the multi-mode V1 shim, not a claim that one particular containerd field already supplies every observation.

The Windows Containers feature and runtime require host setup. The [requirements page](https://learn.microsoft.com/en-us/virtualization/windowscontainers/deploy-containers/system-requirements) requires the Hyper-V role for **Hyper-V isolation**, not for the selected process route. `ContainerUser` is the recommended lower-privilege workload identity, but it does not give the invoking client rootless HCS authority. Docker's named pipe is Administrator-only by default, and granting broad pipe access is not a workload-scoped permission model. A non-admin Simple client needs a separately selected and tested delegated authority route; absent that route, native launch stays unavailable. [Container security](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/container-security); [Docker daemon access](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-docker/configure-docker-daemon).

Microsoft does not treat process isolation as a robust boundary for hostile multitenant workloads. This design can serve trusted developer/build workloads under an explicit policy; it must not silently claim strong hostile-tenant isolation. [Container security](https://learn.microsoft.com/en-us/virtualization/windowscontainers/manage-containers/container-security).
