# PR gate latency and tiers: GitHub domain research

GitHub treats the check/job **name** as the required status identity. Keep one unique, stable required context through a migration; if a workflow is skipped by path or branch filtering, its required check can remain pending. Condition jobs or steps inside an always-triggered workflow instead, and fail closed on unexpected `needs` results. [Required-check troubleshooting](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks), [job conditions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-jobs-with-conditions).

The latest relevant PR head or test-merge commit must carry a successful required result; earlier green commits do not qualify. `workflow_dispatch` job checks do not themselves satisfy PR required-status evaluation. The SPipe broker publishes a check run explicitly to the reviewed head, so its exact-head and base/ruleset binding must remain intact if it stays required. [Required-check troubleshooting](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).

Strict required checks force branch updates and rebuilds when main advances. Loose checks reduce repeats but can admit combinations never tested. A merge queue can test the latest base plus queued PRs without forcing author rebases, but required Actions workflows then need a `merge_group` trigger. [Available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), [merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue).

GitHub workflow-level path filters evaluate only a limited changed-file set and can leave required checks pending. Therefore any required compile/validation workflow should trigger on every PR and classify inside the job. Advisory workflows may use path filters with this coverage limitation documented. [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).
