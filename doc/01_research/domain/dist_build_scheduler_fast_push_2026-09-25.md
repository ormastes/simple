# External constraints for distributed builds and fast push feedback

**Date checked:** 2026-09-25. These are platform contracts, not evidence that the Simple repository implements the proposed scheduler or satisfies a performance target. The bundled Clang research remains in [the extracted archive](simple_clang_header_cache_2026-09-25/README.md).

## Git and GitHub boundaries

- Git's [pre-push hook contract](https://git-scm.com/docs/githooks) supplies each proposed local/remote ref update on stdin and permits a nonzero hook status to block the push. A fast local gate must evaluate the exact outgoing refs and their committed trees, including multiple ref rows, rather than a dirty worktree or guessed `HEAD`.
- GitHub [rulesets and required checks](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets) may require checks from a specified app and can require the head to be current with the base. A local green hook is useful developer feedback; it is not by itself protected merge admission. Whether this repository can use a merge queue or has a particular live ruleset needs an explicit current-state query before configuring GitHub.
- GitHub's [workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) says required checks associated with a workflow skipped by branch/path/commit-message filtering can remain pending. Design an always-present aggregate status and classify non-applicable work inside the job; do not use a skipped required workflow as proof of a passing check.
- If a future merge queue is selected and available, GitHub's [merge queue guide](https://docs.github.com/en/enterprise-cloud%40latest/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue) requires the `merge_group` event for GitHub Actions checks. This is conditional; the imported report does not prove that the current repository has merge-queue entitlement.
- GitHub's [`pull_request_target` security guidance](https://docs.github.com/en/actions/reference/security/securely-using_pull_request_target) distinguishes base-owned workflow code from untrusted PR-head code. A base-owned receipt verifier must treat PR bytes and artifacts as data; executing head code in a privileged job would cross the intended trust boundary.
- GitHub's [dependency cache reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching) treats restored caches as untrusted and describes poisoning risks from low-trust workflows. A distributed build cache requires independent content and policy validation before its outputs become accepted check evidence.
- Git's [submodule documentation](https://git-scm.com/docs/gitsubmodules) defines the parent gitlink as the expected child commit. The [`--remote` update option](https://git-scm.com/docs/git-submodule) follows a remote-tracking branch instead of that recorded commit, so an admitted build must materialize the gitlink and treat any changed pin as a changed input.
- Git's [worktree documentation](https://git-scm.com/docs/git-worktree) describes shared repository administration with per-worktree `HEAD`; the [repository layout reference](https://git-scm.com/docs/gitrepository-layout) places hooks in the common directory for linked worktrees. Parallel agent work therefore needs worktree-aware hook dispatch and distinct writable build directories, not a hook pinned to one checkout.

## Implications for the Simple plan

Keep one canonical gate registry and exact-ref receipt model. Optimize by avoiding repeated scans, sharing immutable parsed inputs and scheduling independent obligations under a bounded budget, then measuring the same admission result against the current implementation. Preserve fail-closed outcomes (`FAIL`, `INCOMPLETE`, `ERROR`) and the protected remote check independently of local elapsed time. The source repository must be inspected for existing parallelism, receipt signing and hook installation before proposing new code; the archived build-platform report is a design baseline, not a current-code census.

## Signed local evidence and GitHub build jobs

The current [signer](../../../scripts/check/sign-local-ci-receipt.shs) makes an SSH-signed local claim about an exact source tree, gate manifest and row results, and the [verifier](../../../scripts/check/verify-local-ci-receipt.shs) checks a base-approved signer, identity and complete pass rows. Signing authenticates the claimant; it does not independently prove that the local checks ran. The base-controlled [code-idiom decision workflow](../../../.github/workflows/code-idiom-receipt.yml) can shorten selected rows in the non-required extended job, while the [required fast-gates job](../../../.github/workflows/repo-hygiene.yml) still runs. The inspected [binary build workflow](../../../.github/workflows/build-binaries.yml) has no receipt admission path; the other inspected build workflows likewise have no receipt reference.

For build reuse, a required GitHub context must still run a trusted verifier and report its verdict. Admit a local build result only for an approved signer and job/platform scope with exact candidate, target, toolchain, complete inputs, submodule/policy/checker digests and output evidence. Missing, stale, malformed, revoked or unverifiable evidence selects full remote build execution. The user's phrase “build claude” is ambiguous; clarification is pending before assigning a specific additional agent or cloud-build check. These are design requirements, not current build-workflow behavior.

## Regular archive retention (2026-09-25 follow-up)

LLVM's [archive format documentation](https://releases.llvm.org/6.0.0/docs/CommandGuide/llvm-ar.html#file-format) describes the eight-byte `!<arch>\n` magic, 60-byte member headers, decimal member lengths and even-byte padding. Current LLVM [archive definitions](https://llvm.org/doxygen/include_2llvm_2Object_2Archive_8h_source.html) distinguish that magic from `!<thin>\n`. GNU [ar documentation](https://sourceware.org/binutils/docs/binutils/ar.html) explains that a thin archive references original member files, so moving its bytes alone into an immutable CAS does not retain the inputs needed to link. The scheduler's pure-Simple archive adapter therefore admits bounded, complete regular archives and refuses thin archives. Its format check establishes self-containment and parse bounds; content digest and accepted-manifest checks establish byte identity, while a real linker consumer still needs qualification.
