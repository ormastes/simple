## Item 2 — root cause: one non-ASCII codepoint disabled the measured wrap

Not flex/grid sizing, `gap`, `align-items` or `box-sizing`, all of which the
round-16 brief listed as candidates. Histogramming `css-layout`'s root rows
showed `dx=0, dw=0` everywhere and a pure vertical `dy` ladder in steps of 24
(one line box), generated by `<li>` rows carrying `dh=24`. The minimal fixture
isolated the trigger to a single character:

| 728 px block, 16px/1.5 sans-serif | Chrome | Simple before |
|---|---|---|
| `<code>…</code> — partial; values=…; owner=…spl` | 48 | 72 |
| `<code>…</code> xx partial; values=…; owner=…spl` | 48 | 48 |

The em dash, not the `<code>` element. Two defects, one substrate cause — this
engine's text API is mixed: `len()`/`substring()` are BYTE-indexed while
`char_code_at()`/`char_at()` are CODEPOINT-indexed.

1. The wrap gated the measured-advance path on
   `resolved_font_advances.len() != txt.len()` — a codepoint count against a
   byte count — so one em dash dropped the whole run onto the flat
   cells-per-line estimate (12 px/char vs a real ~7.8), which wraps ~50 % too
   early. (`…_layout.spl` `_lay_compute_style_wrap_ranges_inner`:1158 and its
   float-band twin :1080.)
2. `style_run_byte_advances`, the byte-indexed table that exists to answer this,
   was itself dead on non-ASCII: it classified `char_code_at(i)` as a UTF-8 lead
   or continuation byte, but `char_code_at` decodes and never returns 128..191,
   so it over-ran the advance array and returned an EMPTY table.
   (`…_layout.spl` `_lay_style_run_byte_advances_inner`:496.)

(2) hid (1) — fixing the guard alone changed nothing, which is the measurement
that named the second defect.

Fix: expand codepoints to bytes from the codepoint VALUES (`utf8_encoded_len`,
fail-closed against the byte length); gate both wrap loops on the byte table;
test for a space through `txt.bytes()` (the space test carried the same mix, so
breaks landed some bytes away from the space they meant to break at); force
progress through `next_codepoint_start`. `fb_text_thin_scaled_clip_range_adv`
(`…_paint_primitives.spl`:1221) needed its own codepoint cursor — that loop's
byte/codepoint mix had been unreachable only because the table was always empty.

Full record, incl. the falsified `<code>`-element and continuation-width
hypotheses and the raw probe of the text API:
`doc/08_tracking/bug/web_non_ascii_run_wrap_falls_back_to_flat_estimate_2026-09-14.md`.

Spec: `test/01_unit/browser_engine/non_ascii_run_wrap_byte_advances_spec.spl`,
6/6, each defect sabotage-proven separately, with the ASCII twin as a control
that must NOT move.

### Why `css-layout`'s COUNT rose while its geometry improved

Its root `dy` maximum falls from **697 px to 169 px** — a four-fold reduction in
real drift. The over-wide estimate had been compensating, in the opposite
direction, for a *second* defect that is now uncovered: a `#text` node that
starts at a non-zero pen x is wrapped independently against the FULL container
width, so an inline sibling before it (`<code>`, `<span>`) does not narrow the
first line. Measured on the `<li>` fixture, Chrome 88 px, Simple 64 px — now one
line SHORT where it used to be one line long. More elements land within a line
of Chrome and therefore mismatch by a small amount instead of a large one. This
is named and filed, not papered over; it is the next round's dominant cluster.

## Item 1 — the `<body>` collapse premise does not hold on these pages

The brief predicted that the outer `<ul>` fails to collapse out of `<body>`
(Chrome y=0, Simple y=16) and that fixing it would shift every page's first
block up 16 px. Measured instead:

- Chrome, bare fixture with `body{margin:0}`: `html y=0 h=84 ; body y=16 ;
  ul y=16 ; p y=50`. The first child's margin DOES collapse through `body`,
  moving body's own border box to 16 — the `<ul>` is flush with body's content
  top, not at 0.
- Run A, the catalog pages: the `path:` (`body`) row is `dx=0 dy=0` on both
  `html` and `css-layout`. There is no 16 px body offset to fix.

`node_tag_is_document` still excludes `body` from top-margin collapse-through,
which is not what CSS 2.1 §8.3.1 says; but with `dy=0` on every page there is no
measurement supporting a change, so it was NOT touched. Recorded here rather
than acted on.
