# Contributing Translations

Thank you for your interest in translating Simple compiler error messages!

## Overview

Simple uses a catalog-based i18n system where error messages are stored in `.spl` files organized by domain and language.

## File Structure

```
src/i18n/
├── __init__.spl          # English UI strings (severity names)
├── __init__.ko.spl       # Korean UI strings
├── parser.spl            # English parser errors (E0001-E0012)
├── parser.ko.spl         # Korean parser errors
├── compiler.spl          # English compiler errors (E1xxx-E3xxx)
├── compiler.ko.spl       # Korean compiler errors
└── [lang]/               # Future: directory per language
```

## Adding a New Language

### Step 1: Copy Existing Catalogs

Copy the English catalogs and rename with your language code:

```bash
# For Japanese (ja)
cp src/i18n/__init__.spl src/i18n/__init__.ja.spl
cp src/i18n/parser.spl src/i18n/parser.ja.spl
cp src/i18n/compiler.spl src/i18n/compiler.ja.spl
```

### Step 2: Translate Messages

Edit the copied files and translate all messages:

**Before** (`__init__.spl`):
```simple
val severity = {
    "error": "error",
    "warning": "warning",
    "info": "info"
}
```

**After** (`__init__.ja.spl`):
```simple
val severity = {
    "error": "エラー",
    "warning": "警告",
    "info": "情報"
}
```

### Step 3: Test Your Translation

```bash
# Test with your language
simple build test_file.spl --lang ja

# Verify error messages appear in your language
```

### Step 4: Submit Pull Request

1. Fork the repository
2. Create a feature branch: `git checkout -b i18n-japanese`
3. Commit your translations: `git commit -m "Add Japanese translations"`
4. Push and create PR

## Translation Guidelines

### 1. Preserve Placeholders

Keep all `{placeholder}` markers unchanged:

**✅ Correct**:
```text
"message": "{expected}を予期しましたが、{found}が見つかりました"
```

**❌ Incorrect**:
```text
"message": "expectedを予期しましたが、foundが見つかりました"
```

### 2. Maintain Tone

- Use **formal/polite** tone
- Be **clear and concise**
- Avoid slang or colloquialisms

**Good**: "この範囲で変数を見つけることができません"
**Bad**: "変数がないよ"

### 3. Technical Terms

Some terms should remain in English or use standard translations:

| English | Korean | Japanese | Notes |
|---------|--------|----------|-------|
| identifier | 식별자 | 識別子 | Translate |
| token | 토큰 | トークン | Keep English or transliterate |
| function | 함수 | 関数 | Translate |
| variable | 변수 | 変数 | Translate |

### 4. Grammar Particles (Language-Specific)

**Korean**: Use neutral particles when subject is unknown:
- "을(를)" instead of just "을" or "를"
- "이(가)" instead of just "이" or "가"

**Japanese**: Use appropriate particles:
- "を" for objects
- "が" for subjects

## Message Structure

Each error message has these fields:

```text
"E0001": {
    "id": "E0001",                    # Error code (DO NOT TRANSLATE)
    "title": "Error Title",           # Short title
    "message": "Full message {var}",  # Main message with placeholders
    "label": "Label text",            # Optional: code label
    "help": "Help text",              # Optional: suggestion
    "note": "Additional note"         # Optional: extra info
}
```

### Required Fields

- `id`: Error code (always keep in English)
- `title`: Short error title
- `message`: Main error message

### Optional Fields

Only include if present in the English version:
- `label`: Text for code labels
- `help`: Helpful suggestions
- `note`: Additional information

## Testing Checklist

Before submitting:

- [ ] All placeholders preserved (e.g., `{expected}`, `{found}`)
- [ ] No syntax errors in `.spl` files
- [ ] Tested with `simple build --lang [code]`
- [ ] All error codes covered
- [ ] Consistent terminology throughout
- [ ] Native speaker review (if possible)

## Quality Standards

### Completeness

Translate **all** error messages in a domain:
- ✅ All parser errors (E0001-E0012)
- ✅ All compiler errors (E1001-E3005)
- ✅ All UI strings (__init__.spl)

### Consistency

Use the same translation for recurring terms:
- "expected" → Always use the same word
- "found" → Always use the same word
- "type" → Always use the same word

### Cultural Appropriateness

Consider cultural context:
- Date/time formats
- Number formats
- Measurement units

## Review Process

1. **Initial Review**: Maintainers check for completeness
2. **Native Speaker Review**: If possible, native speaker verification
3. **Testing**: Automated tests ensure catalogs load correctly
4. **Merge**: Approved translations are merged
