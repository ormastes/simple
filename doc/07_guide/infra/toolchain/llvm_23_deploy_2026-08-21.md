# LLVM/clang 23.1.0 deployment (2026-08-21)

Deploys LLVM/clang 23 on this host and pins the repo's C compiler, C++ compiler
and native linker to it, with LLVM 20 kept as an explicit fallback.

## What is installed

| Tool | Version | Path |
|---|---|---|
| `clang-23` / `clang++-23` | `23.1.0` | `/mnt/data/toolchains/llvm-23-root/usr/bin/` |
| `ld.lld-23` | `LLD 23.1.0` | same |
| `llvm-config-23` | `23.1.0` | same |

Exact apt version string, as published by `apt.llvm.org` for `noble`:

```
1:23.1.0~++20260818083557+55feb0a3b6b7-1~exp1~20260818083714.47
```

**This is a 23.1.0 snapshot, not a final 23.1.0 release tarball.** The `~++`
suffix marks it as apt.llvm.org's automated build of the release branch at
commit `55feb0a3b6b7`, dated 2026-08-18. It self-identifies as
`Ubuntu clang version 23.1.0`. It is genuinely 23.1, not 23.0 and not a
`-snapshot` (trunk) build: the `llvm-toolchain-noble-23` suite is the branch
suite, and `llvm-toolchain-noble-snapshot` is the separate trunk one. There was
no need to fall back to 22 or 21 — both also exist upstream and were not used.

17 packages were deployed: `clang-23`, `clang-tools-23`, `lld-23`, `llvm-23`,
`llvm-23-dev`, `llvm-23-runtime`, `llvm-23-linker-tools`, `llvm-23-tools`,
`libllvm23`, `libclang1-23`, `libclang-cpp23`, `libclang-23-dev`,
`libclang-common-23-dev`, `libclang-rt-23-dev`, `libpolly-23-dev`,
`libc++-23-dev`, `libc++abi-23-dev` (185 MB of `.deb`).

## Why it is not a root install

This host has **no passwordless sudo** (`sudo -n true` -> "a password is
required"), so `apt-get install` is not available to an unattended session, and
neither is adding the `llvm-toolchain-noble-23` line to
`/etc/apt/sources.list.d/` (only the `-18` and `-20` suites are configured
there).

The packages were therefore fetched directly from the apt pool and unpacked
with `dpkg-deb -x` into a private prefix:

```
/mnt/data/toolchains/llvm-23-debs/   # the .deb files
/mnt/data/toolchains/llvm-23-root/   # the extracted tree
```

This is a real, complete toolchain rather than a workaround with caveats: clang
locates its resource directory (`lib/clang/23/`) relative to its own
executable, so an extracted tree behaves identically to an installed one. It
picks up glibc headers, the GCC 13 runtime and crt files from the system as
usual. The Debian `/usr/bin/*-23` symlinks are relative (`../lib/llvm-23/bin/`)
and so resolve correctly inside the prefix. A later root install of the same
packages needs no change here — the env script finds `clang-23` on `PATH`
either way, and `SIMPLE_LLVM_ROOT` simply stops mattering.

Reproduce (no root, ~185 MB download):

```sh
# fetch the pool files listed in binary-amd64/Packages.gz for
# http://apt.llvm.org/noble/dists/llvm-toolchain-noble-23/main/
for d in /mnt/data/toolchains/llvm-23-debs/*.deb; do
  dpkg-deb -x "$d" /mnt/data/toolchains/llvm-23-root
done
```

## How the repo uses it

`scripts/setup/llvm-toolchain-env.shs` is the single wiring point. **Source it,
do not run it:**

```sh
. scripts/setup/llvm-toolchain-env.shs
```

It exports `CC=clang-23`, `CXX=clang++-23`, `LD`/`SIMPLE_LLD=ld.lld-23`,
`LLVM_CONFIG=llvm-config-23`, `LLVM_SYS_231_PREFIX`, and `SIMPLE_LLVM_MAJOR=23`;
it prepends both `usr/lib/llvm-23/bin` (unsuffixed names) and `usr/bin`
(suffixed names) to `PATH`.

Preference order is 23, then 20, then nothing. `SIMPLE_LLVM_VERSION=20`
forces the fallback, verified to yield `CC=clang-20 LD=ld.lld-20`. If no
versioned clang exists at all the script says so on stderr and leaves `CC`
unset rather than guessing.

### Why the unsuffixed bin dir is on PATH

Setting `CC` alone is **not** sufficient, and finding that out is the main
non-obvious result of this work. The seed's native link step chooses its linker
by probing `PATH` for a bare `ld.lld`:

```
src/compiler_rust/compiler/src/pipeline/native_project/linker.rs:1972  // use_direct_lld
    ["ld.lld", "/opt/homebrew/bin/ld.lld", "/usr/local/bin/ld.lld"]
```

That decision never consults `$CC`, `$LD` or `$SIMPLE_LLD`. With only the
suffixed dir on `PATH` the C compiler was 23 while the actual link still ran the
host's bare `ld.lld` 18 — measured, `readelf -p .comment` on the first
hello-world read `Linker: Ubuntu LLD 18.1.8`. Ordering the unsuffixed dir ahead
of `/usr/bin` fixes it without touching Rust source (that file is owned by
another lane) and is the no-root equivalent of `update-alternatives`, scoped to
shells that opt in.

The C-compiler side needs no such trick: `detect_c_compiler_for_target`
(`src/compiler_rust/common/src/platform/cc_detect.rs:43`) reads `CC` before any
probing, and `scripts/check/check-c-runtime-compiles-push.shs`'s `detect_cc()`
does the same, so both honour the export directly.

## Evidence

**1. C runtime syntax gate — zero new diagnostics vs clang-20.** Both runs are
byte-identical in outcome:

```
CC=clang-23  FAIL — 1 file(s) failed to compile: src/runtime/test/rt_browser_renderer_namespace_selfcheck.c (108 compiled clean, 2 skipped)
CC=clang     FAIL — 1 file(s) failed to compile: src/runtime/test/rt_browser_renderer_namespace_selfcheck.c (108 compiled clean, 2 skipped)
```

Same file, same two errors (`call to undeclared function
'browser_renderer_apply_namespaces'` / `'browser_renderer_drop_privileges'` at
`rt_browser_renderer_namespace_selfcheck.c:55` and `:57`), same 108 clean, same
2 external-SDK skips. **This failure is pre-existing and is not caused by
clang-23** — it reproduces identically on clang-20 and is a missing declaration
in repo source, not a build-flag issue, so it was left alone (that path is owned
by another lane). clang 23 introduced **no** new errors and no new warnings
across the 108 files that do compile.

**2. Full C runtime builds under clang-23.** `cargo build --release -p
simple-runtime` with `CC=clang-23` succeeded (rc=0) and every object in the
resulting 1.9 MB archive is stamped 23:

```
$ readelf -p .comment .../out/libruntime_sffi_c.a
  Ubuntu clang version 23.1.0 (++20260818083557+55feb0a3b6b7-...)
```

**3. Rust seed still builds.** `cargo check --release --bin simple` with clang
23 first on `PATH`: rc=0, finished in 1m14s, 3 pre-existing warnings and no new
ones.

**4. hello-world `native-build` links with LLVM 23.**

```
$ . scripts/setup/llvm-toolchain-env.shs
$ bin/simple native-build hello.spl -o hello23     # rc=0
$ ./hello23                                        # "hello 23", rc=0
$ readelf -p .comment hello23
  Linker: Ubuntu LLD 23.1.0
  Ubuntu clang version 20.1.8 (...)
  GCC: (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0
```

The link is LLD 23.1.0. The clang 20.1.8 line is **not** a failure of the pin:
it comes from the pre-built `build/simple-core/libsimple_runtime.a`, which was
compiled by another session at 06:18 before this change. That archive was
deliberately not rebuilt in place, because it is a shared artifact that other
running lanes link against. It picks up clang-23 on its next rebuild
automatically — the `cc` crate in `src/compiler_rust/runtime/build.rs` honours
`$CC`, which is exactly what evidence item 2 demonstrates in a private target
dir.

## Not on 23, and why

**The Rust seed's LLVM backend stays on LLVM 18.** `src/compiler_rust/compiler/
Cargo.toml:123` pins `inkwell = { version = "0.5", features = ["llvm18-0"] }`
behind the optional `llvm` feature. **inkwell has no LLVM 23 support at any
published version:** inkwell 0.10.0, the latest release, offers features up to
`llvm22-1` only (`llvm15-0`, `llvm16-0`, `llvm17-0`, `llvm18-1`, `llvm19-1`,
`llvm20-1`, `llvm21-1`, `llvm22-1`), and the underlying `llvm-sys` has only
`231.0.0-rc2` — a release candidate — for LLVM 23. Bumping the feature would
simply fail to resolve, so the pin was left untouched and `cargo check` was run
against the existing configuration instead. The env script already exports
`LLVM_SYS_231_PREFIX`, so the day inkwell publishes an `llvm23-*` feature over a
stable `llvm-sys` 231 the change is a one-line feature edit with no env work.

**No system-wide `update-alternatives`.** It needs root, which is unavailable
here. The `PATH` ordering in the env script gives the same result for opt-in
shells, and has the advantage of being reversible and invisible to anything that
does not source it — worth preferring even where root exists, since bare `clang`
is shared with every other user of the machine.
