# Addendum — two corrections to the design, 2026-09-06

Recorded here rather than silently amending `doc/05_design/infra/local_ci_receipt/design.md`,
which shipped in #415; fold these in when that PR is next touched.

## A. Base-only reads are NOT delivered by the landed implementation

Design §9.1 promises the allowed-signers file, the verifier and the skip logic are read from the
BASE ref so a PR cannot ship its own trust root or edit the gate deciding to skip.

**The implementation does not deliver this**, and the reason recorded in #416's body —
"`pull_request_target` is not usable because this job must execute head content" — is **false**.
`pull_request_target` evaluates BASE workflow YAML and can still check out head content
explicitly:

```yaml
on: pull_request_target
...
      - uses: actions/checkout@v4
        with: { ref: '${{ github.event.pull_request.head.sha }}' }
```

The gates need no secrets, so the usual `pull_request_target` hazard (secret exposure to
untrusted head code) does not apply to them.

What actually shipped is a `pull_request` job whose mitigation — refuse admission when the PR
touches `.github/workflows/`, `scripts/check/`, `scripts/hooks/` or `config/check/` — is itself
evaluated by head-controlled YAML, so it protects nothing against a PR that edits that YAML.

**Fair framing, so this is neither overstated nor waved away:** this is not a regression. Every
`pull_request` workflow producing a required check in this repo already trusts head YAML today,
and the receipt path is no worse than the status quo it replaces. But the design promised
better and the code does not deliver it, so the promise is downgraded to advisory until the
admission decision moves to a `pull_request_target` job with an explicit head checkout.
That move is the recommended follow-up and is small.

**Resolved 2026-09-24 (split design).** The decision and the gates now live in two workflows:

- `.github/workflows/code-idiom-receipt.yml` — `pull_request_target` (types
  `[opened, synchronize, reopened]`, PRs into `main` only), `permissions: {contents: read,
  pull-requests: read}`, no secrets, **no checkout and no head script**: the head is fetched
  blobless as git objects into a private repo under `RUNNER_TEMP`, the verifier, allowed-signers
  file and manifest come from `git show <BASE_SHA>:…`, and the decision (`mode`, `skip_ids`,
  attested `tree`, `docs_only`, bound to pr / head sha / base sha / base ref) is uploaded as
  artifact `receipt-decision-<head sha>`.
- `.github/workflows/code-idiom-gates.yml` — `pull_request`, runs the head's gate scripts with
  only the PR's own Actions cache scope. It imports the decision only from a run the API reports
  as `event=pull_request_target`, `path=.github/workflows/code-idiom-receipt.yml`,
  `completed/success`, whose fields match its own payload and whose `tree` equals the tree it
  checked out; anything else is `full`.

An intermediate version (single `pull_request_target` job running the head's gate scripts) was
rejected in review: head code in a base-context job can write main's Actions cache
("Cacheract"), which `release.yml` restores. The split removes that. The policy refusal now uses
`git diff --no-renames` and also refuses `scripts/lib/` and `scripts/setup/`; the docs-only
predicate accepts only `doc/**`, root `*.md` and root `README`/`LICENSE`. D8 kill switch:
repository variable `SIMPLE_CI_RECEIPT_DISABLED` set to anything other than `false` forces
`full` on the next run. Honest limit: the gate job's YAML is still the PR head's (as for every
`pull_request` workflow), so a PR that edits it can drop its own gates; what the split
guarantees is that the skip authority can no longer be produced or widened by head content.

## B. pq script signing — evaluated, rejected for this use

`scripts/trust/{keygen-pq,sign-script,verify-script}.shs` with the pure-Simple verifier twin
`src/lib/nogc_sync_mut/trust/script_signature.spl` (`wots-merkle-sha256-w16-h8`) was a serious
candidate and is arguably more repo-native than sshsig: SHA-256 only (no OpenSSH floor), a
pure-Simple verifier that already exists, and post-quantum.

Measured 2026-09-06: keygen minutes (256 leaves, 8 workers); sign **7 s**; verify **4 s** with
`--no-selftest` (an earlier 45 s figure wrongly included `--selftest`); tampered payload
correctly `FAIL — root mismatch`.

**Speed is not why it was rejected.** It is a *stateful one-time* signature scheme:
`max_signatures=256`, each signature consumes a leaf, and reusing a leaf is a real
cryptographic break. Leaf state is a single directory. This receipt is re-signed on every
rebase (~9/day/PR under the up-to-date ruleset) from up to 9 concurrent agent sessions, so
cross-session leaf collision is a realistic failure mode and a key is exhausted in weeks. The
scheme was built for occasional script signing and fits that well; per-rebase CI receipts are
the wrong shape for it.

The pure-Simple *verifier* story stands as future work either way — see the design's §13.
Note its shell verifier already runs on a CI runner today; the blocker is the state model,
not the language.
