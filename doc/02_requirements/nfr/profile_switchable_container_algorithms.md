# Profile-switchable container nonfunctional requirements

**Scope:** [feature requirements](../feature/profile_switchable_container_algorithms.md). Operation counts, not shared-host wall time alone, are the primary evidence, following collection planner research §19–20.

- **NFR-PSC-001 — Semantic stability:** Transitions and profile admission shall preserve the same result, order contract, side-effect trace, and error result as the unoptimized operation on every supported engine. Verify with differential execution over empty, singleton, duplicate, colliding, and mutating cases.
- **NFR-PSC-002 — Complexity:** Linear membership compares at most `n` keys. Hash membership is measured for probes and collisions and is never selected where the policy requires a deterministic worst-case bound. Ordered membership requires at most logarithmic key comparisons; ordered construction and updates must have a stated, measured bound. Verify at `n`, `2n`, `4n`, `8n` with comparison/probe counters.
- **NFR-PSC-003 — Profile isolation:** Hot lookup/insert/remove paths perform no file open, shell command, repo scan, or global profile search. The app loader admits at most 100,000 samples, rejects duplicate sample IDs, and computes p95 from the admitted samples. Verify with instrumented process/file facades and a 100,001-sample rejection test.
- **NFR-PSC-004 — Compilation cost:** Default CollectionPlan analysis remains one local HIR traversal plus bounded candidates, with cached summaries and affected-SCC propagation. Verify compiler operation counts and cache invalidation on representative projects.
- **NFR-PSC-005 — Resource evidence:** Report allocations, copied bytes, peak RSS, and warm operation latency for each representation and transition on realistic fixtures. No release PASS is possible without a reviewed memory/latency target and measured result for each supported target profile.

**Current state:** These are acceptance targets, not PASS claims. The ordered text-set now uses an AVL tree, and the generic ordered map exposes comparison counts from its real lookup and update paths. The four adaptive families expose counts from their forced-linear lookup paths and emit hash probes/collisions through the bounded capture path. Geometric-size ordered, linear, and hash perf cases exist but have not run. The profile loader can prepare set and named-metric indexes; the compiler optimizer does not yet consume them. Measured memory and latency bounds, adversarial hash cases, and native execution remain open. A 100,001-sample rejection integration spec exists but has not run.
