# Caret shared multiplexer and TUI extension requirements

Selected by user: option A, 2026-10-25. NFR profile: N2. Target branch: release/1.0.0. Selection does not establish implementation or qualification.

- REQ-CMUX-001: One backend-neutral CoreMux interface shall operate real smux and tmux sessions, windows and panes through Sosix host owners. Actual Caret workflows and the audited command/format contracts in doc/09_report/caret_smux_compatibility_2026-10-25.md remain mandatory.
- REQ-CMUX-002: Core operations shall include background session creation, discovery, attach/detach, rename/termination, independent server namespaces, and owned child cleanup. Closing a client/dashboard shall not terminate independent background sessions. Unknown/ambiguous targets shall fail without choosing another object.
- REQ-CMUX-003: Pane launch shall preserve argv, cwd, environment, real child identity and output. Literal input, named keys, paste, shell commands and user notifications shall be distinct operations. Cross-session targeting shall not change unrelated focus or leak output.
- REQ-CMUX-004: Mandatory geometry operations shall support directional and nested splits, pane/window focus, required layouts, resize, zoom/restore, multiple windows and multiple clients, including child-observed dimensions and stable identity. Failed mutations shall preserve prior geometry or return explicit partial state. Caret title, border, hide/show and rebalance workflows in the audited matrix are mandatory; their presentation category does not make them optional.
- REQ-CMUX-005: Capture shall preserve requested history, wrapping/join semantics, plain versus styled output, Unicode cell boundaries and exact required tmux formats. Exited/hidden objects shall have declared lifecycle/listing semantics, not fabricated IDs or success.
- REQ-CMUX-006: Capability discovery shall describe per-operation native/emulated/unavailable support, limits, backend/version/owner generation, constraints and separate execution-evidence status. Operations shall still validate at invocation. Required missing features block usable-replacement qualification.
- REQ-CMUX-007: Optional TerminalLayoutV1 shall expose stronger revisioned complete-plan/multi-pane operations beyond the mandatory Caret commands. Optional TerminalPresentationV1 shall expose additional terminal-cell overlays/input routing beyond required messaging. Acquisition and operations shall return typed unsupported results when absent; no silent mutation, no-op success or automatic backend migration.
- REQ-CMUX-008: Core and optional operations shall distinguish Unsupported, InvalidRequest, InvalidTarget, PermissionDenied, Unavailable, StaleRevision, Busy, Timeout and PartialFailure. Retry behavior shall depend on outcome/commit evidence. A timeout with unknown commit shall be reconciled before retrying a non-idempotent operation.
- REQ-CMUX-009: Caret semantic widgets shall reuse the established Simple shared UI contract. Terminal extensions own cell geometry and host presentation, not a new GUI/web/WM/widget system. Running Caret's ordinary TUI as a pane child shall remain usable on both backends.
- REQ-CMUX-010: Every required workflow shall have production-connected modern SSpec coverage and actual backend execution evidence. Shared semantic contracts, legacy caller compatibility and optional backend suites are separate. Source models, parsed command strings, test discovery and unexecuted specimens shall not count as native feature support.
- REQ-CMUX-011: The current compiler instruction is Phase3-only producer use/rebuild; do not rebuild Phase2. Verify actual generation/runtime/Hello lineage before smux compilation; use the matching full CLI or standalone runner for SSpec/docgen claims. Land only reviewed, qualified changes through a PR to release/1.0.0.
- REQ-CMUX-012: Integration and system-test scope shall include the full Caret suite, IDE integration and every application using the shared pane/multiplexer API. Retain an authoritative production caller inventory, including shared library families and selected/dynamic adapters. Each caller shall be covered by a production-connected modern SSpec workflow using actual processes, terminals, layouts, messaging and owned cleanup as applicable. Execute with the verified compiler/runtime; retain failing and passing cases, blocked/unrun counts, exact commands and artifacts. Repair failures and rerun affected criteria within the finite attempt budget. Authored tests, source models and discovery-only checks never count as application or backend passes.
