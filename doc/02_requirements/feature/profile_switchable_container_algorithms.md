# Profile-based switchable container algorithms

**Selection:** The user requested full implementation of item 7. This requirement set instantiates P6 of [the collection planner research](../../01_research/compiler/collection_planner/collection_plan_ir_2026-07-31.md) and the explicit per-container attribute and feedback request.

## Functional requirements

- **REQ-PSC-001 — Per-container attribute.** A source-level attribute on each eligible container declaration shall select `auto`, `linear`, `hash`, or a worst-case-bounded ordered implementation. Changing one container's attribute shall change that container's physical representation without changing another instance or its logical contents.
- **REQ-PSC-002 — Runtime equivalence.** Lookup, insert, remove, length, iteration, and clear shall have the same observable set/map semantics across representations and after every transition. Unsupported key/equality types shall fail clearly rather than silently select an unsound implementation.
- **REQ-PSC-003 — Measured load.** Collection sites shall record stable AST identity, target profile, cardinality, lookup count and hit/miss distribution. Compiler-selected plans shall also record the P6 collection/join metrics listed in research §12 where applicable.
- **REQ-PSC-004 — Persisted feedback.** `.sprof` v2 shall retain collection measurements alongside existing function/block/edge counters. Loading shall reject incompatible schema, module, workload, target, corrupt records, and duplicate sample identities. Distinct samples for the same site shall contribute to a measured distribution. The hot path shall consume an already-loaded profile without file opens or repo scans.
- **REQ-PSC-005 — Guarded selection.** The planner shall select a physical algorithm from proven semantics, available target capabilities, explicit attribute, policy level, and measured workload. Profile data may affect cost estimates but may not relax effect, order, duplicate, ownership, or worst-case complexity obligations.
- **REQ-PSC-006 — Explainability.** `simple optimize --explain-collection-plan` shall identify the selected algorithm, static and profile evidence, rejected alternatives, guards, extra memory, and any fallbacks.
- **REQ-PSC-007 — Scope.** The implementation shall cover the supported set and map key types and typed collection operations declared by the collection planner, not only a text-set helper. Nested/hash/merge choices shall become available after the P0 correctness gates in the research are met.
- **REQ-PSC-008 — Cross-backend proof.** Interpreter and native tests shall prove semantic equivalence and profile/attribute behavior; performance tests shall verify the relevant scaling and memory targets before production readiness.

## Current evidence boundary

Attribute-switch identity follow-up: parser site hashes now exclude the `@collection_algorithm` text for both locals and fields. `.sprof` source identity canonicalizes only valid algorithm tokens through lexer ranges and uses a new `source-fnv64-collection-v2` prefix. This permits exact-site feedback across an algorithm switch after regenerating the profile under the new identity; it does not admit arbitrary source edits. The source-level cases are not yet run on an admitted source-matched runner.

The `AdaptiveTextSet` and `AdaptiveTextMap` implementations, flat-parser `@collection_algorithm` rewrites for locals and fields, `sprof_collection_profile` bridge, and advisory `collection_plan_selection` model are initial slices of REQ-PSC-001, -003, -004, and -005. The text set and map have per-instance linear/hash/AVL-ordered storage, deterministic interim site IDs, collection workload p95, validated named P6 metric records with distribution summaries, and a fail-closed candidate selector. Interim parser site IDs no longer depend on byte offsets and include enclosing function/class names where parsed; identical locals within one owner use ordinals. Complete lexical owner identity and whole-module edit-tolerant profile admission remain open. Generic `OrderedMap<K,V>`, `AdaptiveMap<K,V>`, and `AdaptiveSet<K>` source now covers `Hash + Eq + Ord` keys, but its parser, native, and cross-engine behavior is unverified. Both parsers route known direct constructors and explicitly typed factory initializers; a conflicting direct-constructor family is rejected, while factory return type validation remains a typed-compiler obligation. Direct callers can install a target-specific runtime feedback catalog. `simple run` now admits a profile before parsing and embeds an exact-site hint in each matching attributed initializer; it bypasses cached SMF and frontend parse results for that run. The full path remains unverified. The attribute paths, ordered backing, and named metrics have no executable proof yet. The advisory decision now records linear, hash, and ordered rejections for explanation, but no CLI explains the selected runtime instance. Typed AST site identity and automatic dependency-closure/target identity, full P6 metric instrumentation, full generic key/value coverage, planner-to-MIR integration, and REQ-PSC-006 through -008 remain unfinished.

Target-specific feedback installation now rejects a loaded envelope with no collection sample for the requested target. This permits a multi-target profile while making an absent target an admission failure; unit and CLI cases await the pure-Simple runner.

The opt-in capture channel now emits `materialization_count` for public set/map snapshots alongside size, lookup, and final distinct-key metrics. The channel and loader remain bounded at 100000 total collection/metric records, but the new four-metric Simple integration path has not run on an admitted source-matched runner. Other applicable P6 metrics and planner-to-MIR feedback remain open.

Text and generic adaptive hash lookup paths now count inspected probes and nonmatching occupied slots/entries during the lookup and emit `hash_probe_count` and `hash_collision_count`. A hash lookup miss counts the final empty probe; a full set table counts all occupied slots. The capture cap is 14285 sites so one collection record plus at most six metric records per site remains below the 100000-record loader limit. Sites without observed hash lookups omit both hash metrics rather than reporting unmeasured probes as zero. The Linux C runtime selfcheck passes against the full current `runtime_native.c`. The text and generic Simple unit and CLI integration specs for these two metrics are not yet executable on an admitted source-matched runner. Other P6 metrics and planner-to-MIR feedback remain open.
