# Linux output-follow owned launch

Status: IN_PROGRESS / UNEXECUTED. Source implementation and focused specifications; no native stream acceptance or Ready outcome is claimed.

The common stream facade delegates planning and opening to the Linux adapter. Planning validates the canonical workload request, strict retained V2 full native identity and current managed engine observation. It derives typed Podman attach argv through the approved absolute engine policy route, ending in `attach --no-stdin --sig-proxy=false FULL64ID`. There is no stdout reader, stdin/TTY/resize claim or host shell in the provider.

`output_session_v2.spl` constructs the canonical daemon V3 launch template. Helper CPU and memory are separately requested resources; the authenticated shared-broker budget is carried by the V3 profile. The supported image mode is explicitly `trusted-local-admin-image-fd-v1`, matching the mutable-path dynamic engine policy rather than claiming sealed execution. The canonical daemon serializer/digest is reused. Only transport generation and launch admission expiry normalize to zero; expiry is assigned from the separately admitted helper at open, and is never a running-stream lifetime cap.

The helper root is `policy.root + /output- + container_output_identity_digest_v2(identity)`, worker ID is the helper operation ID, and generation is the actual provider generation. The outer common request digest additionally binds workload plan, full target, parent operation/assignment/budget correlation, helper resources and policy/provider pins. A copied carrier does not create new launch authority: the canonical daemon exclusively creates the deterministic root's `broker.claim` before broker launch. Retrying the same signed identity cannot choose a new root. A new helper identity requires fresh outer Host admission.

At open, the adapter independently rederives the plan and validates the admitted helper carrier before handing down its deadline. The provider freshly recovers the already-qualified exact retained native ID and requires running plus every identity field before the native spawn. It never discovers this target by generated name and never creates or starts the workload. Scripted provider observations are explicitly barred from native spawn.

The actual boundary is `process_spawn_piped_owned_v2` with a V3 profile. Every outcome is returned intact: Ready owns both group owner and exact reference; CleanupRequired owns the group owner and optional reference even when handoff is uncertain; Rejected is a prelaunch refusal. The adapter/common facade does not collapse cleanup-bearing outcomes into text or retain a duplicate reference. The consumer must keep the whole owner bundle on adoption/close failure and use canonical owned cleanup/reap; no raw PID fallback exists. Ready is ownership availability, not successful attach/output evidence.

Seven authored unit scenarios cover real common planning, independent absolute argv/root/resource vectors, daemon normalization, correlated demand changes, invalid modes/parents/IDs/policy/resources, full scope/engine mismatch, and fresh scripted recovery with explicit native-spawn refusal. The common-open negative case uses the real Host fixture's request/receipt with explicit structural alignment, confirms structural matching only, then corrupts plan/resources/operation/receipt/deadline independently; every common open must reject before another executor attempt. The unchanged structural carrier is never submitted as verified launch authority. These specifications are UNEXECUTED. Native exact-group transfer, Ready/CleanupRequired, cleanup/reap, durable duplicate-claim and actual output-follow acceptance remain required integration evidence using the real daemon and verified Host helper lease. No fake lease or process reference is constructed as proof.

Dependencies are the canonical daemon V3 stream protocol/profile/process owner and common stream/Host helper admission modules. This slice does not implement consumer reading, terminal features or wire transport of process authority.

The trusted helper carrier retains the original `HostReservationIntentV1`. Structural validation matches its plan digest to the canonical helper plan, its host/scope/fence and CPU/memory to the output demand, and its canonical payload to the original operation using the Host codec. It then matches the full prepared receipt. The operation payload digest is an intent hash, not a helper-plan hash; comparing those domains directly would reject genuine leases. Host signature verification and durable admission remain prerequisites, and copying the carrier confers no second launch.
