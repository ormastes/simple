# Container configuration observation V1

The existing Simple Container API owns the observation. `simple_container_configuration_observe_v1(owner, original_request)` returns the updated owner on success and refusal. It adds the read action `configuration`; it does not accept caller-authored query strings, native IDs, command results or observation DTOs as evidence.

Each adapter first checks the original immutable plan/request and its existing ownership/current-policy rules. The retained runtime uses its existing executor for three bounded captures: container configuration, the exact observed image/config ID, then the same container configuration. Query kinds and Go templates are trusted constants; only a validated full native ID or observed image/config ID enters typed argv. There is no shell. Linux keeps its installed routing and observation checks; Windows keeps its installed endpoint, explicit clean child environment and existing engine/current-container guard.

The strict JSON parser rejects duplicate keys, unknown/missing fields, nesting beyond three, source above 1 MiB, NUL text, text above 65536 bytes, more than 512 argv/environment entries, more than 256 repository digests, or more than 64 mounts. Engine policy capture limits may be smaller and refuse earlier. Arrays retain order. Environment values, including duplicates, are hashed as a canonical ordered SDN array. Public data exposes only ordered names and the digest; parser/native errors never quote raw query output or environment values.

The public record contains actual engine Path plus Args, working directory, configured user, actual ReadonlyRootfs, and every Mounts entry (kind/source/destination/read-only). It also contains the image-default environment digest/names. A repository manifest/index reference must appear exactly in the actual image RepoDigests; it is never compared directly to the image/config ID. Bare and sha256-prefixed engine config IDs are normalized only for config-ID comparison. Missing correspondence refuses observation. Engine normalization that changes the requested repository spelling can conservatively refuse.

Both container captures must have the expected full native ID and workload/attempt/operation/boot/provider-generation labels. Their selected configuration must encode identically. The snapshot digest is SHA256 of the canonical SDN record with its own digest field zeroed. Common API matching checks the returned runtime and original request digest/scope again. This detects configuration changes between the captures; it does not make the observation atomic or prove kernel execve, effective target mount namespace, future immutability, freshness or launch authority. Windows false ReadonlyRootfs is reported as false.

Container inspect is an engine configuration surface, not a complete kernel observation ([Podman documentation](https://docs.podman.io/en/stable/markdown/podman-container-inspect.1.html)). Registry digests and image configuration IDs have distinct semantics ([Docker Engine API history](https://docs.docker.com/reference/api/engine/version-history/)).

The separate `simple_container_logs_capture_v1(owner, original_request)` and `simple_container_logs_capture_step_v1(owner, capture, cancel=false)` use the genuine IO process-capture evidence owner. The opaque pending capture retains the original request, scope/runtime and actual lower process owner. Every turn returns the common owner; pending/error/cancel retains the native cleanup carrier while it exists. Only actual native retirement permits the final observation. This observation carries the opaque native evidence, with optional EOF/count/truncation fields left unavailable where the backend did not observe them. No legacy ProcessResult/CLI exit-zero value manufactures completeness.

The accepted IO R2 facade is Linux native main-thread-only: its genuine retained process-origin check runs before every canonical capture-registry access, including cleanup. Windows uses its canonical native thread. A wrong thread, fork or changed process namespace refuses; this API does not add a worker-thread fallback. The configuration read itself does not manufacture or broaden a capture capability.

The log command is exactly `logs <owned-full-native-ID>` with no tail, follow or filters. Linux uses its installed route and the same inherited trusted Host environment as its existing read executor; it makes no clean-environment claim. Windows uses the installed engine endpoint, SystemRoot/TEMP/TMP allowlist, system-root cwd, timeout/output bound and actual newly sampled deadline through the existing Windows command owner. The log query has no launch/admission authority. Both adapters apply existing immutable request/current ownership validation before begin. Native process cleanup can cancel through its retained actual lease even if the parent provider has died; it cannot start another child. A completed normal capture re-inspects the original runtime and rejects identity drift. Consumers still require a separate actual workload wait/exit result: native log-process EOF is not workload exit.

Scripted providers explicitly refuse actual capture evidence before starting the log child. This prevents a fixture result or caller DATA from becoming a fake EOF receipt. The exact IO R2 dependency passed independent source review (bundle `c288ddd322d661f7a49305deed245fbbad49bf26550ea82bfcc67871a48e5280`); integration still requires the combined source delta review. No executor, PTY or native export is added.

Seven authored source scenarios exercise the actual common API/scripted Windows owner and production parser. All are **NOT_RUN**. No native/runtime/compiler campaign or platform qualification was performed. Linux runtime forwarders preserve the historical oversized module; shared parsing stays in new bounded modules. Independent source review is required before landing.
