# Same-journal exec child resource barriers

Authored source design, NOT_RUN. This is a resource-settlement prerequisite. It does not prohibit separately signed parent stop/destroy, create a second ledger, observe live children or grant any native exec authority.

The read-only index walks at most4096 actual journal rows under the held writer. Every runtime-exec row is validated through the shared `host_runtime_exec_child_packet_v3`: exact child envelope/request, original parent reservation/payload, full retained V2 execution, creation identity and immutable observation provenance. Only then is parent ID trusted. Missing/corrupt provenance fails closed globally. All child state labels remain barriers until qualified no-effect or contained-child teardown evidence exists; none is inferred from a terminal string, deadline, running=false or parent object absence.

The validated packet helper is an extraction of existing child projection. Its boolean wrapper retains semantics. `host_runtime_exec_verify_v3` is the existing full SDK verifier renamed/exported without duplicate crypto; the ordinary producer uses the same function. Shared test parent/child composition is extracted from existing source cases.

Release gates: ordinary capacity projection builds one child map before its loop, skips child allocation only after that prepass, and rejects both completed-cleanup proof and cancelled-abort release while parent is blocked. Direct normal prepared abort/expiry invokes actual child guard before candidate release; each existing API handles ONE operation and builds one index, with no invented unused batch API. Helper releases remain their separately qualified path because exec children may bind only ordinary reservation parents.

`host_capacity_completion_evidence_owned_v2` is the actual journal-aware acceptance gate; root-only evidence decoding is receipt integrity data, not sufficient release authority. Direct settle and host_cleanup_settled use the gate. Actual cleanup entry/destroy/receipt publication remain unchanged: explicit signed destruction and positive parent absence can occur, and receipt is durably retained even when settlement returns recovery-required/charged. A valid parent absence receipt proves object lookup absence only, not contained exec/cgroup teardown.

Startup builds one `HostCapacityCompletionBatchV3` internally before its row loop. It holds a child barrier map and hash-only entries for fully validated canonical completed evidence (operation-envelope digest, outcome digest, evidence digest). Proof blobs are not retained per row. Each current completed row must still match all entry digests before release; no wire/caller batch is accepted. The existing sole writer/quarantine admits no callbacks/new children; intervening appends are only existing disjoint no-effect reservation cancellations, while completed targets/children stay immutable. Startup no-effect release also consults the barrier map. This avoids parents×children packet IO and GiB proof caches. No latency/RSS PASS is claimed; worst-case child/proof IO remains bounded by retained history and packet limits.

A child-bearing parent is kept charged on reopen even if historical cleanup wrote completed or cancelled. Unrelated sibling reservation may release through its own existing no-effect proof. No other parent/helper allocation or release proof body is rewritten. A separate exact no-Host-BEGIN cancellation receipt is the next liveness prerequisite; executing/unknown children require actual contained teardown proof. Lifecycle effects remain held until the respective owners close those conditions.

Source evidence: seven exact-step scenarios/manual. Native facts are explicitly scripted; actual SDK/WAL/private files/owned locks are used. Negative ordering-fault fixtures omit BEGIN intentionally and do not counterfeit Released flags or positive child teardown receipts.
