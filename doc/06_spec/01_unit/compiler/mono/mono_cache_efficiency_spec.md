# MonoCache persistence and capacity contract

Requirement REQ-MONO-CACHE-RESTORE-001 implements the existing generic formal hardening plan §7 loaded-count/capacity/eviction requirement. Executable owner: `test/01_unit/compiler/mono/mono_cache_efficiency_spec.spl`.

Eleven real API scenarios replace the old skipped-reason placeholder and commented obsolete fixtures. They use actual frontend lowering to obtain a typed HirFunction, the actual MonoCache store/save/load/evict owners, real SDN parsing and isolated host files. They assert saved metadata count and oldest-key restoration; last-duplicate-wins with unique cardinality; no neighbor eviction on replacement at capacity; exactly one eviction for new insertion at capacity; trusted 50,000-row acceptance and 50,001-row refusal; missing/malformed index fallback; ignored invalid keys; and disabled zero/negative-capacity stores. Advertised saved capacity/count are deliberately forged to prove they cannot grant admission.

Disk entries contain nil values. Restoring metadata is not restoring compiled specialization bodies. These scenarios never execute a specialization or claim active pipeline cache reuse. Lookup hit/miss behavior for metadata-only rows is unchanged. Timestamp ordering after subsequent stores/lookups is not repaired or qualified as LRU.

Status: authored manual and executable scenarios, all UNRUN. No parser, compiler, fixture, test runner, docgen, perf or RSS measurement was executed to prepare this change. Existing admitted runtime/SPipe and required core/lib/MCP gates remain pending. No coverage percentage or runtime PASS is claimed.

Source cost: successful restore traverses decoded rows once and retained keys once, using O(k) additional retained keys for k <= 50,000. Duplicate updates do not increment count. Oversize unique admission falls back to a fresh empty cache. The pre-existing SDN parser still reads/materializes the whole input: this is a retained-entry bound, not an input-byte/RSS limit. Normal new insertion adds only constant-time membership/count guards; full-capacity eviction retains its pre-existing dictionary rebuild and scan. Replacement avoids that eviction cost. Native behavior and scaled time/RSS require measurement before a nonregression claim.

Cycle2 CACHE-RESTORE-001: replacing the recorded minimum invalidates its marker. An empty marker on a populated table stays unknown across intervening inserts/replacements, and the existing eviction fallback discovers the minimum only when needed. Empty-table insertion reestablishes the marker, including after singleton eviction. Three additional production API scenarios prove oldest replacement, intervening writes and singleton behavior; all UNRUN. No extra per-store scan or new clock/field is introduced. Existing synthetic timestamp and lookup-aging limitations remain.
