# Offline application container plan preparation V1

Source: `test/01_unit/app/orchestrator/container_plan_prepare_v1_spec.spl`.
Requirements: REQ-002, REQ-005. Qualification: **source-only NOT_RUN**.
No runtime, native owner, signing, reservation or container launch was exercised.

The actual application command is:

```text
simple orchestrator container-plan-prepare <linux-podman|windows-docker-process> <candidate-context.sdn> <native-request.sdn> <config|-> <consumer> <context|-> <server|->
```

There are exactly eight arguments including `container-plan-prepare`. File paths
are absolute. `-` selects existing server-config discovery or the current
context/server defaults. The consumer is `simple`, `orchestrator`, `caret` or
`agent`. The command reads bounded regular files through application IO facades.

Candidate context V1 has exactly these fields:

| Field | Type and meaning |
| --- | --- |
| `version` | Integer `1`. |
| `kind` | Text `container-plan-candidate-context`. |
| `backend` | Exact CLI backend, checked for agreement. |
| `scope` | Text containing a canonical `container-host-scope` V2 record, generated by `container_host_scope_bytes_v2`. All values are **unverified candidate input**. |
| `providerPolicy` | Text containing the existing canonical backend policy record. Linux uses `linux_oci_engine_policy_encode_v1`; Windows uses `windows_docker_policy_encode_v1`. The Linux policy's historical `trusted-local-admin-v1` mode string does not make this input trusted or installed. |

The exact example-producing helper is
`plan_prepare_context_fixture_v1(backend)` in the executable source above. It
constructs both records through their existing canonical encoders, places the
encoded strings in the five-field V1 context, then encodes the outer SDN record.
`plan_prepare_native_fixture_v1(backend)` supplies the corresponding canonical
native retained request. These source examples are not observed machine facts.

The native input is the backend's retained request record with its semantic
digest, without a signed execution envelope. Linux uses
`linux_oci_retained_request_decode_v1`; Windows uses
`windows_docker_request_decode_v1`. The command applies a strict parser before
each existing canonical decoder, which also rejects unknown fields. The scope
decoder and both policy decoders reject unknown fields as well. Duplicate
syntax, unknown/mistyped context fields, inconsistent backends and invalid
Windows policy/scope generation or fence bindings are rejected.

The actual command source function resolves selected server configuration in
container scope and calls the typed pure pre-sign producer. It emits a complete
canonical `ContainerExecutionRequestV2` encoded as the `execution` text field,
plus request, plan, candidate-context and candidate-policy digests. The reply
sets `signingRequired` and `admissionRequired` to true and `ownerVerified` and
`executionAuthorized` to false. It does not connect to or launch containers.

| Authored scenario | Assertions |
| --- | --- |
| Both candidate backends | Real application source function returns complete canonical requests, all authority-status flags, matching digests and three reserved discovery environment entries. |
| Selected endpoint mutation | Changes both request and plan digests before signing. |
| Candidate context rejection | Rejects unknown/duplicate/mistyped fields and backend disagreement. |
| Embedded input rejection | Rejects duplicate policy syntax, unknown fields added to otherwise valid policy/scope/native records, and signed-envelope substitution. |
| CLI early validation | Rejects incorrect argument count, unsupported backend, relative file paths and unsupported consumer before IO. |

Later execution must use the existing actual owner's validation and effect
paths. The candidate policy hash is not an observed provider identity and does
not authorize a host, network, credential or engine. The actual owner verifies
its installed policy, scope, request digest and engine/network observations.

Application composition of reservation inputs, assignment binding and signing
remains a separate open lane. Existing `controller_assignment_admit_v1`,
`controller_assignment_begin_prepare_v1`, `controller_assignment_commit_v1`
and `controller_assignment_execution_ready_v1` remain the assignment state
machine. `host_authorized_prepare_v1` verifies existing signed grants/approvals
before producing a capacity reservation. `controller_dispatch_authorize_v2`
requires four independently signed actions. They are reused unchanged.

There is no admitted application issuer/approver private-key owner in this
command. Existing signature-message builders and raw Ed25519 signing primitives
do not themselves supply that authority. The prepared candidate must go through
that separate authorized composition before dispatch.
